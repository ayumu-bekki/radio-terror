## 1. 事前準備 (マネージャー)

1. 風船を適当に膨らませて Core にセットする。
2. 切断された配線(kLine)を復旧する。
   - Core は Setup 状態(フルカラーLED黄点滅)で、**結線済みの線に対応する
     kLED が点灯**する。復旧が進むほど点灯が増え、全点灯で準備完了になる。
   - 全線復旧し、サーバーと接続済みであれば Ready 状態(フルカラーLED青点灯)に
     なり、開始可能になる。

## 2. ブリーフィング (マネージャー → プレイヤー)

最低限の説明のみ行う:

- どんな遊びか
- セーフティーグラスの装着
- エレクトロニッパーの扱い方

## 3. 難易度選択とゲーム開始

1. プレイヤーが難易度(イージー / ノーマル / ハード)を選ぶ。
2. **マネージャーがトランシーバー経由で開始を申告する**。この一声が
   バインド(無線 ⇔ Core の紐付け)・難易度指定・セッション開始指示を兼ねる:

   > マネージャー「こちらマネージャー。CoreID 3701 難易度ノーマルで開始してください。どうぞ。」
   >
   > ナビゲーター「こちらナビゲーター。CoreID 3701 難易度ノーマルで開始します。」

3. サーバーは申告から CoreID(数字4桁)と難易度を抽出し、
   対象 Core が Ready であることを確認して、難易度に対応するシナリオ
   テンプレートからセッションJSONを組み立てて `session_start` を送信する。

## 4. ゲーム開始

- Core のカウントダウンが開始される。
- **ナビゲーターから先に声掛けを行い、プレイヤーの行動を促す**
  (プレイヤーの発話待ちにしない):

  > ナビゲーター「こちらナビゲーター。どうやら危険物を見つけたようですね。
  > 私がサポートするので安心してください。まずは光っている色を教えてください。どうぞ」

- 以降、プレイヤーはナビゲーターとの無線対話で解除を進める。
  **マネージャーはサポートしない**。

## 5. ゲーム中

- プレイヤーは Core の状態(LEDの光り方など)を無線で報告し、
  ナビゲーターがヒントを返す。
- Core の進行イベント(`stage_cleared` / `whack_completed` / `push_progress` /
  `wrong_action` / `exploded` / `defused`)はナビゲーターの声掛け演出のトリガーになる。

### 5.1 混線演出

たまに混線して、ナビゲーターでない人の声が聞こえてくる。
3系統・計18パターンをプールし、サーバーがランダムに再生する。

**邪魔者系**(ゲームに絡む罠。指定する色は正解以外から選ぶ)

| 役 | セリフ例 |
|---|---|

| 邪魔者(自称犯人) | 「ナビゲーターを信じるな!私は作った本人だ。いいから黄を切れ!」 |
| 邪魔者(囁き) | 「……青だ……青を切れば、全部終わる……」 |

**環境ボイス系**(無害な生活ノイズ。世界の広がりと笑いを担当)

| 役 | セリフ例 |

**不穏系**(世界観を深める。色や操作の指示は一切しない)

| 役 | セリフ例 |
|---|---|
| 黒幕らしき独り言 | 「……気づかれてる?いや、まだだ。まだ大丈夫……」(誰かが装置の様子を見ている気配。ヒバリ黒幕説 — `navigator_design.md` §2.2 — と響き合う。ただし声はナビゲーターとは別にし、音で直接確定させない) |
| 別現場の通信 | 「こちら現場B、解体失敗。繰り返す、解体は失敗した。総員退避——ザザッ」(よその現場の失敗が漏れ聞こえる) |

**イベント駆動の混線**: 「別現場の通信」はランダム再生に加え、**並行プレイ中の
他チームのCoreが実際に爆発(`exploded`)した直後**に、Playing中の他チームの
無線へ流すことができる。会場に響いた本物の破裂音と通信内容が一致し、
「今の音はあれか……」という強い臨場感が生まれる。ゲームサーバーは全Coreを
管理しているため、イベントの横流し先(他のバインド済みbridge)の解決だけで実現できる。

**共通ルール**

- **混線音声はすべて事前生成**(TTSの事前レンダリングまたは収録)した
  音声アセットを再生する。実行時のTTS生成は行わない。
  - 邪魔者系: 色を指定する部分は**5色分のバリエーションを事前生成**
    (3パターン×5色=15ファイル)し、再生時に「現在の正解以外」の色の
    ファイルをサーバーが選ぶ(偶然正解と一致して「邪魔者を信じたら成功した」
    となるのを防ぐルールは維持)。
- **アセットの配置とファイル名規約**(サーバーはこの規約でファイルを走査する):

  ```
  assets/crosstalk/jamming/{name}_{色}.ogg   … 色サフィックスは A-E
  assets/crosstalk/ambient/{name}.ogg
  assets/crosstalk/uneasy/{name}.ogg
  assets/sfx/success.ogg, assets/sfx/failure.ogg
  ```

  形式は **Ogg Opus**(radio-bridge がそのままキューへ積んで再生する)。
  「別現場の通信」はイベント駆動再生でサーバーが名前指定で参照するため、
  ファイル名を `uneasy_bessgenba.ogg` に固定する。
  制作用の一覧は `app/game-server/assets/README.md` に置く。
- **アセットが未制作でもサーバーは起動する**(該当の再生がスキップされ、
  ログとマネージャー向けWeb画面に読み込み数が出る)。コンテンツ制作を
  待たずにゲーム進行の検証ができる。
- 発生タイミングはゲーム中のランダム。系統別の再生回数は難易度テンプレートで
  指定する(初期値は `scenario_design.md` §4.1。控えめ運用でゲームのテンポを優先)。
- **イージーでは邪魔者系を再生しない**(誤切断の既定がexplodeのため、
  初心者が邪魔者を信じて即失敗する事故を防ぐ)。ノーマル以上で解禁。
- **不穏系は色・操作の指示をしない**(邪魔者との役割分担を守り、混乱を防ぐ)。
- ナビゲーターの発話と重ならないようサーバー側でスケジュールする。
  実装ではカウントダウンを再生回数+1で区切り、各区間内のランダムな時刻に
  1回ずつ流す(開始直後と終盤に寄らないよう散らす)。

  **重なり判定は「無線が塞がっている終了予定時刻」で持つ**。
  当初は「発話中か」の真偽値だったが、サーバーが最後のパケットを
  送った時点でフラグが落ちるため、**bridge がこれから十数秒かけて
  再生する間に混線が割り込んでいた**(実運用で発生)。
  bridge から再生完了を受け取る経路は proto に無いので、
  **送出した音声の再生時間**(発話は PCM のサンプル数、混線・効果音は
  Ogg の granule position から算出)を現在時刻に足した時刻を保持し、
  それまでは塞がっているとみなす。PTT の on/off と経路遅延ぶんの
  余裕(2秒)を加える。

  発話は生成時間が事前に分からないため、生成開始時に見込み(30秒)で
  押さえ、送出後に実測値へ差し替える。生成に失敗した場合は取り消す。
  再生時刻に塞がっていた場合は鳴り終わりまで待ち(最大3回)、
  それでも空かなければその回は見送る。
- 花火大会(「打ち上げ3分前」)は爆発物と紛らわしいのが狙いの小ネタ。

## 6. 終了

- **解除成功 (Defused)**: フルカラーLED緑点灯。残り時間が停止表示され、スコアになる。
  トランシーバーから成功の効果音とメッセージを再生する:
  > (成功効果音)「無事に解除できましたね。おめでとう!」
- **失敗 (Exploded)**: 赤点灯+ブザーで2秒ためてから風船破裂。
  トランシーバーから失敗の効果音とメッセージを再生する:
  > (失敗効果音)「ありゃりゃ?生きている?」

  `exploded` はソレノイド駆動前(失敗確定時点)に届くため、破裂音と無線演出を同期できる。

**効果音とメッセージは1つの Ogg にまとめて送る**。効果音を別パケットで先に
送ると、効果音が鳴り終わってから TTS の生成を待つ**数秒の無音**が無線に乗る
(PTT を握ったまま黙る形になり、間が抜ける)。TTS の生成完了後に、
効果音の PCM を発話の前へ連結して**1回だけエンコード**し、1パケットで送出する。

生成に数秒かかるぶんがそのまま「効果音 → メッセージ」の間になるため、
**意図的なインターバルは入れない**。

効果音アセットは TTS と同じ **24kHz mono** で用意する。レートやチャンネル数が
違うと連結時に再生速度が狂うため、`decodeOggOpusToPCM` が弾いて
効果音なしで発話だけを送る(ログに WARN を残す)。
- マネージャーが強制リセット(§7)で Setup に戻し、§1 の準備に戻る。

## 7. マネージャーの音声コマンド

| コマンド | 例 | 動作 |
|---|---|---|
| 開始申告 | 「こちらマネージャー。CoreID 3701 難易度ノーマルで開始してください。どうぞ。」 | バインド+難易度指定+`session_start` 送信(§3) |
| 強制リセット(キルスイッチ) | 「こちらマネージャー。CoreID 3701 リセット でんぱ」 | **秘密ワード**(例:「でんぱ」)が一致した場合のみ、対象 Core へ `session_abort` を送り Setup へ戻す |
| 強制破裂 | 「こちらマネージャー。CoreID 3701 強制爆破 でんぱ」 | **秘密ワード**が一致した場合のみ、対象 Core へ `force_detonate` を送る。**風船が実際に割れる** |

- 秘密ワードはサーバー設定(`[manager] secret_word`)で定義し、運営内でのみ共有する
  (プレイヤーがマネージャーを騙ってリセット・破裂させるのを防ぐ)。
  リセットと強制破裂で同じワードを使う(運営が覚えることを増やさないため。
  どちらもキーワードが別なので取り違えない)。
- リセットはどの状態(Playing / Exploded / Defused)からでも可能。
- **強制破裂は Playing 中のみ**有効。それ以外の状態では送信せず、記録も残さない。
- **強制破裂したセッションは失敗として終了する**。デバイスが返す `exploded` を
  契機に、通常の失敗(時間切れ・誤切断)と同じ演出・スコア確定・履歴記録が動く。
  バインドは残るため、次のプレイへ進むには**リセット申告が必要**
  (爆発後の通常の流れと同じ。§6)。
- **誤認識対策**: 開始申告はナビゲーターが復唱応答する(§3)ため、誤認識されて
  いたらマネージャーが言い直す(バインド・難易度は後勝ちで上書きされる)。
  秘密ワードの一致判定は**かな正規化のゆるい一致**とする(認識ゆれで
  キルスイッチが効かない事態を防ぐ。ワード自体が運営外秘のため緩くても安全)。

### 7.1 意図抽出の判定条件

文字起こし結果に対し、次を**すべて**満たす場合にコマンドとして扱う。
コマンドと判定された発話はナビゲーターの会話へは流さない。

| コマンド | 判定条件 |
|---|---|
| 開始申告 | 4桁の数字(CoreID) **かつ** 難易度語 **かつ** 開始の意図語(「開始」「始め」) |
| 強制リセット | 4桁の数字(CoreID) **かつ** 秘密ワード **かつ**「リセット」 |
| 強制破裂 | 4桁の数字(CoreID) **かつ** 秘密ワード **かつ**「強制爆破」「強制破裂」「ばくは」のいずれか |

- **かな正規化**: カタカナ→ひらがな、長音・区切り記号・空白の除去、英字の小文字化。
  秘密ワードの一致はこの正規化後の部分一致で判定する。
- **難易度の語彙**: イージー / ノーマル / ハード に加え、ひらがな表記・英語表記
  (easy/normal/hard)・「簡単」「普通」「難しい」も受け付ける。
- 開始申告は**すべての条件が揃ったときのみ**成立する。CoreIDだけ・難易度だけの
  発話は通常の交信として扱われるため、プレイヤーの雑談が誤ってセッションを
  開始することはない。
- **強制破裂はリセットより先に判定する**。語が違うので競合しないが、
  取り返しのつかない操作を先に確定させる。
- 無線が使えない場合の代替として、**マネージャー向けWeb画面の
  ダッシュボード (`/manager`) からも強制リセット・強制破裂ができる**
  (それぞれ `session_abort` / `force_detonate` を送る)。
  強制破裂のボタンは赤くし、確認ダイアログで**風船が割れること**を明示する。

### 7.2 疎通確認 (カラス)

セッション開始前 — まだどの Core にもバインドされていない状態 — で無線に話しかけると、
**「カラス」**というコールサインの相手が応答する。会場設営時に
**無線・PTT・文字起こし・TTS の経路がつながっているか**を確かめるための機能。

> スタッフ「こちらマネージャー。感度はどうか。どうぞ」
>
> カラス「こちらカラス。感度良好だ。どうぞ」

- 応答は生成AIが作るため、内容は毎回変わる。**返事が返ってくること自体**が
  経路の疎通を示す。
- **カラスは雑談に応じる。** 「たまたま同じ周波数に居合わせた無線好き」という
  設定で、天気・近況・機材の話などに普通に乗る。テスト用と分かる応答にすると
  会話が続かず、音声品質や聞き取りやすさの確認がしにくいため。
- **カラスだけ Google 検索を使える。** 天気・店の営業時間・観光地など、
  実世界の情報を聞かれても「分からない」で終わらせない。
  **ナビゲーターでは使わない** — 検索は1往復ぶんレイテンシが増え、
  カウントダウン中の応答が遅れる。正解はセッションJSONで渡されるため
  ナビゲーターに外部情報は不要。
- カラスは**ゲームの内容(装置・解除手順・正解)を知らない**。尋ねられても
  「何の話だ、こっちにはさっぱりだ」と素で分からない反応を返し、
  その話題には立ち入らない(運営の事情を説明する言い方もしない)。
- 開始申告(§7)が成立するとバインドされ、以降はナビゲーターが応答する。
  疎通確認の交信ログは本番の文脈へ持ち越さない。
- ナビゲーターの4キャラクター(フクロウ/ヒバリ/アオサギ/ヨタカ)とは
  別の声・別の名前にしてあるため、本番の交信と混同しない。

**返事が返ってこない場合**は §7.1 のトラブル対応(無線が繋がらない)へ。

## 8. 無線構成の前提

- **Coreは複数台の並行運用が可能**な構成とする(CoreIDは数字4桁で識別。
  現行の会場計画では2台を用意する想定)。
- チームごとに特定小電力トランシーバーの**周波数を分離**する。
- radio-bridge は周波数(チーム)ごとに1プロセスとし、それぞれ**専用の
  オーディオインターフェース**で入出力する。PTT制御のGPIOピンもプロセス
  (Raspberry Pi・PCB配線)ごとに異なる。
  プロセスごとに変わる設定(bridge ID・オーディオIF・PTT用GPIOピン)は
  **環境変数**で指定し、`config.toml` は全プロセスで共有する
  (`bridge_connection_design.md` §6.1)。チームの増設は環境変数を変えた
  プロセスを追加するだけで済む。
- マネージャーは開始申告時に対象チームの周波数に合わせて話す。これにより
  申告は対象チームの bridge のみが受信し、バインド(`bridge_connection_design.md`
  §5)が正しい bridge に対して成立する。

| 3 | 混線演出 | ゲーム中にランダムでナビゲーター以外の声を再生する(§5.1)。邪魔者系・環境ボイス系・不穏系の3系統18パターン。邪魔者の色指定は正解以外から選び、不穏系は指示をしない。「別現場の通信」は他チームCoreの `exploded` を契機にしたイベント駆動再生にも対応 |

| 7 | 邪魔者系と難易度 | イージーでは邪魔者系を再生しない(ノーマル以上で解禁)(§5.1) |
| 8 | 会場構成 | Coreは複数台の並行プレイに対応(台数固定にしない)。現行の会場計画は2台想定(§8) |
| 9 | 音声コマンドの誤認識対策 | 開始申告は復唱応答+言い直し(後勝ち上書き)で担保。秘密ワードはかな正規化のゆるい一致(§7)。プレイヤー発話側のポリシーは `navigator_design.md` §3.6 |
| 4 | キルスイッチ | マネージャーの秘密ワード付き音声コマンドで強制リセット(§7)。既存の `session_abort` で実現し、新規プロトコルは不要 |

| 10 | カラスを雑談相手にする | 「疎通確認用」と分かる応答だと会話が続かず、音声品質や聞き取りやすさの確認がしにくい。**たまたま同じ周波数にいる無線好き**という設定にして雑談に応じさせた。ゲームの話題は『何の話だ』と素で分からない反応で打ち切る(運営の事情は説明しない)(§7.2) |
| 11 | 検索はカラス限定 | 天気・営業時間など実世界の情報に応じられるよう **Google 検索グラウンディングを有効化**。ただし検索は1往復ぶん遅くなるため**ナビゲーターでは使わない**(カウントダウン中の体験を損なう)。無線で読み上げるため、箇条書き・URLを出さず1〜3文で言い切らせる(§7.2) |
| 12 | 混線の重なり判定を**再生時間ベース**に変更(実機確認時) | 「ナビゲーターが発話中か」を真偽値で持っていたが、**送出完了と再生完了がずれる**。サーバーが最後のパケットを送った時点でフラグが落ち、bridge がこれから十数秒かけて再生する間に混線が割り込んでいた(実運用のログで確認。発話の送出と同じ秒に混線が積まれ、次の発話が7秒押しのけられた)。bridge から再生完了を受け取る経路は proto に無いため、**送出した音声の再生時間から終了予定時刻を推定**する方式にした(§5.1)。発話は生成時間が読めないので見込み30秒で押さえ、送出後に実測へ差し替える |
| 13 | granule position を **48kHz 基準に修正**(実機確認時) | 決定12で音声の尺を granule から求めようとして発覚。`encodePCMToOggOpus` が granule を**入力と同じ 24kHz で数えていた**が、Opus の granule は入力レートによらず**常に 48kHz 基準**(RFC 7845 §4)。このため granule から尺を求めると**実尺の半分**になる。再生自体はデコード後のサンプル数で行われるため表面化していなかったが、**radio-bridge の音声長上限(30秒)チェックが実尺60秒まで通す**状態になっていた。エンコーダ側を RFC 準拠に直して解消(bridge 側の変更は不要) |

| 14 | 効果音とメッセージを**1つの Ogg に連結**(実プレイで発覚) | 爆発後、効果音が鳴り終わってからメッセージが流れるまでに**数秒の無音**が入っていた。効果音を別パケットで先に送っており、その後 TTS の生成を待つ時間がそのまま無線の空白になっていたため(PTT を握ったまま黙る形)。TTS の生成完了後に**効果音の PCM を発話の前へ連結し、1回だけエンコードして1パケットで送る**方式へ変更(§6)。生成にかかる数秒がそのまま「効果音 → メッセージ」の間になるので、**意図的なインターバルは入れない**。Ogg Opus を PCM へ戻す `decodeOggOpusToPCM` を追加した。効果音アセットは TTS と同じ 24kHz mono である必要があり、違う場合は連結せず発話だけ送る(WARN ログ) |
