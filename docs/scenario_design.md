# シナリオテンプレート設計 (game-server)

セッションJSONとナビゲーター用コンテンツを組み立てるシナリオテンプレートの設計。

- 作成日: 2026-08-08 / 更新日: 2026-08-09
- ステータス: **実装済み**。TOMLのフィールド詳細は §3.1-3.4 に確定版を記載。
  実装由来の決定は §7 決定記録
- 関連: `game_session_design.md`(セッションJSON仕様) /
  `puzzle_stage_ideas.md`(ステージ内容) /
  `printed_materials.md`(紙資料の印刷内容) /
  `navigator_design.md`(プロンプト構成) / `operation_flow.md`

## 1. 全体構造

```
scenarios/
├── stages/                  … ステージ定義プール(1ステージ1ファイル)
│   ├── 01_kaitai_debut.toml
│   ├── 02_signal.toml
│   ├── ...
│   └── B_hayaimono_gachi.toml
└── difficulty/              … 難易度テンプレート
    ├── easy.toml
    ├── normal.toml
    └── hard.toml
```

- 形式は **TOML**(既存configと統一。コメントが書けて人間が編集しやすい)。
- ステージ定義は**1ステージ1ファイル**。追加・差し替え・レビューがしやすく、
  保留中のステージもファイルを置くだけで将来復活できる。

## 2. 組み立てフロー

マネージャーの開始申告(CoreID+難易度)を受けたサーバーは:

1. 難易度テンプレートを読み、構成ルール(固定並び+タグ抽選)でステージを選ぶ
2. 各ステージの抽選定義(切る線・色・ボタン列・モールス語など)を解決する
3. 解決結果から**2つの成果物を同時に生成**する:
   - (a) **Core向けセッションJSON**(`game_session_design.md` §6)
   - (b) **ナビゲーター向けステージ知識**(正解込み。プロンプトの
     動的ブロック[D]に注入する)
4. 両方を Valkey に保存して `session_start` を送信する

(a)と(b)は同一の抽選結果から機械的に生成するため、**実機の状態と
ナビゲーターの知識は構造的に一致する**(食い違いはこのゲームで最も
致命的なバグなので、別々に人手で書く運用はしない)。

## 3. ステージ定義ファイル

ナビゲーターのヒント文は**固定台詞ではなく「知識+レベル別指針」**として書き、
実際の台詞は思考モデルがキャラクター口調で生成する(`navigator_design.md` §3)。
固定で伝えるべき値(手順の数値など)は知識側に明記する。

記述例(B. 早い者勝ち):

```toml
id = "B"
name = "早い者勝ち"
difficulty = "easy"        # easy / normal / hard のタグ

# --- 抽選定義 (組み立て時に解決される変数) ---
[random]
cut  = { pick = "line" }                          # 空いている線から切断線を抽選
slow = { pick = "color", exclude = ["${cut}"] }   # 比較用のもう1本 (線は消費しない)

# --- Core向けセッションJSONの生成規則 ---
[core]
leds = { "${cut}" = { pattern = "blink", on_ms = 150, off_ms = 150 }, "${slow}" = { pattern = "blink", on_ms = 700, off_ms = 700 } }
cut = "${cut}"

# --- ナビゲーター向けステージ知識 ---
[navigator]
briefing = "2つのランプが点滅している。速く点滅している色の線を切れば解除できる。"
observation = "2つのランプが点滅しており、片方が速く・もう片方が遅いことを報告できたか"
answer   = "正解は${cut}色の線(${slow}色より速く点滅している方)。"
hint_l1  = "2つの点滅しているランプに注目させる"
hint_l2  = "点滅の速さに違いがあることに気づかせる"
hint_l3  = "『速く点滅している方の色の線を切る』と手順を教えてよい(色名は言わない)"
# L4(直言)は answer をそのまま使うため定義不要
```

### 3.1 抽選定義 (`[random]`) の記法

変数は `${...}` で `[core]` / `[navigator]` の両方から参照する。
定義同士も `${...}` で参照でき、依存関係は解決順を自動で入れ替えて処理する
(循環参照は組み立て時エラー)。

| 記法 | 内容 |
|---|---|
| `{ pick = "line" }` | **切断線**を抽選する。ステージ間で重複しないよう、既に他ステージへ割り当て済みの色は候補から外れる |
| `{ pick = "color" }` | 任意の色を抽選する。**切断線の重複制約を受けない**(演出用のLED色など) |
| `{ pick = "colors", count = "N" }` | 複数色をまとめて抽選する(カンマ区切りで展開される) |
| `{ pick = "int", min = A, max = B }` | 範囲内の整数を抽選する(ロータリー位置・匹数など) |
| `{ pick = "choice", candidates = [...] }` | 候補から1つ選ぶ |
| `{ derive = "rank_slot", cut, rank, slot, others }` | cut を **rank 番目**に置き、残りを others の順で詰めた並びの **slot 番目**を返す。「N番目に速い色を切れ」のように**正解の順位を毎回抽選したい**場合に使う(208)。rank / slot は1始まり。cut は `pick = "line"` で先に引いておく(§7 決定19) |
| `{ pick = "choice", as_line = true, ... }` | 選んだ値を**切断線として扱う**。既に他ステージで切られた色を候補から除く。表示は全色出したまま正解だけを未使用線に限りたい場合に使う。**候補が少ないと全て使用済みになって組み立てが失敗する**ため、候補が2〜3個しかない場合は代わりに `pick = "line"` を先に引き、残りの表示色をそこから除外して埋める(208 がこの理由で切り替えた。§7 決定16)。現在の使用箇所は無効化中の293のみ |
| `{ pick = "morse_word", candidates = [...] }` | モールス語を選ぶ。頭文字→対照表の色が既に使われている語は候補から外れる |
| `{ pick = "romaji_word", candidates = [...] }` | 色名のローマ字表記を選ぶ(305)。表記がそのまま色に対応するため、既に切られた線の語は候補から外れる |
| `{ pick = "noise_leds", exclude = [...], on_ms_min = A, on_ms_max = B }` | 妨害用LEDの割り当てを生成する(304)。`exclude` 以外の全色へ「点灯 / 消灯 / **対称blink**」をランダムに割り当てる。点滅は `on_ms == off_ms` を保証する |
| `{ pick = "color_seq", count = "N" }` | **順番に意味がある色の列**を引く(201 復唱 のボタン列)。`colors` と違い**重複を許し、引いた順のまま**返す(並べ替えない)。「赤赤黄黄赤」の繰り返しはこのステージの持ち味。ただし**同じ色の3連続は避ける** — 無線で「赤赤赤」と読み上げると何個言われたか数えられない |
| `{ pick = "rotary_layout", count = "N" }` | 206 綱渡り の**目的位置と禁止位置を配置ごと**抽選する。返り値は `"target,f1[,f2]"` で、`nth` / `tail` で取り出す。**位置を個別に引かない** — 禁止が2つのとき隣接/離れている/目的地を挟むで難しさの質が変わり、個別だと偏るうえ**目的位置の両隣が禁止**(逃げ場ゼロ)が出る。成立する配置だけを列挙して等確率で引く(ADR S-10) |
| `{ derive = "tail", from = "${x}", index = N }` | カンマ区切りの N番目以降を**まとめて**返す。数が可変のリストを `positions = ["${x}"]` へ渡すのに使う(`nth` だと要素数が減ったとき範囲外になる) |
| `{ pick = "codebook", cut = "${cut}" }` | 202 の対照表から **cut になる表示を1通り選ぶ**。返り値は `"1011"` のような4桁2進表記で、他の変数はこれを `codebook_field` で読み直す。**表示を先に抽選しない** — cut が表側で決まると他ステージとの色の重複を避けられない(ADR S-1・S-2) |
| `{ derive = "choice_value", from = "${x}", <候補> = "値", ... }` | `choice` の抽選結果をキーにして値を引く(207)。`odd = { pick = "choice", candidates = ["fast","slow"] }` に対し `odd_ms = { derive = "choice_value", from = "${odd}", fast = "300", slow = "650" }`。**抽選結果に応じて変わる値を別々に人手で書かない** — 片方だけ直し忘れると謎が成立しないまま組み立てが通る。対応するキーが無ければ組み立てエラー |
| `{ derive = "codebook_field", from = "${pattern}", field = "..." }` | 選ばれた表示から1項目を取り出す(202)。`field` は `lit`(点灯色) / `dark`(消灯色) / `word`(キーワード) / `rotary`(ダイヤル位置) / `pattern`(4桁2進表記)。**点灯色とキーワードを別々に人手で書かない**ため(ADR S-1) |
| `{ derive = "...", from = "${x}" }` | 抽選ではなく他の変数から機械的に導出する(`morse_word_color` / `romaji_color` / `terminal_for_color` / `nth` / `spoken_letter`) |

- どの記法にも `exclude = ["${x}", ...]` を付けられる(その値を候補から外す)。
- `precondition.push_seq` は `entries` を直接書くほかに、
  **`colors = "${seq}"`**(カンマ区切りの色列)で書ける。各色が
  `{ push = "<色>" }` の1エントリへ展開される。**列の長さが難易度で変わる**
  ステージ(201 復唱)はこちらを使う — `entries` を書くと個数が固定される。
- `${load_*}` は暗黙変数で、**難易度テンプレートの `[load]`** に展開される
  (§4.2)。`${load_color_match_min}` など。**難易度で変えたい量**をここから引く。
- `${rest}` は暗黙変数で、「`cut` 以外の全色」に展開される
  (207 息が合わない の「残り4色を同じ周期で点滅」などに使う)。
- **キーにも `${...}` を書ける**。複数色に展開されるキー(`${rest}` など)は、
  同じ値が各色へ配られる。
- 展開後に数値として解釈できる文字列は**数値に戻す**
  (`rotary = "${rotary}"` は最終的にJSONの数値になる)。
- `noise_leds` の結果は `[core]` で **`noise_leds = "${変数名}"`** と書くと
  `leds` テーブルへマージされる。**既に `leds` に指定のある色は上書きしない**
  (モールス表示用のLEDが妨害で潰れると謎が成立しないため)。

```toml
[random]
display = { pick = "color" }
noise   = { pick = "noise_leds", exclude = ["${display}"], on_ms_min = 200, on_ms_max = 900 }

[core]
leds = { "${display}" = { pattern = "morse", word = "${word}", unit_ms = 300 } }
noise_leds = "${noise}"   # 残り4色へ妨害表示がマージされる
```

### 3.2 ステージ属性

**ステージIDは3桁で、百の位が難易度を表す**(1xx=簡単 / 2xx=普通 / 3xx=難しい。
`puzzle_stage_ideas.md` §2)。ファイル名 `{ID}_{名前}.toml` がそのまま
難易度順に並ぶため、一覧性が高い。`id` と `difficulty` は必ず整合させる。

| キー | 内容 |
|---|---|
| `difficulty` | `easy` / `normal` / `hard` のタグ。抽選の対象を決める |
| `easy_only` | `true` のステージはイージー以外で選出しない(101) |
| `[hints]` | ヒント閾値の**ステージ単位の上書き**(任意)。書いた項目だけが難易度の値を差し替える。206 は `l4_pct = 0` で直言を塞ぐ(ADR N-36) |
| `keep_cut_secret` | `true` にすると**L4 でも切る線の色名を伏せ続ける**。色名を言うと課題そのものが消えるステージ(205・202・203)に付ける。散文の但し書きは L4 で負けるため、フラグで機械的に分岐させる(ADR N-38) |

### 3.3 ナビゲーター知識 (`[navigator]`)

- `briefing`: ステージ開始時にプレイヤーへ伝える内容(の要旨)
- `observation`: **プレイヤーに報告してほしい観察**。発話生成と同じ呼び出しで
  「報告できたか」を判定させ、できていればヒントレベルを L2 へ前倒しする
  (`navigator_design.md` §3.2 / ADR N-35)。**全ステージに定義する**。
  「**〜を報告できたか**」と**判定条件の形**で書くこと — 装置の状態を
  書き写すと、モデルが自分の知識と照合して常に true を返す
- `answer`: 正解と理由。L4(直言)とヒント整合の根拠に使う
- `hint_l1`〜`l3`: レベル別の「何をどこまで教えてよいか」の指針。
  **`hint_l1` は報告を受けた後の返し先まで書く** — 「報告を受けてから
  見比べるよう促す」で終わると、**報告済みの相手に空振りが返る**(決定61)
- `procedure`(任意): 会話の進め方。対話で誘導するステージ(101・202・104・203)で、
  手順の区切り方・聞き返しへの対応をプロンプトへ渡す
- 紙資料に依存するステージ(202・203・205)は、シートの内容(記号の数・
  対照表の色割当など)を知識に含める。07のシート物理定数はサーバー設定から
  参照する(`puzzle_stage_ideas.md` §7)。

### 3.4 保留中のステージの無効化

ロードするのは拡張子 `.toml` のファイルのみ。保留中のステージは
`.toml.disabled` にしておけば、ファイルを置いたまま無効化できる
(採用時はリネームするだけで復活する)。

## 4. 難易度テンプレート

記述例(easy.toml):

```toml
name = "イージー"
countdown_ms = 300000        # 5分
detonate_delay_ms = 2000

[compose]
fixed_head = ["01"]          # 先頭固定(解体デビュー)
random = { easy = 1 }        # 残り枠を「簡単」タグから抽選

[crosstalk]                  # 混線の系統別再生回数上限
jamming = 0                  # イージーは邪魔者系なし
ambient = 1
uneasy  = 0

[hints]                      # ステージ予算(countdown÷ステージ数)に対する比率(%)
l2_pct = 25
l3_pct = 50
l4_pct = 75
```

### 4.1 難易度別パラメータ初期値

いずれも実機テストで調整する前提の初期値。

| パラメータ | イージー | ノーマル | ハード |
|---|---|---|---|
| カウントダウン | 300秒(5分) | 420秒(7分) | 600秒(10分) |
| ステージ数 | 2 | 3 | **4** |
| 構成 | 簡単×2(01固定+抽選) | 簡単×1 + 普通×2 | 普通×2 + 難しい×2 |
| ステージ予算(1ステージあたり) | 150秒 | 140秒 | **150秒** |
| ヒント閾値 L2/L3/L4(予算比 25/50/75%) | 約38/75/113秒 | 35/70/105秒 | 約38/75/**無効** |
| 混線回数(邪魔者/環境/不穏) | 0 / 1 / 0 | 1 / 1 / 0 | 1 / 1 / 1 |

- ステージ数は**最大4**(配線5本のうち1本以上を余らせる。§4 と
  `puzzle_stage_ideas.md` §5)。ハードはステージ数が減った分、
  1ステージあたりの持ち時間はイージーと同じ150秒になるが、
  出題内容が「普通・難しい」に寄るため難度は上がる。

- ヒント閾値は固定秒ではなく**ステージ予算に対する比率で自動算出**する。
  難易度・ステージ数を変えても「直言が予算内に必ず来る」整合が保たれる。
  質問回数・誤操作による前倒し(`navigator_design.md` §3.2)は従来通り。
- **ハードは `l4_pct = 0` として L4(直言)を無効にする**
  (`navigator_design.md` §3.2 の「イージー・ノーマルのみ直言」に対応)。
  比率0が無効化の指定であり、質問回数・誤操作による前倒しも
  無効なレベルへは到達しない。
- 混線は控えめ運用とし、演出よりゲームのテンポを優先する。
  イベント駆動の「別現場の通信」(`operation_flow.md` §5.1)は回数枠の外
  (該当イベント発生時のみ)。

### 4.2 難易度で変える入力量 (`[load]`)

**押す回数のような「量」は難易度テンプレートに置く**。ステージ定義へ
数値を直書きすると、イージーでもハードでも同じ負荷になる。

```toml
# scenarios/difficulty/hard.toml
[load]
color_match_min = 9
color_match_max = 12
```

ステージ側は変数として参照する:

```toml
# 204 色合わせ
count = { pick = "int", min = "${load_color_match_min}", max = "${load_color_match_max}" }
```

| 項目 | イージー | ノーマル | ハード | 使うステージ |
|---|---|---|---|---|
| `color_match_min` / `_max`(押す回数) | 4〜6 | 6〜9 | 9〜12 | 204 色合わせ |
| `forbidden_rotary_count`(禁止位置の数) | 1 | 1 | **2** | 206 綱渡り |
| `push_seq_len`(ボタン列の長さ) | 5 | 5 | **8** | 201 復唱 |
| `speed_rank_ms`(点滅速度4段階) | 150/300/550/1000 | 同左 | **150/210/294/412** | 205 速さくらべ |

- **未設定(0)は起動時に落とす**。「押す回数0回」の成立しないステージに
  なるが、書き忘れは**抽選次第でしか現れない**ため
  (`terminal_map` の5色必須と同じ性質)。
- **伸ばしすぎない**。206 は押し終えるまで手がかりが増えず、
  押している間はナビゲーターが黙る(ADR N-26)ため、
  長いほど無線が沈黙する時間が延びる。
- **回数はナビゲーター知識に入れない**(ADR N-42)。ナビゲーターは装置を
  見ておらず今何回目かを追えないため、知っていると実況して嘘になる。

- `compose` はハイブリッド方式: `fixed_head` / `fixed_tail` で固定並びを指定し、
  `random` でタグ別の抽選数を指定する。合計ステージ数は最大4(§4.1)。
- 同一ステージの重複選出はしない。切断線はステージ間で重複しないよう
  組み立て時に割り当てる。
- タグ別に抽選した分は**並び順もシャッフル**する(タグ順に固まらないようにする)。
  固定並び(`fixed_head` / `fixed_tail`)の位置は保つ。

## 5. サーバー側の検証

組み立て後、`session_start` 送信前にサーバー側でも検証する
(Core側の検証 `game_session_design.md` §6.2 と同等の項目+テンプレート起因の項目):

- 切断線がステージ間で重複していないこと・A-Eのいずれかであること
- ステージ数が4以下であること(切断線を1本以上余らせる。§4.1)・
  `countdown_ms` が表示上限(999,900ms)以内であること
- `color_match` と `push_seq` が併用されていないこと
- ロータリー位置(`precondition.rotary` / `forbidden_rotary.positions`)が0-5の範囲であること
- 抽選変数が全て解決されていること(未解決の `${...}` が残っていない。
  キー側・値側の両方を再帰的に確認する)
- ナビゲーター知識(answer)と Core向けJSON の正解が一致していること。
  `answer` が `cut` の色に**色記号(A-E)または日本語色名(赤/黄/緑/青/白)で
  言及している**ことを確認する。この食い違いはゲームで最も致命的なバグなので、
  組み立て時に必ず弾く

これらは組み立てのたびに実行され、失敗した場合は `session_start` を送らずに
エラーとする(不整合なセッションを実機へ流さない)。

## 6. Valkey への保存

セッション状態・ログ・スコアは Valkey に永続化する
(`game_session_design.md` §9)。キー設計の概要:

| キー | 内容 |
|---|---|
| `session:{session_id}` | **進行中(バインド中)セッションのみ**の本体: Core向けJSON、ナビゲーター知識、difficulty、bridge_id ⇔ device_id、状態(stage_index・remaining等の最新報告)、キャラクター割当、スコア(`defused` 時の残り時間)。再起動時の復元・進行中ダッシュボード表示専用。**リセットのたびに(終了後の定型リセットも含め)無条件に消える** |
| `history:{session_id}` | セッション終了(爆発・解除)の瞬間に一度だけ書く要約スナップショット。内容は `session:{session_id}` と同形の JSON。Web履歴一覧・詳細ページはこちらを読み、`session:{session_id}` が消えても残る(`game_session_design.md` §10 決定62) |
| `session:{session_id}:log` | 会話・進行イベントのログ(リスト)。発話とイベントを**1本のタイムライン**に時系列で残す。中断でも消さない |
| `binding:{bridge_id}` | 現在のバインド先 device_id |

- サーバー再起動時は Valkey から復元し、Core からの `device_status` で
  進行状態を再同期する。ナビゲーターは正解・文脈を保ったまま復帰できる。
- ランキング等の集計機能は作らない。
- **ヒントレベルの判定材料(ステージ開始時刻・質問回数・誤操作数)は永続化しない**。
  復元時はそのステージのL1から再開する(復帰直後に直言が出るのを避ける)。
- **Valkey に接続できない場合はメモリ実装へフォールバック**して起動を続ける。
  再起動での復帰はできなくなるが、開発時や Valkey 障害時にゲーム自体は動く。
  設定で `[valkey].addr` を空にした場合も同様にメモリのみで動作する。
- プロンプトへ渡す会話ログは**直近30件**に絞る(プロンプト長の抑制)。
  Valkey 側には全件を残す。
- **ログには発話と進行イベントの両方を記録する**。イベントは
  `kind = "event"` とし、`event`(種別)・`stage_index`・`remaining_ms` を伴う。
  記録するのはセッション開始・ステージ開始/クリア・色合わせ完了・
  ボタン列進捗・誤操作・解除成功・爆発・強制リセット。
  「ナビゲーターが何を言った直後に誤切断したか」を1本の流れで追える。
- イベントはナビゲーターのプロンプト文脈にも `(装置) …` の形で含める
  (直前の出来事を踏まえた発話ができるようにするため)。
- 全記録に**記録時刻(Unix秒)**を付ける。

## 7. 決定記録

| # | 論点 | 決定 |
|---|---|---|
| 1 | 形式 | TOML(既存configと統一)。ステージ定義は1ステージ1ファイル(§1) |
| 2 | 生成物 | 同一の抽選結果から Core向けJSON とナビゲーター知識を**同時生成**する。別々に人手で書く運用はしない(§2) |
| 3 | 構成方式 | ハイブリッド(固定並び + タグ抽選)。合計ステージ数は最大4(§4.1) |
| 4 | ヒント閾値 | ステージ予算に対する比率で自動算出。**比率0は無効化**を意味し、ハードは `l4_pct = 0` で直言を出さない(§4.1) |
| 5 | ステージ数の上限(実装時) | 当初ハードを5ステージ(全配線)としたが、全色を使い切ると切断線の抽選に余地が無くなり、切る色が構造的に決まる203が組み立て不能になる問題が判明。**上限を4ステージにして必ず1色以上余らせる**方式へ変更した。あわせて09の候補語を全5色分揃え、割り当て順の特別扱い(当初導入した `line_constrained`)は**廃止**した(`puzzle_stage_ideas.md` §5) |
| 6 | 07の閾値導出(実装時) | 閾値 = シート実測値 + 2、比較方向は「未満」固定。実測値から離れるため数え間違いに強く、正解を確実に `cut` へ一致させられる(`puzzle_stage_ideas.md` §7) |
| 7 | 検証の強度(実装時) | ナビゲーター知識と Core向けJSON の一致は、`answer` が `cut` の色に**色記号または日本語色名で言及しているか**で検証する。全ステージ定義×多数の抽選結果に対する自動テストで担保する(§5) |
| 8 | 永続化のフォールバック(実装時) | Valkey に接続できない場合は**メモリ実装へフォールバック**して起動を続ける。再起動復帰はできなくなるが、開発時・障害時もゲーム自体は動く(§6) |
| 9 | ステージIDの体系(実装時) | 設計フェーズの案出しの経緯で数字(01-09)と英字(B-J)の2系統が混在し、欠番(06保留・Aなし)もあった。**3桁の難易度別採番**(1xx/2xx/3xx)へ統一し、ファイル名順=難易度順にした。203の対照表が使う色記号(A-E)とステージIDのB・Dが紙面上で紛らわしかった問題も解消する(§3.2) |
| 10 | 5色表示ステージの切断線(実装時) | 205 速さくらべは5色すべてを表示に使うため、`pick = "color"` では切断線の重複制約が効かず、他ステージと cut が衝突する不具合をテストが検出。`choice` に `as_line` を追加し、**表示は5色のまま正解だけを未使用の線に限る**形にした。ステージが進むほど選択肢が狭まるのは許容。→ 208 自体は**決定16でこの方式をやめた**(候補が2色しかなく組み立てが失敗しうるため)。`as_line` の実装と仕様は残っている(§3.1) |
| 11 | morse の word の型(実装時) | 抽選変数の展開では数字だけの文字列が数値へ変換される(rotary などの数値フィールドのため)。しかし Core 側は morse の `word` に文字列を要求するため、数字を表示するステージ(302)で**実機だけが session_rejected を返す**不具合になった。展開後に word を文字列へ戻す処理を入れ、テストで固定した(§5) |
| 12 | 妨害LEDの表現(実装時) | 302 暗号電文・ジャミングのため `noise_leds` を追加。妨害の点滅は**対称(点灯時間=消灯時間)に固定**する。モールスは短点・長点の非対称なリズムなので、対称にしておけば見分けられ、**難度は「見分けにくさ」ではなく「情報量」で上げる**方針にした(§3.1) |
| 13 | ヒント判定材料の永続化(実装時) | ステージ開始時刻・質問回数・誤操作数は**永続化しない**。復元時はL1から再開し、復帰直後に直言が出るのを避ける(§6) |
| 14 | 全ステージに報告できる表示を置く | 体験の軸は「プレイヤーがLEDの状態を報告 → ナビゲーターが解除方法を教える」往復にある。**203 ブループリントだけがLEDを一切出さず**、装置を見ずにシートへ従うだけのステージになっていた。**5色全点灯**(他ステージが使っていない唯一の表示)を割り当て、「全部光っています」の報告を合図に端子番号を出す形へ変更。全灯は色のヒントを含まないため難度は変わらない(`puzzle_stage_ideas.md` §2.2) |
| 18 | **L4 (直言) はイージーだけ** | 難易度で規範を分ける。イージーは行き詰まったら答えを教えて成功体験を優先するが、**ノーマル以上はより実践的な交信を狙う**ため直言の段階を置かない。ノーマルを `l4_pct = 0` に変更(ハードは元から0)。**難易度単位**にしたのは、ノーマルに含まれる easy タグのステージだけ直言するとセッション中で振る舞いが揺れるため(ADR N-39) |
| 19 | **208 を「N番目に速い色」へ戻した** | 決定18 で L4 が消え、決定15 の制約(中間順位だと色名で救済できない)が不要になった。「一番速い色を切れ」しか言えない状態は指示が毎回同じで単調だったため、**順位を毎回抽選**する形へ。実装は `derive = "rank_slot"` で、cut は `pick = "line"` で先に引くため決定16 の失敗は起きない(ADR N-40) |
| 15 | 208 の正解を最速に固定 **(決定19 で見直し)** | 5色を速い順に並べて「X番目」を切らせる形は、中間順位を引くと `answer` が「○番目に速い色」となり**ナビゲーターが色名を言えず、行き詰まりを無線で救えない**(同じ問題で見送った案がある)。**正解を最速に固定**し、さらに**1色を点灯しっぱなし(基準外)**にして「○色だけ点きっぱなしです」という報告を作った。毎回変わるのは「どの色が最速か」なので単調にならない(`puzzle_stage_ideas.md` §2.2) |
| 16 | `as_line` より `pick = "line"` を先に引く | 208 で表示色を先に決めて `choice`(候補=両端2色)＋`as_line` で cut を選ぶ形にしたところ、**2色とも使用済みのセッション後半で組み立てが失敗**した(テストが seed 単位で再現)。cut を `pick = "line"` で**先に**引き、残りの表示色をそこから除外して埋める形へ変更。`as_line` は候補が十分多い場合に限って使う(§3.1) |
| 17 | モールス系を4種→2種に削減 | 203 / 302 / 304 / 305 の4種があり、ハードでは**最大3枠がモールスで埋まる**ため、セッションの大半が対照表を睨む時間になっていた。**203(対照表で変換・報告は語単位)と 305(そのまま色名・報告は1文字ずつ)の2つ**を残し、203と正解の決め方が完全に同じ 304 と、5色すべての解読を要して報告が最も重い 302 を無効化した。実装は残しているため復活は TOML を戻すだけ(`puzzle_stage_ideas.md` §2.4) |
