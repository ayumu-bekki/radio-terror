# Core System ゲームセッション設計

危険物解体ハンズオン用デバイス(core-system)のセッション制御設計。

- 作成日: 2026-08-07 / 更新日: 2026-08-09
- ステータス: **実装済み**。設計確定後、実装で判明した事項を反映済み
  (実装由来の決定は §10 決定記録 #18-20)
- 関連: `bridge_connection_design.md`(radio-bridge接続) /
  `operation_flow.md`(体験運用フロー) /
  `puzzle_stage_ideas.md`(謎解きステージ集) /
  `navigator_design.md`(ナビゲーター設計)

## 1. コンセプト

トランシーバーを使って危険物(風船入りの模擬爆弾)を解体するハンズオン。
プレイヤーはLED表示のヒントを元に謎を解き、プッシュスイッチ・ロータリースイッチを
操作しながら配線を切断して解除を試みる。失敗すると風船が破裂する。

### 1.1 用語

| 用語 | 意味 |
|---|---|
| プレイヤー | このゲームを遊ぶ人 |
| ナビゲーター | プレイヤーがトランシーバーで話す相手(生成AI) |
| マネージャー | 運営者 |
| Core | 危険物体験装置(本リポジトリの core-system。本文中の「デバイス」はCoreを指す) |

## 2. システム構成と全体方針

```
[core-system (複数台)] ──WebSocket /ws──▶ [game-server (1つ)]
                                              ▲
[radio-bridge (複数プロセス)] ──/ws──────────┘
                                              │
                                        ナビゲーター (生成AI・無線メッセージ演出)
```

- **サーバーがシナリオ(セッションJSON)を決め、デバイスは自律実行する**。
  デバイスはJSON受信後、WiFiが切断されても単体でゲームを完遂できる。
  正解情報(切る順序・事前条件)はセッションJSONに含めてデバイスに渡す。
- デバイスは進行イベント(ステージクリア・誤操作・爆発・解除)をサーバーに都度通知する。
  サーバー側はこれをトリガーにナビゲーター(生成AI)の無線メッセージ演出を行う。
- サーバーは割り込みコマンド(強制破裂・中断・時間増減)をいつでも送れる。
- 謎解きのヒント内容(kLEDの光り方と正解の対応)は完全にサーバー側コンテンツの責務。
  デバイスはJSONで指定されたパターンを表示するだけ。謎の差し替えにファーム書き換え不要。
- **複数デバイス対応**: core-systemデバイスは複数台接続を想定する。
  デバイス → サーバーの全メッセージに `device_id` を含める。`device_id` は
  **トランシーバー経由の音声申告に使う**ため、**数字4桁**のIDを sdkconfig で設定する。サーバーは device_id と接続の
  対応を管理し、サーバー → デバイスは対象デバイスの接続に対して送信する。
  チーム(無線)とデバイスの対応は、セッティング時の音声申告による動的バインドで
  確立する(詳細は `bridge_connection_design.md`)。

## 3. 利用ハードウェア

配線・アドレスの定義は `app/core-system/main/hardware_config.h` 参照。

| 名称 | 種別 | 用途 |
|---|---|---|
| kPush A-E | プッシュスイッチ x5 (MCP23017) | 事前条件(押した状態を保持) |
| kRotary | ロータリースイッチ 6接点 (MCP23017) | 事前条件(位置合わせ)。**位置はパネル表記・JSONとも 0-5**(対応は下表) |
| kLine A-E | 切断可能な配線 x5 (ESP32直結GPIO) | 切断でシーケンス進行 |
| kLed A-E | 単色LED x5 (MCP23017) | 謎解きヒント表示(点灯・消灯・点滅) |
| kFullColorLed | PL9823 (RMT) | 状態表示(§4.1 の色仕様) |
| kBuzzer | アクティブブザー | 警告音(GPIO ON/OFFのみ、音程制御なし) |
| kSolenoid | ソレノイド | 風船破裂(200ms HIGHパルス一発) |
| HT16K33 | 7セグ4桁 | カウントダウン表示(最大 999.9 秒) |
| kBatteryAdc | ADC | バッテリー電圧監視。220kΩ×2の分圧(1/2)をADC入力(実電圧=測定値×2)。device_statusで報告+低電圧保護(§8.5) |

**色体系**: kPush / kLed / kLine の3系統に共通の5色を割り当てる。
A=赤, B=黄, C=緑, D=青, E=白(基板・パネル実装時に最終確認)。
「同じ色の線を切れ」等の色対応の謎解きが成立する。

**ロータリーの位置対応**(確定済み。基板の結線)

| 位置 (パネル表記・JSON) | 基板の接点 | MCP23017 |
|---|---|---|
| 0 | kRotary1 | GPA7 |
| 1 | kRotary2 | GPA6 |
| 2 | kRotary3 | GPA5 |
| 3 | kRotary4 | GPA4 |
| 4 | kRotary5 | GPA3 |
| 5 | kRotary6 | GPA2 |

`core_system.cc` の `kRotaryGpios` は**配列の添字がそのまま位置番号**になる並びで
定義する。ここがずれると全ステージのロータリー条件が1つずれ、
「動くが正解しない」形で現れるため、基板を変更したら必ず突き合わせる。

## 4. デバイス側状態機械

### 4.0 起動シーケンスと起動演出

電源投入から Setup に入るまでの流れ。**WiFi接続を待たずに演出を流す**ため、
電源を入れてすぐ「動いている」ことが目視で分かる。

```
電源投入
  ├─ フルカラーLED: 紫点灯 (初期化中)     ← 最優先で点ける
  ├─ I2C初期化 ─────失敗─▶ 紫点滅 (初期化失敗) で停止
  ├─ MCP23017 / HT16K33 初期化
  ├─ 起動演出 (約2.8秒)                    ← WiFi接続より先
  ├─ WiFi接続 (15秒でタイムアウト)
  │    └─失敗─▶ 紫点滅。ただし起動は続行する
  └─ Setup(準備中) へ
```

**起動演出**(約2.8秒)は3段階。

| 段階 | 内容 | 時間 |
|---|---|---|
| スイープ | kLED A→E を順に点灯(消さずに足していく)。7セグの桁も1つずつ埋める | 5×160ms |
| 全点灯 | kLED 5個 + 7セグ全桁が点いた状態を見せる | 1200ms |
| 点滅 | 全体を3回点滅させて締める | 3×280ms |

演出後は必ず全消灯してから Setup に入る。GameTask は全消灯を前提に
描画を始めるため。

**フルカラーLEDの起動インジケータ**

| 状態 | 表示 |
|---|---|
| 初期化中 | 紫 **点灯** |
| 初期化失敗(I2C / WiFi) | 紫 **点滅** |

同じ色の点灯では成功/失敗が区別できないため、失敗は点滅で示す。

**WiFi接続失敗でも起動は止めない。** Core はセッション受信後、WiFiが切れても
単体でゲームを完遂できる設計(§1)なので、会場のWiFiが未設営でも
Setup までは進める。以前は `portMAX_DELAY` の無限待ちだったため、
WiFiが無いと永久に起動しなかった。

```
起動 ──▶ Setup(準備中) ──全線結線を確認──▶ Ready(セッティング完了)
             ▲    ▲                            │ session_start 受理
             │    └──結線が外れたら戻る──────┘
             │                                 ▼
             │                        Playing(stage 0..N) ──全ステージクリア──▶ Defused
             │                             │
             │                             ├─ タイムアウト(ペナルティ・time_adjustによる0到達含む)
             │                             ├─ explode指定の誤切断
             │                             ├─ force_detonate
             │                             ▼
             │                        Detonating ──(detonate_delay_ms)──▶ ソレノイド200ms ──▶ Exploded
             │
             └────────── session_abort でどの状態からも Setup へ戻る
```

- **Setup(準備中)**: マネージャーによる風船交換・配線復旧のための状態。起動直後および
  `session_abort` 受信後はこの状態になる。全kLineの結線を監視し、全線が結線された
  状態が一定時間(1秒程度)安定し、サーバーと接続できたらReady へ自動遷移する。切断中の線に対応する
  kLEDを点灯して復旧ガイドとする。
- **Ready(セッティング完了)**: `session_start` を受理できる唯一の状態。
  ここで線が外れた・WebSocketのセッションが切れたら Setup へ戻る。
- **セッション開始のトリガー**: デバイスが Ready の状態で、マネージャーが
  トランシーバー経由で CoreID(数字4桁)と難易度を申告し、サーバーが難易度に
  対応するシナリオからセッションJSONを組み立てて `session_start` を送信する
  ことでゲームが開始される(運用の詳細は `operation_flow.md`)。
  デバイス側から開始操作は行わない。
- **Playing**: セッションのステージを順に消化する(ルールは §5)。
- **Detonating**: 失敗確定。kFullColorLed 赤点灯+ブザーON にし、`exploded` を
  サーバーへ送信(無線演出と破裂音を同期させるためソレノイド駆動前に送る)。
  `detonate_delay_ms` 経過後にソレノイドを200ms駆動して Exploded へ。
- **Exploded**: 赤点灯を維持、ブザーOFF。マネージャーが復旧を始める際は
  サーバーから `session_abort` を送って Setup へ戻す。
- **Defused**: 全ステージクリア。緑点灯+ブザー短音3回。残り時間を停止表示する。

### 4.1 状態別の表示・音仕様

| 状態 | kFullColorLed | ブザー | HT16K33 | kLED A-E |
|---|---|---|---|---|
| Setup | 黄点滅 | OFF | 消灯 | 切断中の線に対応するLEDを点灯(復旧ガイド) |
| Ready | 青点灯 | OFF | 消灯 | 全消灯 |
| Playing | 赤の短発点滅(残り時間僅少で点滅加速) | OFF(ペナルティ発生時のみ短音1回) | 残り時間(秒+0.1秒) | ステージ定義のパターン |
| Detonating | 赤点灯 | ON(連続) | 0.0(固定) | 全消灯 |
| Exploded | 赤点灯(維持) | OFF | 0.0(固定) | 全消灯 |
| Defused | 緑点灯 | 短音3回→OFF | 残り時間で停止表示(スコア確認用) | 全消灯 |

- カウントダウン中の刻み音(チック音)は鳴らさない
  (トランシーバーの音声指示の聴取を妨げないため)。
- 終盤警告は点滅加速のみで段階的に行う(閾値・速度は実装時に調整)。
- Detonating / Exploded のHT16K33は、爆発理由(タイムアウト・誤切断・強制)に
  かかわらず 0.0 固定表示とする(時間切れの演出に統一)。

## 5. ゲームルール

- セッションは `stages` を先頭から順に消化し、全ステージクリアで解除成功(Defused)。
- **ステージクリア条件**: `precondition`(省略可)を満たした状態で、`cut` に
  指定された線を切断する。事前条件は次の種類を組み合わせられる(全てAND条件):
  - `rotary`: 切断の瞬間にロータリーが指定位置(0-5)であること
  - `push`: 切断の瞬間に指定スイッチが押されていること
  - `whack`: モグラ叩き(§5.1)を完了済みであること
  - `push_seq`: 指定順のボタン列入力を完了済みであること。entryごとに
    ロータリー位置条件を付けられる。ミス時は `on_wrong_press`
    (retry / penalty / explode、既定retry。retryは列の先頭からやり直し)。
    正しい入力のたびに `push_progress` をサーバーへ通知する(§7.2)
  - `timer_digit`: 切断の瞬間の「残り秒数の指定桁」が条件を満たすこと。
    比較相手は固定値(判定窓は対象桁が一致する期間+直後1秒の猶予)、
    またはロータリー位置(桁とロータリーの一致)。
    `offset` を指定すると**桁に加算してから**比較する
    (「ランプの数 + タイマーの桁 = ダイヤル位置」のような暗算を要する謎用)
  - `leds_all_off`: 切断の瞬間に全kLEDが消灯していること(点滅の重なりを見切る謎用)
  - 制約: `whack` と `push_seq` は**併用不可**(どちらもkLED表示を専有・使用するため。
    §6.2 の検証で拒否する)
- **ステージ属性 `forbidden_rotary`**: ステージ有効中に回してはいけない
  ロータリー位置。違反時は `on_violation`(explode / penalty)。
  ロータリーはストッパー付き直線配置(0-5)のため経路上の**通過は違反にせず**、
  一定時間(300ms程度、要調整)止まったら違反確定とする。
- **誤切断**: 現在ステージの `cut` 以外の線を切った場合、そのステージの
  `on_wrong_cut` に従う。
  - `explode`: 即座に Detonating へ。
  - `penalty`: 残り時間を `penalty_ms` 減らす(ブザー短音1回)。
- **事前条件未達のまま正解の線を切った場合**: 誤切断と同じく `on_wrong_cut` に従う。
  ただし `penalty` の場合はペナルティ適用の上で**当該ステージはクリア扱いとして次へ進む**
  (配線は物理的に戻せず、そのままではステージがクリア不能になるため)。
  サーバーへの通知では誤配線(`wrong_line`)と事前条件未達(`precondition_unmet`)を
  `detail` で区別する(§7.2)。
- **タイムアウト**: 残り時間が0になったら Detonating へ。ペナルティや `time_adjust` の
  減算により0以下になった場合も同様(`exploded` の `reason` は `timeout`)。

### 5.1 モグラ叩き (whack)

kLED A-E と kPush A-E の対応を使った反射ゲーム。`precondition.whack` を持つ
ステージで発動し、完了が切断の事前条件の一つになる。

- **表示の二相切り替え**: whack が未完了の間、kLEDはモグラ叩き表示に専有される。
  完了した瞬間にステージの `leds` ヒントパターン表示へ切り替わる
  (切り替わり自体が完了のフィードバックになる)。
- **進行**: kLEDが1個ずつランダムに点灯(モグラ出現)。点灯中に対応するkPushを
  押せたらヒットとなり即消灯、`gap_ms` 後に次のモグラが出現する。
  規定匹数(`count`)ヒットで完了。
- **出題順序はデバイス側でランダム抽選**(直前と同じLEDは避ける)。
  JSONは匹数・速度のみ指定する。
- **ミス**: 点灯時間(`mole_on_ms`)内に押せなかった、または点灯中に別のkPushを
  押した場合はミス。**ペナルティはなく、進捗カウントを進めずに同じモグラが
  出直すだけ**(カウントダウンが進むこと自体が時間的ペナルティになる)。
- 完了時は `whack_completed` をサーバーへ通知する(§7.2)。
- オプション `last_mole_matches_cut`: 最後の1匹を `cut` と同色に固定する
  (「最後に押した色の線を切れ」の謎用。それ以外の出題はランダムのまま)。
- ヒット・ミス時の細かなフィードバック演出(短い明滅等)は実装時に調整する
  (ブザーは鳴らさない方針を維持)。

### 5.2 入力読み取りの詳細

- **kLine**: プルアップ有効で「GND接続の線が切れる → HIGH」で切断検知。
  50ms程度のデバウンスを入れる。
- **ロータリー**: 6接点のうち「ちょうど1つがLOW」の状態が約50ms安定したときに
  値を確定する。接点間の全OFF・過渡状態では最後に確定した値を保持し、
  事前条件の判定には切断イベント時点の確定値を使う。
- **プッシュ**: `precondition.push` は「切断の瞬間に押されていること」で判定する。

## 6. セッションJSON

```json
{
  "type": "session_start",
  "session_id": "s-001",
  "countdown_ms": 300000,
  "detonate_delay_ms": 2000,
  "stages": [
    {
      "leds": {
        "A": "on",
        "B": "blink",
        "C": { "pattern": "morse", "word": "HELP", "unit_ms": 300 },
        "D": { "pattern": "blink", "on_ms": 200, "off_ms": 800 },
        "E": "off"
      },
      "led_blink_ms": 500,
      "precondition": {
        "rotary": 3,
        "push": ["A", "D"],
        "whack": { "count": 8, "mole_on_ms": 1500, "gap_ms": 400 }
      },
      "cut": "C",
      "on_wrong_cut": { "action": "penalty", "penalty_ms": 30000 }
    }
  ]
}
```

| フィールド | 内容 |
|---|---|
| `countdown_ms` | カウントダウン時間。表示桁の制約から最大 999,900ms (999.9秒) |
| `detonate_delay_ms` | 失敗確定(赤点灯+ブザー)からソレノイド駆動までの時間 |
| `stages[].leds` | kLED A-E の表示パターン。文字列の簡易記法またはオブジェクト指定(§6.1) |
| `stages[].led_blink_ms` | 文字列 `"blink"` 指定時の点滅周期(省略時デフォルト500ms) |
| `stages[].precondition` | 省略可。以下を組み合わせ可(§5)。`rotary`: 位置0-5 / `push`: 保持するスイッチ(複数指定可。5個あるので複数人で押さえる協力プレイが成立する) / `whack`: モグラ叩き(§5.1)。`count`: ヒット数, `mole_on_ms`: 点灯時間(省略時1500), `gap_ms`: 出現間隔(省略時400), `last_mole_matches_cut`: 最終モグラを `cut` と同色に固定 / `push_seq`: `entries`: [{`push`, `rotary`(省略可)}...], `on_wrong_press`(省略時retry) / `timer_digit`: `digit`(ones/tens), `value`(固定値)または `match: "rotary"`, `offset`(桁への加算値。-9〜9) / `leds_all_off`: true |
| `stages[].forbidden_rotary` | 省略可。`positions`: 禁止位置リスト, `on_violation`: explode / penalty(+`penalty_ms`)。通過はセーフ、一定時間停止で違反確定(§5) |
| `stages[].cut` | このステージで切断すべき線 (A-E) |
| `stages[].on_wrong_cut` | `{"action": "explode"}` または `{"action": "penalty", "penalty_ms": N}` |

### 6.1 kLED表示パターン指定

`leds` の各LEDの値は文字列(簡易記法)またはオブジェクトで指定する。

**文字列(簡易記法)**

| 値 | 動作 |
|---|---|
| `"on"` / `"off"` | 点灯 / 消灯 |
| `"blink"` | `led_blink_ms` の周期で点滅(デューティ50%) |

**オブジェクト指定**

| pattern | フィールド | 動作 |
|---|---|---|
| `"blink"` | `on_ms`, `off_ms` | 点灯時間・消灯時間を個別指定した点滅(非対称パターン可) |
| `"morse"` | `word`, `unit_ms`(省略時300) | `word` をモールス信号(英字)として繰り返し表示 |

**モールス信号の仕様**(ITU標準タイミングに従う):

- 短点 = 1単位 点灯、長点 = 3単位 点灯
- 符号内の要素間 = 1単位 消灯、文字間 = 3単位 消灯
- `word` の表示終了後、7単位の消灯を挟んで先頭から繰り返す
- `word` は A-Z / 0-9 のみ(パース時に検証)。`unit_ms` はtick粒度(100ms)の
  倍数を推奨し、最小100ms
- モールスLEDと通常のblink LEDが同一ステージに同居することは**意図的に許容する**
  (どのLEDがモールスかを見分けること自体を謎解きの一部にできる)。
  デバイス側は個数・組み合わせに制約を設けない

**実装方針**: セッションJSONのパース時にパターンを「点灯/消灯+継続時間」の
シーケンスにプリコンパイルし、GameTaskの100ms tickでLEDごとに独立して進める。
MCP23017への書き込みはtickごとに変化があった場合のみグループ単位で行う。

### 6.2 デバイス側の検証

§7.2 `session_rejected` の条件:

- JSONとして妥当で、必須フィールドが揃っていること
- `cut` の線が重複していないこと・`countdown_ms` が表示上限以内であること
- `morse` の `word` が対応文字(A-Z / 0-9)のみで構成されていること
- `whack` の `count` が1以上、`push_seq` の `entries` が1以上であること
- `whack` と `push_seq` が同一ステージで併用されていないこと
- `rotary` / `forbidden_rotary` の位置が0-5の範囲であること
- デバイスが Ready 状態であること

## 7. WebSocketメッセージプロトコル

`game-server` の `/ws` エンドポイントで受ける。JSONテキストフレームを
`type` でディスパッチする構造。**接続してくるのは core-system デバイスのみ**で、
最初の `device_status` が名乗る `device_id` がその接続の宛先になる。

(設計当初は同じ `/ws` にトランシーバー用のコールサイン払い出し機能も
相乗りする想定だったが、無線は gRPC の radio-bridge 経由に一本化されたため
実装では削除した。§10 決定記録 #23)

### 7.1 サーバー → デバイス

サーバーは device_id で解決した対象デバイスの接続にのみ送信するが、
**サーバー → デバイスの全メッセージにも `device_id` を含める**。
デバイス側は自分宛でないメッセージを無視するため、宛先解決を誤った場合でも
他のデバイスが誤作動しない(取り違えによる誤爆発を防ぐ二重の安全策)。

| type | 内容 |
|---|---|
| `session_start` | セッション定義一式(§6)。Ready状態のデバイスのみ受理し、Playingへ遷移。それ以外の状態では `session_rejected`(`not_ready`)で応答 |
| `session_abort` | 安全に中断してSetupへ(爆発させない)。Exploded/Defusedからのリセットにも使う |
| `force_detonate` | 即座に爆発シーケンス(Detonating)へ。Playing中のみ有効 |
| `time_adjust` | `delta_ms` で残り時間を増減(ナビゲーター演出用)。Playing中のみ有効。減算で0以下になった場合はタイムアウト扱い |

### 7.2 デバイス → サーバー

全メッセージに `device_id` を含める。

| type | 内容 |
|---|---|
| `device_status` | 接続時+定期(5秒毎)。`state`, `session_id`, `stage_index`, `remaining_ms`, `battery`(実電圧), `low_battery`, `lines`(各配線の結線状態)を含む。WS再接続時のサーバー側再同期と、Setup中の復旧進捗のマネージャー確認はこれで行う。`low_battery` はフェイルセーフ(§8.5)の通知を兼ね、マネージャー向けWeb画面で検知する |
| `session_accepted` | セッションJSON検証OK・ゲーム開始 |
| `session_rejected` | 検証NG。`reason` 付き(`not_ready`: Ready状態でない(切断済みライン一覧付き) / `parse_error`: JSON不正 など) |
| `stage_cleared` | `stage_index`, `remaining_ms` |
| `whack_completed` | モグラ叩き完了の通知。`stage_index`, `remaining_ms`。ナビゲーター演出のトリガーに利用可 |
| `push_progress` | `push_seq` の正しい入力ごとの進捗通知。`stage_index`, `seq_index`, `remaining_ms`。ナビゲーターが実操作に反応する演出に使う(08対話誘導など) |
| `wrong_action` | 誤操作の通知。`detail`, `line`, `penalty_ms`, `remaining_ms`。ナビゲーターの煽り演出に利用可。`detail` は誤操作の種類を示す: `wrong_line`(誤配線の切断) / `precondition_unmet`(事前条件未達での正解線切断) / `forbidden_rotary`(禁止位置での停止) / `push_seq`(ボタン列の入力ミス)。`line` は配線に起因する場合のみ含める |
| `exploded` | `reason`(`timeout` / `wrong_cut` / `forced`)。`wrong_cut` の場合は `detail`(`wrong_action` と同じ値域)と `line` も含める。禁止ロータリー・ボタン列ミスの `explode` も `reason` は `wrong_cut` とし、`detail` で区別する。ソレノイド駆動前(失敗確定時点)に送信 |
| `defused` | `remaining_ms`(残タイムはスコア) |

### 7.3 切断・再接続の方針

- ゲーム進行はデバイス内で完結するため、WS切断中もゲームは継続する。
- 切断中に発生した個別イベント(`stage_cleared` 等)の再送は行わない。
  再接続時に `device_status` で最新状態(state・stage_index・remaining_ms)を送り、
  サーバー側はこれで再同期する(演出イベントの取りこぼしは許容する)。

## 8. ファームウェア実装方針

新設の **GameTask**(既存の `Task` 基底 + `MessageQueue` パターンを流用)に
全イベントを集約するシングルコンシューマー構成。

### 8.1 入力(→ GameEvent としてキューへ)

- **Push / Rotary**: 既存のMCP23017監視(INTA割り込み→再読込)から変化イベントを発行。
- **kLine A-E**: ESP32直結GPIOを `GpioInputWatchTask` に追加登録(検知仕様は §5.2)。
- **WS受信**: `WSClient` に受信コールバックを追加し、受信文字列をそのままキューへ。
  cJSONパースはGameTask内で行い、WSイベントハンドラを軽く保つ。

### 8.2 時間管理

GameTaskのキュー待ちを100msタイムアウト付きにして、以下を全てこのtickで処理する:

- カウントダウン減算
- HT16K33表示更新(既存実装の右詰め+0.1秒表示を踏襲)
- kLEDパターン進行(blink・morseのプリコンパイル済みシーケンスをLEDごとに独立再生)
- ブザーパターン

既存の `CountdownTaskEntry`(テスト実装)は廃止してGameTaskに吸収する。

**tickは実経過時間で刻む**: キュー待ちのタイムアウトだけを頼りにすると、
入力イベント(ボタン連打・モグラ叩き中の操作)が連続した場合にキュー待ちが
タイムアウトせず、**カウントダウンが進まなくなる**。イベント処理後に
`xTaskGetTickCount()` の差分を見て、100ms分ずつ溜まった回数だけtickを進める。
イベントの多寡にかかわらず残り時間が実時間どおりに減ることを保証する。

### 8.3 出力

- kLED A-E: MCP23017出力。点滅はGameTaskのtickで処理(専用タスク不要)。
- PL9823: 既存 `Pl9823Task::SendCommand`。
- ブザー: アクティブブザーなので `gpio_set_level` のみ。
- ソレノイド: 200ms HIGHパルス一発(既存実装通り)。
- WS送信: GameTaskから `WSClient::Send`。

### 8.4 ファイル構成イメージ

| ファイル | 役割 |
|---|---|
| `game_task.h/.cc` | 状態機械本体 |
| `game_session.h/.cc` | セッションJSONのパース+検証(SessionConfig構造体) |
| `buzzer.h` | ブザー制御(小物) |

`core-system.cc` のテスト実装(カウントダウンタスク・サンプルWS送信ループ)は
GameTask・`device_status` 定期送信に置き換える。

### 8.5 フェイルセーフ

ハードウェア側(ドライバ回路のゲート安定化等)は対応済みのため、
ファーム側はGameTask実装時に組み込める最小限のルールのみとする:

- ソレノイド駆動は単一関数に集約し、**Detonating状態でのみ**呼べる。
  200msパルスはタイマーで強制OFF(二重駆動防止。テスト実装の方式を踏襲)。
- GameTaskをタスクWDTに登録。ハング時はリセット→Setup起動で安全側に倒す。
- **再起動後は常にSetupから**開始する(セッション状態の不揮発保存はしない。
  リセット→再セッティングを正とし、途中復帰は作らない)。
- Detonating中に `session_abort` を受けた場合、**ソレノイド駆動前なら中止**して
  Setupへ戻る(キルスイッチの安全停止を優先。パルス開始後は完了させる)。
- 破裂失敗(風船が割れない)の検知手段は設けず、マネージャーの物理対応とする。
- **バッテリー低電圧保護**: 30秒に1回、kBatteryAdcで電圧を測定する
  (220kΩ×2の分圧1/2のため実電圧=測定値×2)。**3.4Vを下回ったら
  Deep Sleepに入る**(過放電保護)。誤判定防止のため測定は複数サンプルの
  平均とし、2回連続で下回った場合に確定する(ソレノイド駆動などの
  瞬間的な電圧降下でスリープしないため)。Deep Sleep突入前に
  `device_status`(低電圧フラグ)を送信し、Web画面で検知できるようにする。
  復帰は電源の入れ直し(バッテリー交換後)。測定値は通常時も
  `device_status` に含め、低下傾向をマネージャーが事前に把握できるようにする。

## 9. サーバー側実装方針 (game-server)

- `/ws` の `wsSession` にデバイス用メッセージtypeのハンドリングを追加する(§7)。
- セッションJSONの組み立ては**難易度別(イージー / ノーマル / ハード)の
  シナリオテンプレートを複数用意し、
  その中からランダム選択+テンプレート内のランダム要素(切る線の割り当て・
  ロータリー位置・LEDパターン等を候補から抽選)で変化をつける**方式とする。
  難易度はマネージャーの音声申告で指定される(`operation_flow.md` 参照)。
  構成は**ハイブリッド方式**: 難易度タグ(簡単/普通/難しい)による抽選に加え、
  テンプレートで固定の並び(例: イージーは01→02固定)も指定できる。
  ステージ内容の一覧と構成ルールは `puzzle_stage_ideas.md`、
  テンプレート形式と組み立てフローは `scenario_design.md` 参照。
- デバイスからの進行イベントをナビゲーター演出(無線メッセージ)のトリガーに接続する。
  宛先の無線(radio-bridge)は音声申告による動的バインドで解決する
  (`bridge_connection_design.md` 参照)。
- **永続化**: セッション状態(組み立て済みセッションJSON=正解を含む)・会話ログ・
  スコア(`defused` 時の残り時間)は **Valkey** に保存する。サーバー再起動後も
  ナビゲーターが正解・文脈を保って復帰できるようにするため。
  ランキング等の集計・表示機能は作らない。
- サーバーの動作ログは標準出力のみ(別途の永続化はしない)。
- **生成AI(思考・TTS)の障害時**は自動フォールバックを設けず、
  **マネージャー介入**で運用する(障害はWeb画面で検知する)。
- **マネージャー向けWeb画面**を用意する。`/ws` と同じHTTPサーバーで提供し、
  外部依存のない構成にする(会場のネットワーク事情に左右されないため)。
  **進行中の監視と終了後の振り返りは目的が異なる**ため、ページを分ける
  (§10 決定26)。

  | URL | 役割 | 更新 |
  |---|---|---|
  | `/manager` | ダッシュボード。進行中セッションの監視 | 2秒ごとに差し替え |
  | `/manager/history` | 履歴一覧。日付・Core・結果で絞り込む | 更新しない |
  | `/manager/history/{session_id}` | セッション詳細 | 進行中のみ5秒 |

  CSS は `/manager/manager.css` として3ページで共有する。

  - **画面はサーバー側で描画する** (`html/template`)。表示の判断 — 色分け・
    時刻書式・進行表示・ステージの到達判定 — はすべてビューモデルへ寄せ、
    テンプレートは受け取った値を並べるだけにする(§10 決定32)。
    表示用のJSON APIは持たない。残る `/manager/api/` は画面描画ではなく
    **操作と書き出しの口**(`abort` の POST と `transcript` のダウンロード)。
    テンプレートは `manager_*.gohtml`(素のHTMLではないため `.html` にしない)。
  - **ダッシュボードの更新**は `?partial=live` で進行中の部分だけを取り直し、
    差し替える。ページ全体をリロードしないのは、**スクロール位置と交信ログの
    末尾追従を保つ**ため(2秒ごとに先頭へ戻るとログを追えない)。

  - **ダッシュボード**: セッション状況(Core状態・進行・バインド)、デバイス、
    無線、外部APIの状況、進行中セッションの交信ログ、**直近5件の履歴**。
    - **現在の正解を表示する**: マネージャーがプレイヤーの状況を把握し、
      介入判断できるようにするため、進行中ステージの `answer` を表示する。
    - **バッテリー電圧・低電圧フラグ**を表示し、実機の異常を検知する。
    - **強制リセット**を画面から実行できる(無線が使えない場合の代替手段。
      `operation_flow.md` §7 のキルスイッチと同じ `session_abort` を送る)。
    - 外部APIの状況は「最終成功時刻・最終エラー時刻・エラー件数・直近のエラー内容」
      を表示する(生成AI障害時のマネージャー介入の判断材料)。
    - **交信ログ**: 発話と進行イベントを時刻付きの1本のタイムラインで表示する。
      ダッシュボードでは進行中セッションの実況に絞る。
  - **履歴一覧**: 過去のセッションを新しい順に表示し、結果(解除成功/爆発)・
    スコア・難易度・担当ナビゲーターを一覧できる。絞り込みは
    **クエリパラメータ** (`?date=&device=&result=`) で行い、サーバー側で絞る。
    URLに条件が残るので**共有・ブックマークできる**。
    絞り込みの選択肢は絞る前の全件から作る(絞った結果で選択肢が消えると
    元に戻せなくなるため)。1日の開催で数十〜数百件の規模なので、
    サーバー側ページングは設けない。
  - **セッション詳細**: 1セッションの概要・**全ステージの正解**・交信ログ全文を
    1ページで読む。セッションが終了・リセットされてもメモリから消えるだけで、
    Valkey から読み直して閲覧できる。**テキストファイルとして保存**もできる。
    - **到達しなかったステージの正解も出す**。履歴は終了後の振り返りであり、
      「どこで詰まり、この先に何があったか」を読むための画面のため。
    - Core へ送ったステージ定義(JSON)も折りたたみで確認でき、
      実機の挙動と設計の突き合わせに使える。

## 10. 決定記録

| # | 論点 | 決定 |
|---|---|---|
| 1 | 判定主体 | シナリオはサーバーがJSONで決め、実行判定はデバイス側で完結。強制破裂・中断はサーバーからの割り込みコマンド。進行通知はナビゲーター演出のトリガー |
| 2 | 誤切断の挙動 | JSONでステージごとに「即爆発 / 時間ペナルティ」を指定可能 |
| 3 | クリア条件 | 事前条件+指定配線の切断。条件なしステージも可(事前条件の種類は後に #11・#13 で拡張) |
| 4 | ブザー種別 | アクティブブザー(GPIO ON/OFF制御のみ) |
| 5 | 事前条件未達での正解線切断 | `on_wrong_cut` に従い、`penalty` の場合はクリア扱いで次へ進む(§5) |
| 6 | 開始前の配線チェック | Setup/Ready状態を新設し、全線結線が確認できるまで `session_start` を受理しない(§4)。開始はReady状態でのトランシーバー音声指示→サーバー送信 |
| 7 | ロータリー読み取り | 「ちょうど1つがLOWで約50ms安定」で確定、過渡状態は最終確定値を保持(§5.2) |
| 8 | 演出 | §4.1 の状態別表示・音仕様として確定(刻み音なし・終盤は点滅加速のみ) |
| 9 | サーバー受け口 | 既存 `/ws` 1ストリームに相乗り。最初のメッセージで接続種別を判定。複数デバイスを device_id で識別。シナリオはテンプレート+ランダム化(§9) |
| 10 | kLEDパターン拡張 | 文字列簡易記法に加えオブジェクト指定を導入。blinkの点灯・消灯時間の個別指定と、モールス信号(英字ワードの繰り返し表示)に対応(§6.1) |
| 11 | モグラ叩き | 切断の事前条件(`precondition.whack`)として組み込む。ミスはペナルティなしのやり直しのみ。出題順はデバイス側ランダム(JSONは匹数・速度のみ)。whack完了までkLEDはモグラ表示に専有され、完了後に `leds` ヒント表示へ切り替わる(§5.1) |
| 12 | 色体系・ロータリー表記 | kPush/kLed/kLineに共通5色(A=赤, B=黄, C=緑, D=青, E=白)を割り当てる。ロータリー位置はパネル表記・JSONとも0-5(§3)。謎解きステージ案は `puzzle_stage_ideas.md` 参照 |
| 13 | 謎解きステージ拡張 | ステージ案の確定(`puzzle_stage_ideas.md`)に伴い事前条件を拡張: `push_seq`(ボタン列入力+`push_progress` 進捗通知)、`timer_digit`(切断時のタイマー桁条件)、`leds_all_off`(全消灯判定)、ステージ属性 `forbidden_rotary`(禁止位置)、whackの `last_mole_matches_cut`。構成はタグ抽選+固定並びのハイブリッド |
| 14 | 事前条件の併用制約 | `whack` と `push_seq` は併用不可(kLED表示の専有が衝突するため)。セッションJSON検証で拒否(§6.2) |
| 15 | サーバー運用方針 | セッション状態・会話ログ・スコアは Valkey に永続化(ランキング機能なし)。動作ログは標準出力。生成AI障害時は自動フォールバックなしでマネージャー介入。マネージャー向けWeb画面(セッション状況・ログ・API状況)を用意(§9。ページ構成は後に #31 で分割) |
| 16 | フェイルセーフ | ハード側対応済みを前提に、ファームは最小限(駆動関数の状態ガード・WDT・再起動は常にSetup・Detonating中abortは駆動前のみ中止)。破裂失敗は運用でカバー(§8.5) |
| 26 | 起動演出 | 電源投入から約2.8秒、kLED・7セグを使った演出を流す(§4.0)。**WiFi接続より先**に実行し、電源投入直後から動作が目視で分かるようにする |
| 27 | 起動インジケータ | フルカラーLEDで紫点灯=初期化中 / 紫点滅=初期化失敗(§4.0)。同じ色の点灯では成功/失敗を区別できないため、失敗は点滅にした |
| 28 | WiFi接続にタイムアウト | 15秒で諦めて起動を続行する(§4.0)。従来は `portMAX_DELAY` の無限待ちで、会場のWiFiが無いと永久に起動しなかった |
| 29 | timer_digit の猶予(実装時) | 猶予タイマーは定義・減算・リセットはあるが**セットする箇所が無く常に0**だった(§5の「直後1秒の猶予」が効いていない)。一致中は満タンに保ち、外れた瞬間から減衰する形で実装した |
| 30 | ロータリー初期位置(実装時) | `System` 側の保持値を 0 初期化していたため、**起動時に実際に位置0にあると初回通知が飛ばない**。-1(未確定)で初期化して必ず1回は通知するようにした |
| 17 | バッテリー低電圧保護 | 30秒ごとに電圧測定(220kΩ×2分圧、実電圧=測定値×2)し、3.4V未満が2回連続したらDeep Sleep。突入前に低電圧フラグ付き `device_status` を送信。復帰は電源入れ直し(§8.5) |
| 18 | tickの進め方(実装時) | キュー待ちのタイムアウトのみに頼ると入力イベント連続時にtickが飢え、**カウントダウンが停止する**不具合が実装中に判明。実経過時間の差分でtickを進める方式に変更(§8.2) |
| 19 | サーバー→デバイスのdevice_id(実装時) | サーバーは対象接続にのみ送るが、**送信メッセージにも `device_id` を含め、デバイス側で自分宛以外を無視**する。宛先解決の誤りが誤爆発に直結するため二重の安全策とした(§7.1) |
| 20 | 誤操作通知の粒度(実装時) | `wrong_action` / `exploded` の `detail` を拡張し、`forbidden_rotary`(禁止位置での停止)と `push_seq`(ボタン列ミス)も区別できるようにした。ナビゲーターが誤操作の種類に応じた演出を出せる(§7.2) |
| 21 | 進行記録の保存形式(実装時) | 会話ログと進行イベントを**1本のタイムライン**に統合して Valkey へ保存する。別リストに分けるより「何を言った直後に何が起きたか」が追いやすく、振り返り時の価値が高いため。マネージャー画面から履歴として閲覧・テキスト保存できる(§9) |
| 23 | /ws の用途(実装時) | 設計当初は `/ws` にトランシーバー用のコールサイン払い出し機能も相乗りさせる想定だったが、**無線は gRPC の radio-bridge 経由に一本化**されたため到達不能になっていた。`/ws` は core-system デバイス専用とし、旧機能(約400行)を削除した。設営時の無線疎通確認は別途「カラス」が担う(§7) |
| 24 | I2Cエラー検知の削除(実装時) | 設計では「I2Cエラーが回復しない場合は紫点滅+サーバー通知」としていたが、**ドライバ側がエラーを検知しても通知経路へ繋がっておらず紫点滅は発生しない**状態だった(受け口だけの実装)。動かない機能を残すとマニュアルの記述と食い違うため、機能ごと削除した。I2Cエラーはログ(`ESP_LOGE`)にのみ出る(§8.5) |
| 22 | 強制リセット時の記録(実装時) | デバイスが未接続でも**サーバー側の状態整理とログ記録は必ず行う**。デバイス切断中こそリセットしたい場面であり、送信失敗で早期リターンすると「なぜ終わったか」が記録に残らない不具合が実装中に判明(§9) |
| 31 | マネージャー画面のページ分割(実装時) | 1ページに全部を縦積みしていたが、**進行中の監視と終了後の振り返りは目的が異なる**ため3ページに分けた(§9)。当日の運営は進行中セッションの状態と正解を秒単位で見るのに対し、振り返りは1セッションを腰を据えて読む。同居させると、監視中に履歴が視界を圧迫し、振り返り時はログが高さ制限の枠に押し込まれて読みにくかった。詳細は**全ステージの正解**を出す(到達しなかった先に何があったかまで読めるようにするため)。ダッシュボードには直近5件だけ残し、当日の「さっきの回はどうだったか」には即答できるようにした |
| 32 | 画面をサーバー側描画へ(実装時) | 当初はJSON APIを返して**ブラウザ側のJSでHTMLを組み立てて**いたが、`html/template` によるサーバー側描画へ作り直した(§9)。理由は3つ。(a) **エスケープが自前**だった — ステージ名・ナビゲーターの発話は外部TOMLと生成AI由来で、`esc()` を通し忘れた箇所が実際にあった。`html/template` は文脈に応じて自動エスケープする。(b) **同じ整形を複数ページのJSへ書き写す**ことになり、色分けや時刻書式が食い違う温床だった。表示の判断はビューモデル (`manager_view.go`) に一本化し、Goのテストで検証できるようにした。(c) 表示用のJSON APIが**画面専用の中間層**として二重管理になっていた。削除し、`/manager/api/` は操作(`abort`)と書き出し(`transcript`)だけにした。ダッシュボードの2秒更新は `?partial=live` の部分描画を差し替える形にし、スクロール位置とログの末尾追従を保っている |

## 11. 実装ステップ(完了)

1. ✅ `game_session`: セッションJSONスキーマ定義とパース・検証
2. ✅ `game_task`: 状態機械+100ms tick(カウントダウン・表示・点滅をGameTaskへ集約。§5の事前条件拡張を含む)
3. ✅ kLine入力の監視追加(デバウンス含む)
4. ✅ `WSClient` 受信コールバック化と `device_status` 定期送信
5. ✅ 爆発・解除シーケンスの演出実装
6. ✅ サーバー側 `/ws` へのデバイス用メッセージtype追加+シナリオテンプレート選択・ランダム化

### 11.1 ファイル対応

| ファイル | 役割 |
|---|---|
| `game_session.h/.cc` | セッションJSONのパース+検証(§6・§6.2)、kLEDパターンのプリコンパイル(§6.1) |
| `game_task.h/.cc` | 状態機械本体(§4)、100ms tick(§8.2)、ゲームルール(§5)、送受信(§7) |
| `led_controller.h` | kLED A-E の表示制御。パターン再生・上書き表示・変化時のみのI2C書き込み(§4.1・§6.1) |

| `battery_monitor_task.h` | バッテリー電圧監視と低電圧保護(§8.5) |
| `core-system.cc` | 入力(kLine・kPush・ロータリー)のイベント化とタスク起動 |

**責務の分離**: GameTask は状態機械とゲームルールの判断に専念し、
表示制御・モグラ叩き・ボタン列入力はそれぞれ独立したクラスへ切り出している。
切り出した3クラスは GameTask の他の状態に依存しないため、単体で動作を確認できる。

**残る調整項目**(いずれも実機で詰める前提の初期値):
終盤警告の点滅加速閾値(30秒)、`forbidden_rotary` の違反確定時間(300ms)、
whackのヒット・ミス時のフィードバック演出。
