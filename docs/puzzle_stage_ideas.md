# 謎解きステージ集

採用が確定した謎解きステージの一覧と、構成ルール・必要資料のまとめ。
全ステージは「**事前条件を満たした状態で指定の線を切る**」形で統一されている。
事前条件の正式仕様は `game_session_design.md` §5・§6 を参照。

- 作成日: 2026-08-08 / 更新日: 2026-08-24
- ステータス: **実装済み**
  (`.toml.disabled`。理由は各ステージの項に記載)。紙資料は制作待ち
- 関連: `game_session_design.md` / `operation_flow.md` / `navigator_design.md` /
  `printed_materials.md`(紙資料の制作仕様)

## 1. 共通の前提

- ナビゲーターは解除手順を知っており、ヒント・指示を無線で出す。
- Coreの隣に紙資料(A4裏表1枚。資料1〜資料3、§6)を置ける。
- **色体系**: kPush / kLED / kLine の3系統に共通の5色を割り当てる
  (A=赤, B=黄, C=緑, D=青, E=白)。「同じ色の線を切れ」等の色対応謎が成立する。
- **ロータリー**: パネル表記・JSONとも位置0-5。0↔5の端にストッパーあり
  (直線配置・連続回転なし)。
- ステージ内のランダム要素(切る線・ボタン順・モールス語など)は
  サーバーのテンプレートが候補から抽選する。
- **誤切断(指定以外の線を切る)の既定は explode(即失敗)**。
  ステージ定義で penalty(時間ペナルティ)に緩和できる(101 解体デビューなど)。

## 2. ステージ一覧

**ステージIDは3桁**で、**百の位が難易度**を表す。

| 番号帯 | 難易度タグ | 用途 |
|---|---|---|
| 1xx | `easy`(簡単) | **101-104** |
| 2xx | `normal`(普通) | **201-209** |
| 3xx | `hard`(難しい) | **301-305** |

**ステージは隙間なく詰める**(ADR S-9)。欠番が残ると「なぜ204だけ無いのか」を
毎回調べ直すことになる。**採用しないと決めたステージは削除して番号を詰め直す** —
残しておくと現役かどうかの判断が毎回必要になる。

ファイル名(`scenarios/stages/{ID}_{名前}.toml`)がそのまま番号順に並ぶ。
ステージを追加するときは該当の番号帯の**有効な末尾**に採番する。

> **正本は各ファイルの `difficulty` タグ。** 現在は番号帯と一致しているが、
> 難易度を見直せばまたずれる(2026-08-24 の見直しでは一度ずれ、その後
> 振り直して揃えた。§2.5)。**判定が要る場面では必ずタグを見ること**(ADR S-8)。
> **振り直しは運用が始まったら避ける** — セッションログが過去のIDを持つため
> 食い違う。

### 2.1 簡単

**101. 解体デビュー** ※イージーのみ・先頭固定

- **最初にやることを伝えてから**、会話でロータリーを誘導する:
  「ダイヤルを合わせてから、光っているランプと同じ色の線を切る」→
  「まず0に戻して」→「4まで回して」→「最後に2に合わせて」。
  初期位置が不定でも「まず0に戻す」で解決する。
- 中間手順の確認は会話ベース(プレイヤーの返答)。デバイス検証は切断時の最終位置のみ。
- **経由は1つだけ**(`0 → via1 → final_rotary` の3手順)。経由を増やしても
  学べることは変わらず、無線の往復が伸びるだけだった
  (実プレイで 0→3→5→2 の4手順に約3分かかった)。
- **切る線は「光っているランプと同じ色の線を切れ」と指示する**。正解の色だけが
  点灯するので、色名を言わなくても一意に決まる。ナビゲーターが色名を言うと
  プレイヤーは装置を見ずに従うだけになり、**このステージの目的である
  「装置を見て操作する」型が身につかない**(`navigator_design.md` §6 決定19)。
  かつては「何色が光っているか」を尋ね、報告を復唱してから指示し直していたが、
  最後に1往復増えるだけで**冗長**だった(実プレイで確認)。ゴールを先に伝えておけば
  プレイヤーはダイヤル操作中にランプを見て準備できる。
- **禁止位置は置かない**。目的は「無線で報告し、指示を受けて操作する」型を
  覚えることで、罠を仕込むと最初の一手で失敗して萎縮させる。
  禁止位置の緊張感は 206 綱渡り(即爆発)が担う。
- **中間経路は抽選する**(`via1`)。固定値で書くと毎回同じ手順になり、
  繰り返し遊ぶと単調になる。`final_rotary` と重ならないよう除外する。
  (かつては禁止位置との衝突回避も兼ねていた — 固定値だった頃、その値が
  危険位置に抽選されて「そこへ回せ」と「そこは危険」を同時に言う矛盾が出た。
  禁止位置は廃止したが、**手順の値を固定値で書かない**原則は残す。)
- **最終位置に 0 は選ばない**。「0に戻す → 経由 → 0」と出発点へ戻るだけの
  往復になるため(抽選の15%で発生していた)。
- 誤切断は**即爆発**。チュートリアルでも例外にしない (決定27)。
  かつては30秒ペナルティにしていたが、**切った線は物理的に戻せない**ため、
  後続ステージがその色を使うと組み立てが破綻する。
- 必要拡張: なし

**102. ホールド&カット**

- 「ロータリーを3に合わせ、緑のボタンを**押しながら**○色の線を切ってください」
- 片手でボタンを押さえてもう片手で切る、または2人協力になる。
- ランダム要素: ロータリー位置・ボタン色・線の色。
- **押すボタンは切る線と別の色にする**。同色だと `leds` が1エントリに潰れ
  (点灯が点滅で上書きされる)、「点滅=押すボタン / 点灯=切る線」の対応が
  画面に現れない。押さえた指がニッパーの邪魔にもなる。
- **最初にランプの状態を報告させる**。ダイヤルの指示から入ると、
  プレイヤーは押すボタンの存在に気づけないまま終わる
  (実プレイで発生。`procedure` で観察を先に置く形に修正した)。
- 必要拡張: なし(既存の rotary + push 保持で成立)

**103. コール&レスポンス**

- ナビゲーター「どのLEDが点灯している?」→ プレイヤーが色を報告 →
  「では○色のボタンを押して」を2回程度 →
  「最後に点灯しているLEDと同じ色の線を切って」。
- 最終指示の変形(点滅中の下の線・さっき点滅していた色など)はテンプレートで抽選。
- ボタン指示は `push_seq` として定義し、正しい押下のたびに `push_progress` が
  サーバーへ届くため、ナビゲーターは実際の操作に反応できる(「今ので合ってる!」)。
- 必要拡張: `push_seq` + `push_progress` 通知
- **押し切ったら切る線だけが残る**(2026-08-24。ADR C-12)。
  押下中は「報告用の点灯」と「切る線の点滅」が**両方見えている**。
  押し終わると `reveal_cut_on_complete` が働き、**切る線の色だけが点灯**して
  他は消える。押下フェーズの終わりが装置から一目で分かる。
- **最初から両方見せるのが要点**。押し終わってから初めて切る線が光る形だと、
  「報告した色と切る色が違う」という気づきが発生せず、ただの
  「押し終わったら光った色を切る」になり、対話の一往復が消える。
- **`push_progress` では発話しない**(ADR N-26)。正しい押下のたびに通知は
  届くが、ナビゲーターは装置を見ていないので「今ので合ってる」とは言えない。
  反応するのはプレイヤーが**報告してきたとき**だけ。
- 押す数は3個。列は `pick = "color_seq"` で引き、
  **切る線と報告用の点灯色の両方を除外**する — 押す色と報告色が同じだと
  「報告した色を押す」だけになり、対話の一往復が消える。



**104. 早い者勝ち**

- 2つのLEDのうち「**速く点滅している色**」の線を切る。
- 必要拡張: なし(blinkの `on_ms` / `off_ms` 個別指定)

### 2.2 普通

**201. 復唱**

- 「赤赤黄黄赤の順でボタンを押してから、○色の線を切ってください」
- 列はテンプレートで抽選する。**無線で1回聞いて覚えられる長さ(5個)**にする。
- ミスは列の先頭からやり直し(retry既定)。**ボタン列系はノーマルの 201 だけ**。
- ナビゲーターは聞き返されたら**何度でも繰り返す**
  (無線の往復自体が時間消費になる)。
- 必要拡張: `push_seq`
- **列の長さは難易度で変わる**(2026-08-24。ADR S-11)。
  イージー・ノーマルは**5個**(無線で1回聞いて覚えられる長さ)、
  **ハードは8個**。長さは難易度テンプレートの `[load] push_seq_len`
  から引く。**ハードは「普通×2」を引く**ので、normal タグのこのステージも
  ハードのセッションに出て、そこで8個になる。
- **8個を超えて伸ばさない**。記憶ではなく「読み上げを何度も聞き直す」
  時間になり、無線の往復が増えるだけで謎が難しくなるわけではない。
- 列は `pick = "color_seq"` で引く。**重複を許し、引いた順のまま**返す
  (`colors` と違い並べ替えない)。ただし**同じ色の3連続は避ける** —
  無線で「赤赤赤」と読み上げると何個言われたか数えられず、
  記憶ではなく聞き取りの問題になる。
- ナビゲーターは**列が長いほど区切りを細かくする**。5個なら通しで読んでよいが、
  8個は2〜3個ずつに区切り、押せたところを確認しながら進める。


**202. 暗号電文**

- LEDがNATOフォネティックコードの語(3〜5文字推奨: GOLF, ECHO, DELTA,
  BRAVO, ALFA など)をモールスでループ表示。表示するLEDはテンプレート抽選。
- 資料1のモールス対照表(**各文字に色付きの固定印刷**。
  A=赤, B=黄, C=緑, D=青, E=白, F=赤, G=黄… と**5色を循環割当**)で解読して
  ナビゲーターに報告 →
  「アルファですね。ではモールス表のAの色と同じ色の線を切ってください」。
- 「ゴルフ」と読んでも1文字ずつ言ってもOK(ナビゲーター応対ルール)。
- テンプレートは語の頭文字→表の色→`cut` の整合を取って生成する。
- **候補語は5色すべてをカバーするよう揃える**。頭文字から色が一意に決まるため、
  候補が一部の色に偏っていると「残っている色の語が無い」状態になりうる。
  各色から3語ずつ用意しておけば、どの色が残っていても語を選べる。
  頭文字の色が既に他ステージで使われている語は、組み立て時に候補から外れる。
- モールス表示が長くなりすぎないよう、各色から短めの語を選ぶ。
- 必要拡張: なし(LEDモールスは実装済)

**203. ブループリント**

- 資料3に「整備マニュアル風の回路図」を印刷する。端子番号と配線色の対応が
  回路図として描かれており、ナビゲーターは色を言わず端子番号だけを指示する。
- **端子は2系統ある**(X1〜X5 / Y1〜Y5)。どちらを使うかは
  **シリアル銘板(CoreID記載)の下1桁**で決まる(奇数=X / 偶数=Y)。
  銘板は運営が音声申告に使う CoreID と**同じ1枚**で、呼び方だけ場面で変える。
  ナビゲーターは「**シリアル銘板の下1桁が奇数ならX4、偶数ならY2の線を切れ**」と
  **両系統を並べて**言い、**選ぶのはプレイヤー**。
  サーバーは個体のシリアルを知らないため、片方に絞れない(ADR D-6)。
- 「奇数=X / 偶数=Y」の対応は**紙に印刷しない**(ナビが毎回言う)。
  X と Y は**完全に別の対応**にするため、取り違えると必ず誤答になる。
- **5色すべてを点灯**させる。これは**このステージにしか出ない表示**で、
  「全部光っています」というプレイヤーの報告を受けてナビゲーターが
  「回路図参照の合図だ」と応じる**報告 → 指示**の往復を作るためのもの。
  かつてはLEDを一切出さない設計だったが、それだとプレイヤーが装置を見ずに
  紙だけを見ることになり、**このゲームの体験の軸である交信が発生しない
  唯一のステージ**になっていた(§5 決定)。
  全灯は5色が同じ表示なので**色のヒントを含まず**、「資料3だけが手がかり」
  という原則と難度はそのまま保たれる。
- **難易度は normal に据え置く**。増える工程は「銘板の下1桁を見る」だけで、
  解読も計算も伴わない。ただし誤切断は即爆発(S-2b)なので、
  **系統の読み違えは即死**になる。銘板は下1桁が紛れない書体で刷る。
- 必要拡張: なし(紙資料のみ。Core本体にシリアル銘板が必要 — 音声申告でも使う CoreID と同じ1枚なので元々必要)

**204. 色合わせ**

- 「光った色のボタンを押していけ。**最後に押した色の線を切れ**」。
  **時間で切り替わらない**ので、急ぐ要素は無い。
- **押す回数は難易度で変わる**(イージー4〜6 / ノーマル6〜9 / ハード9〜12)。
  難易度テンプレートの `[load]` に置き、ステージ定義は
  `${load_color_match_min}` で参照する(§4.2)。**ステージ側に直書きしない** —
  直書きすると難易度を跨いで同じ負荷になる。
- **ナビゲーターは回数を案内しない**(ADR N-42)。装置を見ていないため
  今何回目かを追えず、「あと3回だ」と言えば必ず嘘になる。
  終わりは回数ではなく**ランプが全部消えること**で伝える。
  回数は**ナビゲーター知識にも入れない** — 但し書きで禁じても漏れるため、
  202・205 の色名と同じく最初からプロンプトへ載せない。
- 押し切ると**kLEDが全消灯**する。手がかりは「最後に押した色」の記憶だけ
  になるので、**先に覚えておくよう伝える**必要がある。
- 最後の1つはJSONの `cut` と同色に固定(それ以外はランダム)。プレイヤーには
  見分けがつかず、サーバーは正解線を既知のまま切断線の重複検証も維持できる。
- 必要拡張: color_matchの `last_matches_cut` オプション

**205. 速さくらべ**

- **1色が点灯しっぱなし(基準外)+ 残り4色が違う速さで点滅**。点灯している色は
  数に入れず、点滅している4色を速い順に並べて「**N番目に速い色**の線を切れ」。
  **N は毎回抽選する**(1〜4)。
- 104 早い者勝ち(2色から速い方)の多色版。2択の見比べから、4色から最速を選び出す作業へ
  難度が上がる。
- **点灯1色を置くのは報告を作るため**。全色が点滅していると最初の報告が
  「全部点滅しています」にしかならず、無線の往復が生まれない。1色だけ点灯させると
  『○色だけ点きっぱなしです』という一言で済む報告が発生し、ナビゲーターが
  「その色は数えるな」と応じる往復ができる。
- **切る順位を毎回抽選する**(ADR N-40)。かつては**正解を最速に固定**していた。
  中間順位を引くと `answer` が「○番目に速い色」となり、**L4(直言)で
  ナビゲーターが色名を言えない**ためだった。
  **ノーマル以上が L4 を出さなくなった(ADR N-39)ので、この制約は消えた** —
  L3 が上限ならどのみち色名は言わない。「一番速い色を切れ」しか言えない状態は
  指示が毎回同じで単調だったため、順位を抽選する形へ戻した。
  「一番速い」「一番遅い」の当たり回もあるので難易度に幅が出る。
- **順位は装置を見ても分からない情報**なので、`hint_l1` で必ず伝える(§5 決定22)。
  伏せると何番目を探せばよいか分からず手詰まりになる。
- 速度は隣接比が 1.4〜2 倍になる**固定4段階**(150 / 300 / 550 / 1000ms)。
  ランダムな速度にすると抽選次第で差が接近し、見分けが運になるため。
  どの色にどの速度を割り当てるかはランダム。
- 点滅は対称(点灯時間=消灯時間)。モールス表示のステージ(203/305)と
  混同されないようにする。
- **`cut` を先に引く**。5色すべてを表示に使うため正解は未使用の線に限る必要が
  あるが、表示色を先に決めて `choice` の `as_line` で選ぶ形にすると、候補
  (両端2色)が両方とも使用済みのときに**組み立てが失敗する**(実際に再現した)。
  `pick = "line"` で先に引き、残りの表示色をそこから除外して埋める。
  **順位を抽選する形に戻したあともここは変えていない** — cut を先に引き、
  `derive = "rank_slot"` で並びの中の位置だけを決めるため、候補が
  使い切られる問題は起きない。
- 必要拡張: `derive = "rank_slot"`(cut を rank 番目に置いた並びの slot 番目を返す)
- **点滅速度は難易度で変わる**(2026-08-24。ADR S-12)。
  値は難易度テンプレートの `[load] speed_rank_ms` から引く。

  | | 速度(ms) | 隣接比 | 最遅 |
  |---|---|---|---|
  | ノーマル | 150 / 300 / 550 / 1000 | 1.82〜2.0倍 | 0.5Hz(明らかに遅い) |
  | **ハード** | **150 / 210 / 294 / 412** | **1.4倍均一** | 1.2Hz(まだ速い) |

- ハードは全体でも 2.75倍しか開かず、**「一番遅いのが一目瞭然」が消える**。
  104 早い者勝ち で決めた下限(1.5倍)を**意図的に下回る** — 104 は2択だが
  205 は**4色を並べ替える**ため比較回数が多く、同じ隣接比でも難しい。
- **ハードは「普通×2」を引く**ので、normal タグのこのステージも
  ハードのセッションに出て、そこで詰まった速度になる。
- **実機で見え方を確認してから確定させる**。詰めすぎると並べ替えが運になる。



**206. 綱渡り**

- **`forbidden_rotary` を使う唯一のステージ**。違反時は**即爆発**。
  (かつては 101 解体デビューにも警告付きで置いていたが、チュートリアルで
  最初の一手を失敗させると萎縮するため廃止した。禁止位置の緊張感はここが担う。)
- ロータリーは直線配置(0-5)なので目的位置へ行く途中で禁止位置を通過する。
  **通過はセーフ、止まると違反**。慎重に、しかし止めずに回す必要がある。
- 必要拡張: なし(`forbidden_rotary` の `explode` 設定)
- **禁止位置の数は難易度で変わる**(2026-08-24。ADR S-10)。
  イージー・ノーマルは1つ、**ハードは2つ**。数は難易度テンプレートの
  `[load] forbidden_rotary_count` から引く。
  **ハードは「普通×2」を引く**ので、normal タグのこのステージも
  ハードのセッションに出る。そのときに2つになる。
- 2つになると**配置によって難しさの質が変わる**。どの型も出す:

  | 型 | 例 | 何が難しいか |
  |---|---|---|
  | 隣接 | 禁止{1,2} → 目的4 | 連続して通過する。一気に回せば1回で抜ける |
  | 離れている | 禁止{1,3} → 目的5 | 間の安全地帯で一度止まれる。**2段構え**になる |
  | 目的地を挟む | 禁止{1,5} → 目的3 | **行き過ぎると危険**。止める精度が要る |

- **位置を個別に抽選しない**。`pick = "rotary_layout"` で**配置ごと**引く。
  個別だと配置が偏るうえ、**目的位置の両隣が禁止**になる組み合わせが出る
  (到達はできるが、合わせたあと手が滑って1つ動かすと即爆発する。
  難度ではなく運になる)。成立する配置だけを列挙して等確率で引く。
- **ナビゲーターは危険位置を全て伝える**。1つでも伏せると、知りようがない
  まま踏んで即爆発する。無線では「3と5」と**数字を区切って**読み上げる
  (カンマのままだと TTS が小数や記号として読み、聞き間違いが直接事故になる)。


**207. 息が合わない**

- 5色すべてが**同じ速さ**で点滅するが、1色だけタイミング(位相)がずれている。
- 205 速さくらべは「速さ」を比べるが、こちらは速さが全部同じ。
  「揃っているかどうか」を見る別の観察になる。
- 周期800msを揃え、点灯時間を **400ms 対 150ms** と大きく離してある。
  探すのは「1つだけ」なので、ナビが「他と息が合っていない色はありませんか」と
  問えばプレイヤーは1色を見つけるだけで済む。
- 必要拡張: なし(blink の `on_ms` / `off_ms` の比率で位相をずらす)

**208. ジャストカット**

- 「タイマーの**秒の一の位がNのとき**に○色の線を切ってください」。
- Nはテンプレートで1〜9から抽選(0は残り時間僅少と紛らわしいため除外)。
- 判定窓は「一の位がNの1秒間+直後1秒の猶予」の計約2秒。**窓を外したら即爆発**。
- プレイヤーへの言い回しは「小数点のすぐ左の数字」等、ナビゲーターの台詞で明確化
  (表示は `123.4` 形式のため)。
- 必要拡張: `timer_digit`(固定値比較)

**209. 配電盤照合**

- **ロータリーを回すたびにランプの光り方が変わる**。今の見え方から現在位置が
  分かるので、手元の資料4で**危険位置**と**解除位置**を引く。
  解除位置へ回すと切るべき線が点滅する。
- 想定する会話:

  ```
  プレイヤー 「赤が点いて青が点滅しています」
  ナビ       「ロータリーが0番にありませんか」
  プレイヤー 「はい、そうです」
  ナビ       「では手元の資料4を見てくれ。解除方法が書いてある」
  ```

- **位置ごとの見え方**(ADR C-14):

  | 位置 | 表示 | 意味 |
  |---|---|---|
  | 現在位置 | 対照表どおり(点灯+点滅) | **ここから表を引く** |
  | 解除位置 | **cut だけが点滅**+ダミー点灯 | ここで切る |
  | 危険位置 | **赤だけ点灯** | 止まると即爆発 |
  | その他 | ランダム2〜3色点灯 | ダミー |

- **解除位置の表示は対照表に載せない**。載せると「解除位置は3 → その行の
  点滅色が答え」と**回す前に分かってしまい**、回す工程が消える。
- **赤だけ点灯は危険位置に予約**。対照表の行はすべて点灯+点滅の2色なので、
  1色だけの表示は必ず「危険位置に止まっている」を意味する。
  ダミーも2〜3色にしてこの合図と紛れないようにする。
- **cut が対照表の点滅色と重なる行は抽選しない**。重なると現在位置の表示で
  cut が点滅し、やはり回す前に答えが見える。
- **危険位置は必ず現在位置と解除位置の「間」にある**。解除位置へ向かうと
  必ず通過するので、「止まらずに通り抜ける」操作が毎回発生する。
  経路の外だと素通りでき、このステージの緊張が消える。
- **ナビゲーターは対照表を持たない**。表を読むのはプレイヤーの仕事で、
  ナビが持つと「0番ですね、危険は4、解除は3です」と全部言えてしまう。
  ただし**危険位置だけは読み取れたか必ず確認する**(踏むと即爆発するため)。
- 必要拡張: `rotary_leds`(位置ごとのLED表示。**ファーム変更あり**)


### 2.3 難しい

**301. LED照合**

- ランプの点灯パターンを**紙資料で3段階に読み解き**、
  **ダイヤル位置と切る線の両方**を導く。202 で唯一「表示から2つの答えが出る」。

  ```
  ランプ4つの点灯/消灯 → 変換表でキーワード       (例 INDEX)
  キーワードの頭文字   → デコード表でダイヤル位置 (I → 1)
  キーワードの末尾文字 → デコード表で基準色       (X → 緑)
  基準色 + ランプの状態 → 分岐表で切る線が決まる   (緑・白点灯 → 緑)
  ```

- **赤のランプは常時消灯のダミー**。残る4つ(黄・緑・青・白)が4bitになる。
  **全消灯だけは使わない** — 故障と見分けがつかず、プレイヤーが止まる。
  資料2 には15通りを載せる。
- 対照表は `app/game-server/scenario_codebook.go` に1箇所だけ置く
  (`printed_materials.md` §3)。**cut から表示を逆引きする**ため、
  他ステージとの色の重複(§S-2)は通常どおり回避される。
- 5色すべてに**最低2通りずつ**表示が対応するよう語を選んである。
  1通りしか無い色があると、その色が正解の回は毎回同じ表示になり暗記できる。
- **ダイヤルを合わせた状態で切る**必要があるため、
  最後まで解かないと切れない(色だけ分かっても足りない)。
- 必要拡張: なし(`pick = "codebook"` + `derive = "codebook_field"` を追加済み)

**302. 暗号電文・ジャミング**

- 202 暗号電文の難しい版。モールス表示に加え、**残り4色のLEDが妨害として
  点灯・消灯・点滅する**。どのランプがモールスかを見つける手間が加わり、
  解読中も視界の情報量が多い状態が続く。
- **切る線の決め方は 202 と同じ**(語の頭文字 → 対照表の色)。
  **違いは妨害があることだけ**で、これは**意図した重複** —
  「同じ解き方を、情報量が多い状況で成立させられるか」を問うステージ。
  202 で手順を覚えたうえで妨害版に挑む流れは難易度の上がり方として自然。
- **モールスは1色だけ**。5色すべてを流すと1本を読む間も他が進み、
  「見比べて絞り込む」つもりが**同じ文字を何周も待つ**耐久作業になる。
  探す対象が1つに定まる形を保つ(妨害はモールスではない)。
- **妨害の点滅は対称(点灯時間=消灯時間)**にする。モールスは短点=1単位・
  長点=3単位の非対称なリズムなので、対称にしておけば「これはモールスではない」と
  落ち着いて見分けられる。**見分けにくさではなく情報量で難度を上げる**設計。
- 妨害の内訳(点灯しっぱなし / 消灯 / 対称blink)と点滅速度はテンプレートで抽選する。
- **名前は「混信」ではなく「ジャミング」**。混線(crosstalk)は**無線に別の声が
  入る音声演出**として既に使っている語で(ADR T-8〜T-12)、運営が「混線が出た」と
  言ったときにどちらか区別できなくなる。
- 必要拡張: `noise_leds`(妨害LEDの割り当て)

**303. 追いかけダイヤル**

- 「残り時間の**十の位**と同じ位置にロータリーを合わせて○色を切れ」。
- 正解が時間とともに変わり続ける。判定はデバイス内で行う。
- 必要拡張: `timer_digit`(ロータリー比較)

**304. 我慢比べ**

- 「○色のボタンを**押し続けたまま**、タイマーの一の位がNのときに△色を切れ」。
- 208 ジャストカット(タイミング)と 102 ホールド&カット(保持)の組み合わせ。片手がふさがった状態で
  ニッパーを構え続ける必要があり、待つ時間の緊張が長く続く。
- 判定窓は約2秒。Nは1〜9から抽選(0は残り時間僅少と紛らわしいため除外)。
- 必要拡張: なし(`push` 保持 + `timer_digit` の同時成立。事前条件はAND)

**305. ローマ字電文**

- モールスで**色名そのもの**(AKA / KI / MIDORI / AO / SIRO)を表示する。
  対照表での変換は不要で、読めればそのまま答えになる。
- 203 が「頭文字→対照表→色」の2段階変換なのに対し、こちらは1段階。
  ただし語が長く(最大6文字)、**解読そのものに時間がかかる**。
  難しい難易度に置く理由は「変換の複雑さ」ではなく**所要時間**。
- 必要拡張: `romaji_word` / `romaji_color`(色名のローマ字表記と色の対応)

### 2.4 モールス系を2つに絞る

モールス解読は 203 / 302 / 304 / 305 の4種あり、ハード(普通×2 + 難しい×2)では
**最大3枠がモールスで埋まる**状態だった。解読は1ステージあたりの所要時間が
長いため、セッションの大半が「対照表を睨む時間」になってしまう。

**当初は 203(普通)と 305(難しい)の2つに絞った**。理由は謎の質が違うこと:

| | 変換 | 報告の形 | 役割 |
|---|---|---|---|
| 202 暗号電文 | 頭文字 → 対照表 → 色(2段階) | 「アルファです」と語で報告 | モールスの入口。**紙資料(対照表)を使う唯一のステージ**になる |
| 305 ローマ字電文 | 読めばそのまま色名(1段階) | 「M、I、D…」と**1文字ずつ積み上がる** | 難度は所要時間で作る。**無線の往復が最も多く発生する** |

**その後 302 を戻して3種にした**(ADR N-41)。数字1桁を**英字1文字**へ
変えたことで所要時間が大きく下がり、「セッションの大半が対照表を睨む時間」に
なる懸念が薄れたため。3種の役割は次のとおり:

| | 変換 | 読む量 | 役割 |
|---|---|---|---|
| 202 暗号電文 | 頭文字 → 対照表 → 色(2段階) | 語1つ(3〜5文字) | モールスの入口 |
| 305 ローマ字電文 | 読めばそのまま色名(1段階) | 語1つ(最大6文字) | 所要時間で難度を作る |

302 は**変換が無い**代わりに**見比べる**のが謎で、203/305 とは作業が違う。
1文字なので1色あたりの解読は最短。

304 を外した理由はその項に記載。実装(`noise_leds`)は残してあるため、
復活は `.toml.disabled` を戻すだけでよい。

ハードで 203 と 305 が同居しても「対照表で変換する版」と「読めばそのまま版」で
体験が異なり、305 のほうが長いので順序としても自然。
ノーマル(普通×2)ならモールスは 203 のみで**最大1つ**に収まる。

### 2.5 難易度タグの見直し (2026-08-24)

全19ステージを**表示色数と工程数**で並べたところ、**ノーマルが重くハードが軽い**
という逆転が見つかった。

| | 表示色数 | 工程 |
|---|---|---|
| 見直し前のノーマル | ほぼ全部が**5色** | 解読・並べ替え・紙3表など**多段** |
| 見直し前のハード | **1〜2色** | タイミング**単発**が3件 |

ハードは 301・302・304 がタイミング系で観察対象が1〜2色、305 も
**変換不要**(読めば色名)で 203 より易しい。一方ノーマルには 202(紙3表+ダイヤル)
や 302(5色同時モールス)が入っていた。

**変更したもの**:

| ステージ | 変更 | 理由 |
|---|---|---|
| **301 LED照合** | normal → **hard** | 資料2の**3つの表を順にたどり**、さらに**ダイヤルを合わせて切る**。工程が4段で全ステージ中最長。ノーマルは3ステージなので時間配分が厳しかった |
| **208 ジャストカット** | hard → **normal** | 「一の位が指定の数字になった瞬間に切る」だけで**観察も推理も無い**。点灯1色。302(ダイヤル追従)・304(押しながら)と違い条件が単発 |

**据え置いたもの**: 203 ブループリント(銘板で系統を選ぶ判断は重いが、
引く工程自体は1段)、104 早い者勝ち(イージーの在庫が4件に減るため)。

**プール内訳**: 簡単4 / 普通9 / 難しい5。必要なのは 簡単1 / 普通2 / 難しい2
なので、いずれも余裕がある。

**この見直しの直後に ID を振り直し、番号帯とタグを一致させた**(ADR S-9。§2 冒頭)。
有効なステージを 101-104 / 201-209 / 301-305 へ詰めてある。

## 5. 難易度別のステージ構成ルール

| ゲーム難易度 | 構成 | ステージ数 |
|---|---|---|
| イージー | 簡単 ×2(101を先頭固定+残り抽選) | 2 |
| ノーマル | 簡単 ×1 + 普通 ×2 | 3 |
| ハード | 普通 ×2 + 難しい ×2 | 4 |

- 配線は5本あるが、**1セッション最大4ステージ**とし、切断線を
  **必ず1本以上余らせる**。5ステージにすると全色を使い切り、最後のステージは
  残り1色に固定されて抽選の余地が消える。特に切る色が構造的に決まるステージ
  (203。頭文字→対照表の色)は、残り色と合わなければ組み立て不能になる。
- 同一ステージの重複選出はしない。
- 101はイージー専用(ノーマル・ハードは経験者・腕に自信のある人向け)。
  テンプレートでは `easy_only = true` で指定する。
- **構成はハイブリッド方式**: タグ抽選に加え、テンプレートで固定の並びを指定できる
  (ステージ間の演出連携は手組みの固定並びで作る)。
- カウントダウン時間は難易度・ステージ数に応じてテンプレートで指定。
- 数値は実機検証で微調整可。
- **切る色が構造的に決まるステージ(203)は、候補を全5色分揃える**。
  203は語の頭文字が対照表で色に決まるため、候補語の頭文字が5色すべてを
  カバーするようにしておけば、どの色が残っていても語を選べる。
  ステージ数の上限(4)と合わせ、割り当て順を特別扱いする必要がなくなる。

- **`[navigator]` に固定値を書かない**。procedure / hint に書いた数値や色が
  抽選値と衝突すると、ナビゲーターの指示が自己矛盾する(101 で実際に起きた:
  中間経路の固定値 `4`/`2` が危険位置に抽選され、「4まで回せ」と
  「4は危険」を同時に言う状態になった)。手順に出てくる値は
  抽選変数にして、衝突しうる値を `exclude` で外す。
- **LEDの見分けは「1つだけ探す」形に留める**。5色すべてを順位付けさせる形は、
  肉眼で差を測る精度が要るうえ、ナビが色名を言えない `answer` になりやすく、
  行き詰まったときに無線の問答で救えない。1色を指させる形なら
  ナビが「他と違う色はありませんか」と誘導でき、難しさが
  「見つけにくさ」だけに収まる。207 息が合わない の点灯時間差を
  100ms → 250ms に広げ、208 の正解を最速に固定したのはこの判断による。
- **装置に現れない情報は `hint_l1` で伝える**。ボタンを押す順番 (102/201/305) や
  危険なダイヤル位置 (209) は**ナビゲーターしか知らず**、プレイヤーは観察でも
  推理でもたどり着けない。これを伏せると無線が「順番を教えて」の往復で浪費され、
  209 では知らずに踏んで即爆発する。段階的に明かしてよいのは**推理できる情報**だけで、
  ヒント段階で調整するのは「一度に何色まで言うか」。
  回帰は `TestUnobservableInfoRevealedAtL1` が押さえている。
- **すべてのステージに報告できる表示を置く**。このゲームの体験の軸は
  「プレイヤーがLEDの状態を無線で報告し、ナビゲーターが解除方法を教える」
  往復にある。LEDを一切出さないステージや、全色が同じ挙動で
  報告に意味が生まれないステージは、装置を見ずに指示へ従うだけの体験になる。
  **表示は正解のヒントである必要はなく、「どの謎か」を識別できれば足りる**

現在のプール内訳(2026-08-24 時点。**難易度は `difficulty` タグで数える**。§2.5):

| タグ | 件数 | ステージ |
|---|---|---|

## 6. 紙資料(制作チェックリスト)

**印刷する表の中身・レイアウト要件・設定との連動は
[`printed_materials.md`](printed_materials.md) に集約**している(制作時はそちらを見る)。
ここでは各資料の位置づけのみをまとめる。

紙は **A4裏表1枚**にまとめ、**独立して参照される要素ごとに「資料N」を印刷**する。
ナビゲーターは「**手元の資料1を見ろ**」と番号で指す (ADR D-2)。

| 資料 | 用途 | 要件 |
|---|---|---|
| **資料1** モールス対照表 | 202, **302**, 305 | 各文字(A-Z)に**色を付けた固定印刷**。5色を循環割当。203では「頭文字の色=切る線」の参照元になる。**数字は載せない**(出題は A-Z のみ。ADR N-41) |
| **資料2** 変換表 + デコード表 + 分岐表 | 202 | **3つの表を1番号に**。変換表=ランプの並び(●○)→ キーワードの15行(**見出しはランプの色名**)。デコード表=頭文字 → ダイヤル位置(区間は 5・4・4・4・4・5)/ 末尾文字 → 基準色(5色を循環割当)。分岐表=基準色+ランプ → 切る線。罫線で区切るが枠は分けない |
| **資料3** 回路図 | 205 | 整備マニュアル風。端子番号(X1〜X5 / Y1〜Y5)⇔配線色の対応。**202 の分岐表は載せない** — 色対応が 205 のプレイヤーの視界に入る(`printed_materials.md` §3.4) |
| シリアル銘板(CoreID記載) | 全体 + **205** | Core本体に貼る**1枚**。4桁IDを表示し、運営は音声申告・リセットに使う。**205 では下1桁の奇数/偶数**で端子系統(X/Y)を選ぶ(ADR D-6)。プレイヤーには「シリアル銘板」、運営には「CoreID」と呼び分ける。紙資料とは別物なので**資料番号を持たない** |

**番号は物理的な紙の枚数ではなく参照単位**で振る。判断基準は引く回数ではなく
**片方だけ見る場面があるか**。202 の変換表とデコード表は必ず順にたどるので1番号。
逆に**複数のステージが同じ資料を見る**(203・305 はどちらも資料1)。

**面(表裏)はナビゲーターが指示しない** — 印刷レイアウトの変更に強くするため、
また探す手間もプレイヤーの遊びのうちと位置づけるため。

## 7. サーバー設定に登録する物理定数

サーバー設定 (`config.toml` の `[mission_sheet]`) に登録する。

| 設定キー | 用途 | 内容 |
|---|---|---|
| `[mission_sheet.terminal_map]` | 205 | 資料3の端子番号(X1〜X5 / Y1〜Y5) → 配線色(A-E) の対応 |
| `[mission_sheet.documents]` | 202/203/205/305 | **資料の呼称**(`morse` / `codebook` / `circuit`) |

紙を刷り直した場合はこれらの値の更新が必要。

**資料の呼称**はステージ定義から `${sheet_morse}` のように参照する。
文面へ直接「資料1」と書かない — 番号を振り直したときに食い違うため。
呼称が空だと空文字に展開されて意味の通らない発話になるので、**起動時に落ちる**。
資料名は**ナビゲーター知識にだけ**入り、Core向けJSONには含めない。

**202 に実測値の登録は要らない**。対照表は**抽選に関わらず固定**で、
刷り直しても値は変わらないため `scenario_codebook.go` に持たせてある
(設定に出すと紙・設定・実装の3箇所が食い違いうる)。
連動するのは**資料の呼称だけ**。テンプレートは `cut` から表示を逆引きし
(`pick = "codebook"`)、キーワード・ダイヤル位置・点灯色を
`derive = "codebook_field"` で引く。

**205の端子対応**: `cut` の色から端子番号を逆引きして
ナビゲーターへ渡す(ナビゲーターは端子番号だけを指示し、色は言わない)。
`terminal_map` に `cut` の色が無いと組み立てが失敗するため、5色すべてを登録する。
