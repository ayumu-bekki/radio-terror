# 紙資料(別紙)制作仕様

プレイヤーが Core の隣で参照する紙資料の制作仕様。
表の中身はサーバー実装と一致していなければならないため、**この文書の値をそのまま印刷する**。

- 作成日: 2026-08-09 / 更新日: 2026-08-23
- ステータス: 制作待ち(内容は確定)
- 関連: `puzzle_stage_ideas.md`(各ステージの内容) /
  `scenario_design.md`(テンプレートからの参照) /
  `game_session_design.md` §3(色体系)

## 0. 制作物一覧

**A4裏表1枚**にまとめ、独立して参照される要素ごとに**資料番号**を振る。
ナビゲーターは「**手元の資料1を見ろ**」と番号で指す(§1.3)。

| 資料番号 | 内容 | 使うステージ | 差し替え頻度 | サーバー設定との連動 |
|---|---|---|---|---|
| **資料1** | モールス対照表 | 202, 302, 305 | 固定 | **あり**(呼称のみ。表は実装にハードコード) |
| **資料2** | 変換表 + デコード表 + 分岐表(**3つの表を1番号に**) | 301 | 固定 | **あり**(呼称のみ。表は実装にハードコード) |
| **資料3** | 回路図(**X/Y 2系統**) | 203 | 刷り直し時に設定更新 | **あり**(`terminal_map_x` / `_y` + 呼称) |
| **資料4** | ロータリー対照表(見え方 → 位置/危険/解除) | 209 | 固定 | **あり**(呼称のみ。表は実装にハードコード) |
| — | シリアル銘板(CoreID記載) | 全体(音声申告・リセット)+ **203**(下1桁で端子系統を選択) | 個体ごと | あり(`CONFIG_CORE_SYSTEM_DEVICE_ID`) |

シリアル銘板は Core 本体に貼るもので、紙資料とは別物のため資料番号を持たない。
**運営用の CoreID とプレイヤー用のシリアルは同じ1枚**(§5)。

**サーバー設定との連動があるもの**は、印刷内容を変えたら
`app/game-server/config.toml` の `[mission_sheet]` も必ず更新する。
食い違うとナビゲーターの指示と正解がずれ、プレイヤーが理不尽に失敗する。

## 1. 共通事項

### 1.1 色体系

kPush / kLED / kLine の3系統に共通の5色(`game_session_design.md` §3)。
**紙資料の色は実機の配線色と厳密に一致させる**。

| 記号 | 色名 | 用途 |
|---|---|---|
| A | 赤 | 配線・LED・ボタン |
| B | 黄 | 〃 |
| C | 緑 | 〃 |
| D | 青 | 〃 |
| E | 白 | 〃 |

- 記号(A-E)は**サーバー内部の識別子**であり、**紙資料には印刷しない**。
  プレイヤーが見るのは色そのものだけ。
- 色覚多様性への配慮として、色面だけでなく**色名(赤/黄/緑/青/白)も併記**する。
  白は紙面上で見えないため、**枠線付きの白**または「白」の文字で示す。

### 1.2 印刷・運用の要件

- 会場の照明下で読める十分なコントラストを確保する。
- プレイヤーは**セーフティーグラス着用・立ったまま**参照するため、
  文字サイズは大きめ(本文14pt相当以上)にする。
- 装置の隣に置くため、**A4横・裏表1枚**にまとめる。枚数を増やすと
  プレイ中に紙を取り違える事故が起きる。
- 濡れ・折れに備え、ラミネート加工を推奨する。

### 1.3 資料番号(ナビゲーターが一言で指すための番号)

**独立して参照される要素ごとに「資料N」という番号を振る**。
ナビゲーターは「**手元の資料1を見ろ**」と番号だけで指示する。

| 資料番号 | 内容 | 参照ステージ |
|---|---|---|
| 資料1 | モールス対照表 | 202, **302**, 305 |
| 資料2 | 変換表 + デコード表 + 分岐表(**3つの表を1番号に**) | 301 |
| 資料3 | 回路図(端子⇔配線色) | 203 |
| 資料4 | ロータリー対照表 | 209 |

**番号は物理的な紙の枚数ではなく参照単位で振る**。判断基準は引く回数ではなく
**一部だけ見る場面があるか**。301 の3つの表は必ず順にたどるので1番号にまとめる。
逆に**複数のステージが同じ資料を見る**ことはある(202・302・305 はどれも資料1)。

**設計上の決まり**:

- **面(表裏)は資料番号に含めず、ナビゲーターも指示しない**。
  面を言うと印刷レイアウトを変えるたびにサーバー設定と文面の更新が必要になる。
  探す手間もプレイヤーの遊びのうちと位置づける。
- **番号順に読める並びにする**(資料1 → 2 → 3 → 4)。配置はデザイン側に任せるが、
  番号を追えば見つかる状態を保つ。
- **ナビゲーターは初出で中身も添える** — 「手元の資料1にモールスの対照表がある」。
  どの資料に何が載っているかは**装置を見ても分からない情報**なので、
  伏せると手詰まりになる(ADR N-4)。2回目以降は番号だけでよい。
- 呼称は `config.toml` の `[mission_sheet.documents]` に登録し、
  ステージ定義は `${sheet_morse}` のように参照する(§7)。
  **文面へ直接「資料1」と書かない** — 番号を振り直したときに食い違う。
- 203 ブループリントの**端子番号 T1〜T5 と数字が重なる**が、「資料3を見ろ」と
  「端子T2の線を切れ」は別の発話に分かれるため許容する。

## 2. 資料1 — モールス対照表 (202 暗号電文 / 302 暗号電文・ジャミング / 305 ローマ字電文)

### 2.1 用途

LEDがモールス信号で表示する語をプレイヤーが解読し、
**その語の頭文字に対応する色の線を切る**ために使う。

ナビゲーターは「解読した単語の頭文字を資料1で引き、その色の線を切ってください」
と指示する。色名は最後まで言わない。

**302 暗号電文・ジャミング・305 ローマ字電文も資料1を使う**。305 は読めた語がそのまま色名になるため、
**色の列は使わない**(符号→文字の変換だけに使う)。

### 2.1.1 資料を分けない理由

符号表(文字↔モールス)と色対応を**別の資料に分けない**。203 のプレイヤーは
「`・－` を引いて A、その A の色は赤」と**同じ行を2回引く**ため、
同じ行に色が並んでいれば視線移動が要らない。分けると無線で急かされながら
2つの表を往復することになり、難度が「見つけにくさ」ではなく
「探す手間」で上がる。

### 2.2 印刷内容(この表をそのまま印刷する)

A-Z の全26文字を印刷する。色は**5色の循環割当**
(A=赤, B=黄, C=緑, D=青, E=白, F=赤, G=黄, …)。

**数字は印刷しない。** モールスの出題は英字1文字のみに揃えたため
(ADR N-41)、実装が出題するのは A-Z だけになった。

| B | `－・・・` | BRAVO | 黄 |

### 2.3 レイアウトの要件

- **色は文字ごとに色面(塗り)で示す**。行全体を塗ると見やすい。
- フォネティックコード列は**あってもなくても成立する**が、あると
  プレイヤーが「ゴルフ」と語で報告でき、無線のやり取りが自然になる
  (ナビゲーターは語での報告・1文字ずつの報告のどちらも受け付ける)。
- 短点・長点は**視覚的に長さの差が明確**になるよう描く
  (`・` と `－` の記号、または実際の長短のバー)。
- 26行は多いので、**2列組**(A-M / N-Z)にすると1枚に収まりやすい。

### 2.4 実際に出題される語

実装が出題する候補は以下の15語(各色3語)。**表は全26文字を印刷する**が、
出題されるのはこの範囲であることを制作時の確認に使う。

| 頭文字の色 | 出題される語 |
|---|---|
| 赤 | ALFA, KILO, PAPA |
| 黄 | BRAVO, GOLF, LIMA |
| 緑 | MIKE, HOTEL, ROMEO |
| 青 | DELTA, INDIA, XRAY |
| 白 | ECHO, TANGO, OSCAR |

候補語を増減する場合は
`app/game-server/scenarios/stages/203_angou_denbun.toml` を編集する。
無効化中の `304_angou_denbun_hard.toml.disabled` も同じ候補語を持つため、
**304 を復活させるときは両方を揃える**。
**各色に最低1語は残す**こと(どの色が残っていても出題できる必要がある。
`puzzle_stage_ideas.md` §5)。

### 2.5 表示タイミング(参考)

デバイスは ITU 標準タイミングでモールスを表示する
(`game_session_design.md` §6.1)。単位長は300ms。

| 要素 | 長さ |
|---|---|
| 短点 | 1単位(300ms)点灯 |
| 長点 | 3単位(900ms)点灯 |
| 符号内の要素間 | 1単位 消灯 |
| 文字間 | 3単位 消灯 |
| 語の繰り返し前 | 7単位 消灯 |

プレイヤーには「長い消灯が語の切れ目」と読めるため、対照表に
**「長く消えたら最初から」**の注記を入れると親切。

### 2.6 数字は印刷しない

かつて数字1桁をモールス表示する案があり数字欄を検討したが、
**モールスの数字は全て5要素**で (1 = `・－－－－` / 2 = `・・－－－`)、
長短を数え違えると隣の数字になる。302 は**英字1文字**の表示に変更したため
(ADR N-41)、実装が出題するのは A-Z だけになった。

数字を印刷すると紙面を圧迫し、解読中に英字と紛れる。**載せないこと。**

## 3. 資料2 — 暗号チェーン (301 LED照合)

### 3.1 用途

ランプの点灯パターンを**3段階で読み解き**、ダイヤル位置と切る線の両方を出す。

```
ランプ4つの点灯/消灯 → 変換表でキーワード         (例 INDEX)
キーワードの頭文字   → デコード表でダイヤル位置   (I → 1)
キーワードの末尾文字 → デコード表で基準色         (X → 緑)
基準色 + ランプの状態 → 分岐表で切る線が決まる     (緑・白点灯 → 緑)
```

**4段階すべてが資料2 の中で完結する**。301 が見る紙は資料2 だけで、
資料3(回路図)は **203 ブループリント専用**。

**3つの表を同じ資料番号(資料2)にまとめる**。301 は必ず順にたどるため、
一部だけ見る場面が無い。番号を分けるとナビゲーターが段階ごとに
番号を言い直すことになり、**同じ紙の中の視線移動なのに
「別の紙を探せ」と聞こえる**(§3.5)。

**赤のランプは常時消灯のダミー**で、パターンには含めない。
残る4つ(黄・緑・青・白)の点灯/消灯が4bit = 16通りになるが、
**全消灯だけは使わない** — ランプが1つも点かない状態は故障と見分けがつかず、
プレイヤーが「装置が壊れた」と報告して止まる。資料2 には**15通り**を載せる。

対照表は `app/game-server/scenario_codebook.go` に1箇所だけ置く。
**紙とサーバーが食い違うとプレイヤーが理不尽に失敗する**ため、
`scenario_codebook_test.go` がデコード表・分岐表の手順を再現して突き合わせている。

### 3.2 変換表(ランプの並び → キーワード)

**ランプの色名を見出しにする**。位置(左から2番目…)で書かない —
プレイヤーはセーフティーグラス着用・立ったまま参照するため、
数え間違いが起きる。色なら見た瞬間に対応がつく。

●=点灯 / ○=消灯。**赤は載せない**(常時消灯のダミー)。

| 黄 | 緑 | 青 | 白 | キーワード |
|:--:|:--:|:--:|:--:|---|
| ○ | ○ | ○ | ● | **ZONE** |
| ○ | ○ | ● | ○ | **BOMB** |
| ○ | ○ | ● | ● | **LEAD** |
| ○ | ● | ○ | ○ | **PROBE** |
| ○ | ● | ○ | ● | **BOARD** |
| ○ | ● | ● | ○ | **XENON** |
| ○ | ● | ● | ● | **WAVE** |
| ● | ○ | ○ | ○ | **ZERO** |
| ● | ○ | ○ | ● | **MODULE** |
| ● | ○ | ● | ○ | **QUIET** |
| ● | ○ | ● | ● | **INDEX** |
| ● | ● | ○ | ○ | **HANDLE** |
| ● | ● | ○ | ● | **LEVER** |
| ● | ● | ● | ○ | **SENSOR** |
| ● | ● | ● | ● | **INPUT** |

- 見出しの色は**色面と色名を併記**する(§1.1)。白は枠線付きで示す。
- 行の並びは上の順(2進の昇順)を保つ。**目で追って探す表**なので、
  並びを崩すと探索時間がカウントダウンを圧迫する。

### 3.3 デコード表(頭文字・末尾文字)

キーワードの**頭文字**からダイヤル位置を、**末尾文字**から基準色を引く。
**変換表と同じ資料2 の中に、罫線で区切って並べる**(§3.5)。

**頭文字 → ダイヤル位置**

| 文字 | ダイヤル |
|---|:--:|
| A〜E | **0** |
| F〜I | **1** |
| J〜M | **2** |
| N〜Q | **3** |
| R〜U | **4** |
| V〜Z | **5** |

**ロータリーは0-5の6接点**(`game_session_design.md` §3)。
区間を 5・4・4・4・4・5 に割って26文字を6つへ収めてある。
**区間を等分(5文字ずつ)にすると Z が6番目にはみ出し**、
物理的に合わせられない位置が出るため、この割り方を崩さないこと。

**末尾文字 → 基準色**

| 文字 | 基準色 |
|---|---|
| A・F・K・P・U・Z | **赤** |
| B・G・L・Q・V | **青** |
| C・H・M・R・W | **黄** |
| D・I・N・S・X | **緑** |
| E・J・O・T・Y | **白** |

A から5色を循環で割り当てる(資料1 のモールス対照表と**同じ割り当て方**)。
並びを揃えてあるので、資料1 に慣れたプレイヤーはそのまま読める。

### 3.4 分岐表(基準色 → 切る線)

基準色が出たら、**ランプの状態でもう一段分岐**して切る線が確定する。
**変換表・デコード表と同じ資料2 の中に置く**(§3.5)。

**回路図(資料3)へ載せてはいけない。** 資料3 は 203 ブループリントが
「端子番号だけを頼りに色を引く」ための紙で、203 の原則は
**シートだけが手がかり・ナビは色を言わない**(§4.1)。そこへ 301 用の
**色の分岐表**を同居させると、203 のプレイヤーの視界に色対応が入る。

| 基準色 | 見るランプ | 点灯していれば | 消灯していれば |
|---|---|---|---|
| 白 / 黄 | **緑のランプ** | 基準色のまま | **青** |
| 赤 / 青 / 緑 | **白のランプ** | 基準色のまま | **赤** |

- **「LED3」「LED5」と位置で書かない**。実機のランプは色で識別するため、
  位置番号を持ち込むと数え直しが要る(§3.2 と同じ理由)。
- この分岐があるおかげで、末尾文字が同じキーワードでも切る線が変わる。
  資料2 の15通りが**5色すべてに最低2通りずつ**割り当たるよう語を選んである
  (対応が1通りしか無い色があると、その色が正解の回は毎回同じ表示になる)。

### 3.5 資料番号の印刷

| 資料番号 | 内容 | 301 での使われ方 |
|---|---|---|
| **資料2** | **変換表**(ランプの並び → キーワード)<br>**デコード表**(頭文字・末尾文字)<br>**分岐表**(基準色 → 切る線) | この順に3つとも引く |
| 資料3 | 回路図 | **301 では使わない**(203 ブループリント専用) |

**資料2 の中に表が3つ並ぶ**。番号は**資料の枠に1つだけ**印刷し、
中の3つには「変換表」「デコード表」「分岐表」と**見出しだけ**を付ける
(見出しに番号を振らない — 番号があるとナビが言い直すべきかどうか曖昧になる)。

- 番号は**離れた位置から読める大きさ**にする。無線で「資料2」と言われた
  プレイヤーが即座に視線を移せることが目的。
- 呼称はサーバー設定から引く(§7)。301 のステージ定義が参照するのは
  `${sheet_codebook}` **だけ**(ADR D-2)。
- 3つの表は**罫線で区切る**が、**枠は分けない**。同じ資料の中にあることが
  見て分かる状態を保つ。離すと「資料2 はどれだ」と迷う。
- ナビゲーターは**2つ目以降で番号を言い直さない**。「同じ資料2 の次の表で」
  と案内する。番号を繰り返すと**別の紙を探しに行く**。
- **並びは引く順(変換表 → デコード表 → 分岐表)**にする。

### 3.6 サーバー設定との連動

**このステージに実測値の登録は要らない**。対照表は**抽選に関わらず固定**で、
刷り直しても値が変わらないため `scenario_codebook.go` に持たせてある
(設定に出すと紙・設定・実装の3箇所が食い違いうる)。
連動するのは**資料の呼称だけ**(§7)。

### 3.7 刷り直し時のチェックリスト

1. 資料2 の変換表15行が `scenario_codebook.go` の `codebookTable` と一致しているか
2. 資料2 のデコード表の区間・色割当が `scenario_codebook_test.go` の
   `letterRanges` / `letterColors` と一致しているか
3. 資料2 の分岐表が §3.4 のとおりか
4. **資料番号を変えたなら `[mission_sheet.documents]` も更新する**(§7)
5. `go test -run TestCodebook` が通ること
6. サーバーを再起動する(設定は起動時に読む)

## 4. 資料3 — 回路図 (203 ブループリント)

### 4.1 用途

ナビゲーターが**色を言わず端子番号だけ**を指示する。
プレイヤーは資料3で端子番号→配線色を引く。

**端子は2系統ある**(X1〜X5 / Y1〜Y5)。どちらを使うかは
**Core 外装のシリアル銘板の下1桁**で決まる(奇数=X / 偶数=Y。§5)。

ナビゲーターは**両系統を並べて**言う:

> 「シリアル銘板の下1桁が**奇数ならX4、偶数ならY2**の線を切れ」

**サーバーは個体のシリアルを知らない**ため、必ず両方を伝える。
どちらを使うかを選ぶのは**プレイヤーの仕事**で、そこがこのステージの
工程のひとつになっている。

**資料番号(資料3)と端子番号の数字が重なる**が、端子には X/Y の
プレフィックスが付くため紛れない(「資料3」と「X3」)。

### 4.2 印刷内容の要件

- **整備マニュアル風の回路図**として、端子番号と配線色の対応を描く。
- **X系統(X1〜X5)と Y系統(Y1〜Y5)の両方**を描く。**合計10端子**。
- 表形式で直接書くより、**回路図の中に端子記号と色を配置**する方が世界観に合う。
- 各系統5端子すべてを記載する(どの色が正解になってもよいように)。
- **X と Y は視覚的に分離**する(別の回路ブロックとして描く、罫線で区切るなど)。
  取り違えると即爆発するため、どちらを見ているかが一目で分かる必要がある。
- **「奇数=X / 偶数=Y」は紙に印刷しない**。対応はナビゲーターが毎回言う
  (§4.1)。紙に書くと、プレイヤーがナビへ確認せずに進められてしまい、
  交信の往復が減る。

### 4.3 端子と色の対応(現在の設定)

| X系統(銘板の下1桁が**奇数**) | 配線色 | | Y系統(**偶数**) | 配線色 |
|---|---|---|---|---|
| X1 | 赤 | | Y1 | 緑 |
| X2 | 黄 | | Y2 | 白 |
| X3 | 緑 | | Y3 | 赤 |
| X4 | 青 | | Y4 | 黄 |
| X5 | 白 | | Y5 | 青 |

対応を変える場合は `config.toml` を同じ内容に更新する。

```toml
# 銘板の下1桁が奇数の個体
[mission_sheet.terminal_map_x]
X1 = "A"  # 赤
X2 = "B"  # 黄
X3 = "C"  # 緑
X4 = "D"  # 青
X5 = "E"  # 白

# 銘板の下1桁が偶数の個体 (X とは別の対応)
[mission_sheet.terminal_map_y]
Y1 = "C"  # 緑
Y2 = "E"  # 白
Y3 = "A"  # 赤
Y4 = "B"  # 黄
Y5 = "D"  # 青
```

- **両系統に5色すべてを登録すること**。登録漏れがあると、その色が正解に
  なったセッション**だけ**が組み立てに失敗する(抽選次第でしか再現しない)。
  そのため**起動時に検査して落とす**。
- **X と Y は完全に別の対応にする**。一部でも同じ番号に揃えると、系統を
  取り違えても偶然当たり、銘板を見る意味が薄れる。
  **全部が一致していたら起動時に落ちる**。

> 回帰: `TestBlueprintOffersBothTerminalSeries` / `TestTerminalMapsValidate`

## 4b. 資料4 — ロータリー対照表 (209 配電盤照合)

### 4b.1 用途

ロータリーを回すたびにランプの光り方が変わる。**今の見え方から現在位置を
割り出し**、同じ行の**危険位置**と**解除位置**を読む。

```
プレイヤー 「赤が点いて青が点滅しています」
ナビ       「ロータリーが0番にありませんか」
プレイヤー 「はい、そうです」
ナビ       「では手元の資料4を見てくれ。解除方法が書いてある」
```

### 4b.2 印刷内容

**「点灯色 + 点滅色」の組が現在位置を一意に示す**。6行で全位置を覆う。

| 点灯 | 点滅 | 現在位置 | 危険位置 | 解除位置 |
|:--:|:--:|:--:|:--:|:--:|
| 黄 | 赤 | **0** | 4 | 5 |
| 赤 | 青 | **1** | 4 | 5 |
| 白 | 黄 | **2** | 3 | 4 |
| 赤 | 緑 | **3** | 1 | 0 |
| 青 | 赤 | **4** | 3 | 1 |
| 黄 | 白 | **5** | 2 | 0 |

**危険位置は必ず現在位置と解除位置の「間」にある。** 解除位置へ向かうと
**必ず危険位置を通過する**ので、「止まらずに通り抜ける」操作が毎回発生する。

**別枠で1行**(表の外に大きく):

> **赤いランプだけが点いているときは、危険位置に止まっている。**
> すぐに別の位置へ回すこと。

### 4b.3 設計上の決まり

- **解除位置での見え方は載せない。** 載せると「解除位置は3 → その行の
  点滅色が答え」と**回す前に切る線が分かってしまい**、回す工程が消える。
  解除位置では切る線だけが点滅するので、回せば装置に現れる。
- **赤の単独点灯は危険位置に予約する。** 表の行はすべて点灯+点滅の2色なので、
  1色だけの表示は必ずこの意味になる。ダミー表示も2〜3色にしてある。
- 見え方は**6通りとも重複させない**。重複すると現在位置を特定できない
  (起動時に検査して落とす)。
- **危険位置は経路の内側に置く**。外にあると素通りでき、
  「止まらずに通り抜ける」という 209 の緊張が消える(起動時に検査する)。
- 色は**色面と色名を併記**する(§1.1)。白は枠線付きで示す。

### 4b.4 サーバー設定との連動

**実測値の登録は要らない。** 対照表は抽選に関わらず固定のため、値は
`app/game-server/scenario_panel.go` の `panelTable` に持たせてある。
連動するのは**資料の呼称だけ**(§7)。

### 4b.5 刷り直し時のチェックリスト

1. 6行が `scenario_panel.go` の `panelTable` と一致しているか
2. 「赤だけ点灯 = 危険位置」の別枠が入っているか
3. **資料番号を変えたなら `[mission_sheet.documents]` も更新する**(§7)
4. `go test -run TestPanel` が通ること

## 5. シリアル銘板 (CoreID記載。資料番号なし)

Core 本体に貼る**1枚の銘板**。**運営とプレイヤーの両方が読む**。

### 5.1 用途

| # | 用途 | 読む人 | 使う部分 |
|---|---|---|---|
| 1 | **音声申告**: 「CoreID 3701 難易度ノーマルで開始してください」(`operation_flow.md` §3) | マネージャー | 番号全体 |
| 2 | **リセット時の対象特定**: 音声コマンドで対象を指定(誤認識は bind 済みIDで補正) | マネージャー | 番号全体 |
| 3 | **複数台運用時の宛先**。IDが重複すると別個体へ指示が飛ぶ(§5.3) | 運営 | 番号全体 |
| 4 | **203 ブループリントの端子系統の選択**(ADR D-6) | **プレイヤー** | **下1桁** |

用途4だけがプレイヤー向けで、**下1桁の奇数/偶数**が資料3のどちらの端子系統を
読むかを決める(奇数=X系統 / 偶数=Y系統)。

ナビゲーターは「シリアル銘板の下1桁が奇数ならX4、偶数ならY2の線を切れ」と
**両系統を並べて**言い、プレイヤーが銘板を見て**自分で選ぶ**。
**サーバーは個体のシリアルを知らない**ため、この判断は完全にプレイヤー側にある。

### 5.1.1 呼び分け(同じ銘板を2つの名前で呼ぶ)

| 場面 | 呼び方 | 理由 |
|---|---|---|
| ナビゲーター → プレイヤー | 「**シリアル銘板**」 | プレイヤーは「CoreID」という運営用語を知らない |
| マネージャー・運営 | 「**CoreID**」 | `operation_flow.md` の既存表現 |

**同じものを指している。** 運営がこれを理解していれば混乱しない。
制作時に印字を `SN-3701` にするか `CoreID 3701` にするかは、
どちらでも成立する(前者なら世界観寄り、後者なら運営が迷わない)。

### 5.2 要件

| 項目 | 要件 |
|---|---|
| 桁数 | **数字4桁**(音声認識で扱いやすくするため。`bridge_connection_design.md` §5) |
| 設置 | Core本体の見やすい位置。**プレイ中に隠れない場所**に貼る |
| 視認性 | マネージャーが離れた位置からでも読める大きさ |
| **下1桁の視認性** | **読み違えられないこと**。3と8、0と6などが紛れる書体を避ける(203 ブループリントで系統を決めるため、読み違えると即爆発する) |

### 5.3 ファームウェアとの一致(必須)

銘板の番号は、その個体のファームウェアに書き込んだ ID と一致させる。

```
idf.py menuconfig → Core System Configuration → Device ID (CoreID)
```

(`sdkconfig` の `CONFIG_CORE_SYSTEM_DEVICE_ID`)

**複数台を運用する場合、IDが重複すると別の個体へ指示が飛ぶ**。
台数分の銘板とファームを組で管理すること。

### 5.4 採番ルール — 奇数と偶数を混ぜる

**CoreID の下1桁が 203 ブループリントの端子系統を決める**ため、採番時に配分を意識する。

- **奇数と偶数を混ぜて振る**。連番なら自然に混ざるが、台数が少ない場合は
  意識して配分する(全台が奇数だと Y系統が一度も使われない)。
- **CoreID を変更すると、その個体の 203 ブループリントの挙動が変わる**。ファーム書き換えで
  IDを振り直すときは、系統が変わることを意識する。

## 7. 資料番号のサーバー設定

呼称は `config.toml` に登録する。ナビゲーターが**無線で読み上げる名前**であり、
ステージ定義は `${sheet_morse}` のように参照する。

```toml
[mission_sheet.documents]
morse    = "資料1"   # モールス対照表 (202/302/305)
codebook = "資料2"   # 変換表 + デコード表 + 分岐表 (202)
circuit  = "資料3"   # 回路図 (203)
panel    = "資料4"   # ロータリー対照表 (209)
```

| 設定キー | 参照する変数 | 使うステージ |
|---|---|---|
| `morse` | `${sheet_morse}` | 202, 302, 305 |
| `codebook` | `${sheet_codebook}` | 202(3つの表とも) |
| `circuit` | `${sheet_circuit}` | 203 |
| `panel` | `${sheet_panel}` | 209 |

- **3件すべて必須**。空のままだと `${sheet_morse}` が空文字に展開され、
  「を使って解読しろ」という意味の通らない発話になるため、
  **サーバーは起動時に落ちる**。
- 資料番号は**ナビゲーター知識にだけ**入る。Core向けJSONには含めない
  (デバイスは紙資料の存在を知る必要がない)。
- 202 は**資料2 だけで完結する**(変換表 → デコード表 → 分岐表)。
  引く呼称は `${sheet_codebook}` の1つで、**`${sheet_circuit}` は使わない**(ADR D-9)。
  ステージ定義に「資料2」と直書きしない — 番号を振り直したときに食い違う(ADR D-2)。
  `TestNavigatorTextHasNoHardcodedDocumentNumber` が文面を毎回検査している。

## 決定記録

| # | 決定 | 理由 |
|---|---|---|
| 1 | 独立して参照される要素ごとに**資料番号**を振る(資料1〜資料3) | ナビゲーターが「モールス対照表」「回路図シート」と説明的に呼んでいたため発話が伸び、無線越しではどこを見るのか伝わりにくかった。「手元の資料1を見ろ」なら一言で指せる |
| 2 | **番号は物理的な紙の枚数ではなく参照単位**で振る | 「参照単位」は**引く回数ではなく、片方だけ見る場面があるか**で決まる。301 LED照合 の変換表とデコード表は必ず順にたどるので1番号(決定26)。逆に 202・302・305 のように**複数ステージが同じ資料1を見る**関係もあるため、ステージ番号とは別体系にする必要がある |
| 3 | **面(表裏)は資料番号に含めず、ナビゲーターも指示しない** | 面を言うと印刷レイアウトを変えるたびにサーバー設定と文面の更新が要る。資料の差し替えに弱くなる。探す手間もプレイヤーの遊びのうちと位置づける |
| 4 | 呼称に**フォネティックコードを使わない**(却下案) | 資料1がモールス対照表そのものなので、「資料アルファ」がSTTに乗ると**資料名か解読した語か区別できない**。配線色の内部記号 A-E とも衝突する |
| 5 | 資料番号と端子番号 T1〜T5 の**数字の重なりは許容**する | 「資料3を見ろ」と「端子T2の線を切れ」は別の発話に分かれる。資料番号を10番台にする案 (資料11〜14) も検討したが、端子記号を別の仕組みへ変更する予定があるため衝突自体が解消する見込み |
| 6 | 資料1を**符号表と色対応に分けない** | 203 のプレイヤーは「`・－` を引いて A、その A の色は赤」と**同じ行を2回引く**。同じ行に色が並んでいれば視線移動が要らない。分けると2つの表を往復することになり、難度が「見つけにくさ」ではなく「探す手間」で上がる |
| 7 | ナビゲーターは**初出で資料番号と中身をひとまとまりで言う** | どの資料に何が載っているかは**装置を見ても分からない情報**で、伏せると番号だけ言われたプレイヤーが探しようがない (ADR N-4)。2回目以降は番号だけでよい |
| 8 | 呼称は `config.toml` の `[mission_sheet.documents]` に持ち、ステージ定義は `${sheet_*}` で参照する | 資料番号は「印刷物の実測値」そのもので、`symbol_count` や `terminal_map` と同じ性質 (ADR D-1)。toml 各所に直書きすると、番号を振り直したとき全ステージを grep して直すことになる |
| 9 | 資料名は**ナビゲーター知識にだけ**入れ、Core向けJSONには含めない | デバイスは紙資料の存在を知る必要がない。サーバーが決めデバイスが自律実行する責務分割を保つ |
| 10 | 呼称が空なら**起動時に落とす** | 空文字に展開されると「を使って解読しろ」という意味の通らない発話になり、プレイ中に初めて気づくことになる。`terminal_map` の5色必須と同じ性質 |
| 11 | 資料1に**数字を載せない** | 数字をモールス表示する案があり数字欄を検討したが、**モールスの数字は全て5要素**で長短を数え違えると隣の数字になる。**出題を英字のみに揃えた**(ADR N-41)ため A-Z だけでよい。数字は紙面を圧迫し、解読中に英字と紛れる |
| 12 | 紙は**A4横・裏表1枚**にまとめる | 枚数を増やすとプレイ中に紙を取り違える事故が起きる |
| 13 | 205 の端子を**X/Y の2系統**にし、**シリアル銘板の下1桁**(奇数=X / 偶数=Y)で選ばせる | 205 は「資料を読んで自分で引く」のが謎の全部だったが、工程が1本道だった。系統の選択が入ると、**銘板を見て自分で判断する**工程が1つ増える。難度の上がり幅は小さい(解読も計算も伴わない)ため normal に据え置く |
| 14 | ナビゲーターは**両系統を並べて**言う(「奇数ならX4、偶数ならY2」) | **サーバーは個体のシリアルを知らない**ため片方に絞れない。加えて、絞って言うと選択の主体がナビへ移り、増やしたかった工程が消える。`ScenarioBuilder` へ device_id を通す実装も不要になり、実装が軽い |
| 15 | 「奇数=X / 偶数=Y」の対応は**紙に印刷しない** | 紙に書くとプレイヤーがナビへ確認せずに進められ、交信の往復が減る。対応はナビが毎回言う |
| 16 | X と Y は**完全に別の対応**にする | 一部でも揃えると系統を取り違えても偶然当たり、銘板を見る意味が薄れる。全一致は起動時に落とす |
