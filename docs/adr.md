## 1. アーキテクチャ

### A-1. 周辺機器がすべてサーバーへダイヤルインする

radio-bridge は gRPC **クライアント**として game-server へ接続する。
サーバーは周辺機器のアドレスを一切持たず、確立済みのストリーム自体を返信路として
`map[bridge_id] → 送信チャネル` のレジストリ経由で返す。

bridge を増やしてもサーバー設定の変更は不要。core-system の WebSocket 接続と
同じパターンに統一してある。

> 出典: BR 決定1・2・3

### A-2. サーバーが決め、デバイスが自律実行する

サーバーがシナリオ(セッションJSON、**正解を含む**)を組み立てて送り、
Core は受信後 **Wi-Fi が切れても単体でゲームを完遂**する。
Core は進行イベントをサーバーへ通知し、それがナビゲーター演出のトリガーになる。

謎解きの内容は完全にサーバー側コンテンツの責務で、**謎の差し替えに
ファーム書き換えは不要**。

> 出典: GS 決定1

### A-3. `/ws` は1エンドポイントに相乗りする

トランシーバーと core-system が同じ `/ws` を使う。接続種別は**最初のメッセージ**で
判定する(`login` → トランシーバー、`device_status` → core-system)。

> 出典: GS 決定9・決定23

### A-4. 外部ファイルで差し替えられるものは再ビルド不要

ステージ定義・難易度テンプレート・プロンプト・キャラクター定義は TOML に分離してある。
編集してサーバーを再起動すれば反映される(compose で bind mount 済み)。

口調やプロンプトは実機で試しながら繰り返し調整する性質のものなので、
再ビルドなしで差し替えられる方が運用しやすい。キャラクターは**1人1ファイル**、
ステージも**1ステージ1ファイル**とし、追加・差し替えをファイル操作で行えるようにした。

保留中のステージは `.toml.disabled` にしておけば置いたまま無効化できる。

> 出典: NV 決定10 / SC 決定1

### A-5. 永続化は Valkey、接続できなければメモリへフォールバック

セッション状態・会話ログ・スコアは Valkey に永続化する(ランキング機能はなし)。
接続できない場合は**メモリ実装へフォールバック**して起動を続行する。

会話ログと進行イベントは**1本のタイムライン**に統合して保存する。

> 出典: GS 決定15・決定21 / SC 決定8

## 2. シナリオ組み立て

### S-1. 正解は同一の抽選結果から機械的に生成する

Core向けJSONとナビゲーター知識は**同一の抽選結果から同時生成**する。
食い違うとプレイヤーが理不尽に失敗するため、`scenario_validate.go` が
「`answer` が `cut` の色に言及しているか」を組み立てのたびに検証する。

**別々に人手で書く運用にしてはいけない。**

> 出典: SC 決定2・決定7

### S-2. 切断線は必ず1本以上余らせる

配線は5本だが1セッション最大4ステージ (`maxStagesPerSession`)。
全色を使い切ると抽選の余地が消え、切る色が構造的に決まるステージ
(202 暗号電文 = 語の頭文字 → 対照表の色)が組み立て不能になる。
203 の候補語は全5色分を揃えてある。

> 出典: SC 決定5

### S-2b. 誤切断は難易度を問わず即爆発

誤切断は**常に即座に爆発**する。チュートリアルの 101 も例外にしない。
**設定項目 `on_wrong_cut` そのものを廃止した** — デバイスはパースせず、
ステージ定義にも書かない。

**切った線は物理的に戻せない。** ペナルティで続行させると、後続ステージが
その色を使う場合に組み立てが破綻する — 配線5本に対し1セッション最大4ステージで、
S-2 のとおり余裕が無い。

かつて 101 だけ「チュートリアルなので爆発させない」と 30秒ペナルティに
していたが、失敗の重さは難易度で変えない方針に統一した。
項目を残すと「書いてあるのに効かない設定」になり事故のもとなので、
分岐ごと削除した。`TestNoOnWrongCutInStages` が `.toml.disabled` も含めて固定する。

なお**ボタン・ダイヤルのミスは別**。こちらは `penalty` でよい
(204 色合わせ の誤押下 5秒、201 復唱 のボタン列 5秒)。押し間違いは取り返しがつく。

> 出典: GS 決定27

### S-3. ナビゲーター知識に固定値を書かない

ステージTOMLの `[navigator]` (briefing / answer / procedure / hint_*) に
数値や色を直接書くと、抽選値と衝突して**指示が自己矛盾する**。

手順に出る値は `[random]` の変数にして、衝突しうる値を `exclude` で外す。

> 回帰: `TestTutorialProcedureUsesDrawnPath`
> 出典: NV 決定19 (101 の実例)

### S-4. 読み上げてよい色名に正解色を混ぜない

ボタン列を読み上げるステージ (103/201) で押下色と `cut` を独立に抽選すると
**列に正解色が入る**(実測で 65%・49%)。
第一声で正解色を音にしてしまい、後段の「その色の線を切れ」と繋がった瞬間に答えが割れる。

押下色は必ず `exclude = ["${cut}"]` で分離する
(102 ホールド&カット が `hold` と `cut` を分けているのと同じ理由)。

> 出典: NV 決定27 (a)

### S-5. `cut` が謎の答えとして導けないステージは置かない

新しいステージを足すときは **`cut` が謎の答えとして導けるか**を先に見る。
導けないなら色は別途伝えるしかなく、その伝達は謎にならない
(ナビゲーターが色を告げるだけの工程が謎の隣に居座る)。

この基準に外れるステージは置かない。

> 出典: NV 決定30

### S-6. 全ステージに報告できる表示を置く

体験の軸は「プレイヤーがLEDの状態を報告 → ナビゲーターが解除方法を伝える」。
表示のないステージはこの軸が成立しない。

> 出典: SC 決定14

### S-7. 動く正解は「読んで・操作して・切る」が終わる長さにする

`timer_digit` のように**正解が時間で変わる**ステージは、条件が成立している
窓の長さを**プレイヤーの動作時間で**見積もる。

プレイヤーは窓の中で次を全部終える必要がある:

    タイマーを読む → 計算する → ダイヤルを回す → 線を切る

しかも**セーフティーグラス着用・立ったまま・無線で急かされている**。
窓が短いと、当たるのは実力ではなく偶然になる。

| 対象の桁 | 同じ値でいる時間 | 判定 |
|---|---|---|
| 秒の**一の位** | **1秒**(+猶予1秒) | **短すぎる**。使わない |
| 秒の**十の位** | **10秒**(+猶予1秒) | 成立する(302 が使用) |

**桁を細かくすると難度ではなく運になる。** 一の位を使うと、ノーマルでも
**ハードの 303 追いかけダイヤル(十の位)より厳しい**という逆転が起きる。

あわせて、**足す数が固定オフセットにしかならない形は難度にならない**。
一度覚えれば以降ずっと同じズレになり、暗算するのは最初の1回だけになる
(S-5 と同じく「謎の隣に残る工程」)。

> 出典: 実装 2026-08-24

### S-8. 難易度は `difficulty` タグが正本。IDの番号帯ではない

**2026-08-24 の振り直し (S-9) で両者は一致させた**が、
**正本はあくまで `difficulty` タグ**。難易度を見直せばまたずれる。
判定が要る場面ではタグを見ること。

2026-08-24 の見直しで、**表示色数と工程数**で全ステージを並べたところ
**ノーマルが重くハードが軽い**逆転が見つかり、次を入れ替えた:

| ステージ | 変更 | 理由 |
|---|---|---|
| 301 LED照合 | normal → **hard** | 資料2の3表 + ダイヤルで工程が4段。全ステージ中最長 |
| 208 ジャストカット | hard → **normal** | 観察も推理も無く条件が単発。ハードで最も軽かった |

**この見直しの直後に ID を振り直し、帯とタグを一致させた** (S-9)。
振り直しは追随箇所が多いので、運用が始まったら避けること。

**判定が要る場面では必ずタグを見る。** 「300番台だから hard」と書いた説明が
docs に複数あり、この見直しで全て誤りになった (実害は無かった — normal も
hard も `l4_pct = 0` のため。だが同じ書き方を再発させない)。

> 出典: PZ §2.5

### S-9. IDは難易度帯ごとに詰めて振る。無効化したら90番台へ退避

**ステージは 1xx / 2xx / 3xx に隙間なく詰める。**

    easy    101-104
    normal  201-208
    hard    301-305

**なぜ詰めるか** — 欠番が残ると「なぜ204だけ無いのか」を毎回調べ直すことになる。
**採用しないと決めたステージは削除して番号を詰め直す** — 残しておくと
現役かどうかの判断が毎回必要になる。経緯は git 履歴に残る。

**振り直しは影響範囲が広い**。2026-08-24 の実施では次を機械的に追随させた:

- ステージ定義のファイル名と `id = "..."` (両者は必ず一致させる)
- Go のテスト・シミュレーション台本の**文字列リテラル**としてのID
- docs とコード**コメント中のID**(決定記録も含む)
- 難易度テンプレートの `fixed_head` など**テンプレートからの参照**

**決定記録も含めて全て現在のIDへ揃える。対応表は残さない。**
「当時はこのIDだった」を併記すると、読む側が毎回どちらの体系かを
判断することになり、参照するたびに誤読の余地が生まれる。
**リポジトリ内のIDは常に1つの体系だけが存在する**状態を保つ。

**置換は「ID + ステージ名」を鍵に行う。裸の数字で置換しない。**
振り直しでIDが循環するため(旧203→202 / 旧202→301)、
途中の状態で別ステージに化ける。ファイル名は一時名を経由した
**2段階リネーム**で衝突を避ける。

検証は**ID と名前の対応**を総点検する(「202 暗号電文」のように
名前が併記された箇所を全ファイルから拾い、対応表と突き合わせる)。

セッションログが残っている場合は過去のIDと食い違うので、
**運用中の振り直しは避ける**こと。

> 回帰: `TestStageIDsFollowNumberingScheme` / `TestDifficultyPoolsHaveEnoughStages`
> 出典: 実装 2026-08-24

### S-10. 配置で難しさが変わるものは「配置ごと」抽選する

206 綱渡り の禁止位置は**難易度で数が変わる**
(イージー・ノーマル1つ / **ハード2つ**。`[load] forbidden_rotary_count`)。
**ハードは「普通×2」を引く**ため、normal タグのこのステージも
ハードのセッションに出て、そこで2つになる。

2つになると**配置によって難しさの質が変わる**:

| 型 | 例 | 何が難しいか |
|---|---|---|
| 隣接 | 禁止{1,2} → 目的4 | 連続通過。一気に回せば1回で抜ける |
| 離れている | 禁止{1,3} → 目的5 | 間の安全地帯で一度止まれる。**2段構え** |
| 目的地を挟む | 禁止{1,5} → 目的3 | **行き過ぎると危険**。止める精度が要る |

**位置を個別に抽選しない。`pick = "rotary_layout"` で配置ごと引く。**
個別に引くと型が偏るうえ、**目的位置の両隣が禁止**になる組み合わせが出る。
到達はできるが、合わせたあと手が滑って1つ動かすと即爆発する —
難度ではなく運になる。**成立する配置だけを列挙して等確率で引く**。

数が可変のリストは `derive = "tail"` で渡す。`nth` で1つずつ取り出すと
**要素数が減ったときに範囲外**になる。

**ナビゲーターは危険位置を全て伝える。** 1つでも伏せると知りようがないまま
踏んで即爆発する。読み上げは「3と5」と区切る — カンマのままだと TTS が
小数や記号として読み、**聞き間違いが直接事故になる**
(`spokenNumberList` が変換する。Core向けJSONは整数の配列のまま)。

> 回帰: `TestForbiddenRotaryCountFollowsDifficulty` /
> `TestForbiddenRotaryCoversAllLayouts`
> 出典: 実装 2026-08-24

### S-11. 列の長さは難易度から引く。`entries` を直接書かない

201 復唱 のボタン列は**難易度で長さが変わる**
(イージー・ノーマル5個 / **ハード8個**。`[load] push_seq_len`)。
**ハードは「普通×2」を引く**ため、normal タグのこのステージも
ハードのセッションに出て、そこで8個になる。

**`precondition.push_seq.entries` を TOML へ直接書かない。**
`p1`〜`p5` のように変数を並べる形は**個数が固定**され、8個へ伸ばせない。
代わりに `colors = "${seq}"`(カンマ区切りの色列)で書くと、
各色が `{ push = "<色>" }` の1エントリへ展開される。

列は `pick = "color_seq"` で引く。**`colors` とは別物**:

| | 重複 | 並び |
|---|---|---|
| `colors` | 不可(互いに異なる) | **ソートする**(表示用) |
| `color_seq` | **許す** | **引いた順のまま**(押す順) |

「赤赤黄黄赤」の繰り返しはこのステージの持ち味なので、重複を避けてはいけない。
ただし**同じ色の3連続は避ける** — 無線で「赤赤赤」と読み上げると
何個言われたか数えられず、**記憶ではなく聞き取りの問題**になる。

**8個を超えて伸ばさない。** 記憶ではなく「読み上げを何度も聞き直す」
時間になり、無線の往復が増えるだけで謎が難しくなるわけではない。

> 回帰: `TestPushSeqLenFollowsDifficulty` / `TestPushSeqLenIsHarderOnHard`
> 出典: 実装 2026-08-24

### S-12. 点滅の見分けにくさは「隣接比」で決める

**点滅速度の差は倍率で考える。** 絶対値ではなく**隣の段階との比**が
見分けやすさを決める。

| ステージ | 速度 | 隣接比 |
|---|---|---|
| 104 早い者勝ち (easy) | 150 / 300ms | **2.0倍** |
| 205 速さくらべ (normal) | 150 / 300 / 550 / 1000ms | 1.82〜2.0倍 |
| 205 速さくらべ (**hard**) | 150 / 210 / 294 / 412ms | **1.4倍均一** |

**基準は 104 の 2.0倍** (2026-08-24 に 4.67倍から締めた)。
4.67倍は「片方がほぼ点きっぱなし」に見えて簡単すぎた。
2.0倍なら片方が「チカチカ」もう片方が「点滅」と質的に違って見える。

**2択なら 1.5倍が下限。** これを切ると両方とも 2.5Hz 以上の
「速い点滅」帯に入り、どちらも速く見えて差が読めない。

**並べ替えは下限を下回ってよい。** 205 のハードは 1.4倍で、104 の下限を
意図的に下回る。**4色を並べ替えるので比較回数が多く**、同じ隣接比でも
2択より難しいため。あわせて全体幅も 2.75倍まで詰まり、
**「一番遅いのが一目瞭然」が消える** (ノーマルの最遅 1000ms は 0.5Hz で
明らかに遅いが、ハードの最遅 412ms は 1.2Hz でまだ十分速い)。

速度は難易度テンプレートの `[load] speed_rank_ms` から引く。
**ステージ側に直書きしない** — 直書きすると難易度を跨いで同じになる。
**ハードは「普通×2」を引く**ため、normal タグの 205 もハードのセッションに
出て、そこで詰まった速度になる。

**実機で見え方を確認してから確定させること。** 詰めすぎると
並べ替えが実力ではなく運になる。数値は `[load]` の1行で変えられる。

> 回帰: `TestSpeedRanksFollowDifficulty` / `TestEasySpeedGapStaysReadable`
> 出典: 実装 2026-08-24

## 3. ナビゲーター — 情報の出し方

### N-1. 正解の色名は L4 未満でプロンプトに入れない

`answer` に色を書く運用は変えない(S-1 の検証に必要)。
**検証には必要だが、プロンプトへ入れる必要はない** — `BuildNavigatorPrompt` が
L4 未満で `redactCutColor` を通し、切る線の色だけを `◯◯色` に伏せる。

「書いてあるが言うな」は守られないことがある(指示を4経路ぶん足しても
616発話中1件残った)ため、**目の前に無い語は言えない**という形にした。

押すボタンの色は伏せない(伝えないと手順が成立しない)。

> 出典: NV 決定40

### N-2. 正解は「今は言うな」とセットで渡す

プロンプトには常に正解が入るので、禁止指示が離れた位置にあると生成AIが引きずられる。
`navigator_prompt.go` は L4 未満で**正解行の直後**に警告を併記する。

> 回帰: `TestHintPolicyBelowL4NeverEmbedsAnswer`
> 出典: NV 決定19

### N-3. `answer` は「照合の材料」として書く

**読み上げる文**として書いてはいけない。なぞられると成立してしまう文
(「プレイヤーが白色を報告してきたら復唱して〜」)は、L1-L2 でそのまま出ると
ナビゲーターから色名が漏れる。

「プレイヤーの報告が白色と一致するかを照合に使う」という**判定の指示**で書く。

> 出典: NV 決定20

### N-4. 装置に現れない情報はヒントレベルで出し惜しみしない

ボタンを押す順番 (103/201)・危険なダイヤル位置 (206 綱渡り) はナビゲーターしか知らず、
伏せるとプレイヤーが手詰まりになる。段階的に明かすのは**推理できる情報**だけ。

ヒント段階で調整するのは「**一度に何色まで言うか**」であって、言うか言わないかではない。
`hint_l1` に抽選変数を書いて必ず伝える。

**「伏せない」と「第一声で言う」は別の話。** `hint_l1` に書いた情報でも、
第一声に前倒しするのは**事故になる情報だけ** (N-49)。
ボタン列やダイヤルの数字は、**ランプの報告を受けてから**伝える。

`HintPolicyText` の共通文にも「**指針が優先**」と明記してある —
一般則だけだと生成AIがそちらを選び、色を伏せてしまう。

> 回帰: `TestUnobservableInfoRevealedAtL1`
> 出典: NV 決定22

### N-5. L4 でも色名を言えないステージがある

203 ブループリントは色を言うと資料3 (回路図) を読む工程が消えるため、L4 でも端子番号しか言えない
(端子は X/Y の2系統あり、**両方を並べて**言う。D-6)。
L4 は `answer` を「そのまま伝えてください」と埋め込むので、`answer` 側に但し書きを書き、
`navigator_hint.go` の L4 ブロックが「**但し書きが優先・但し書き自体は読み上げない**」
と補う。

> 回帰: `TestL4RespectsStageLevelRestriction`
> 出典: NV 決定20

### N-6. 禁止は独立した文にし、代替の言い方まで書く

「〜と手順を教えてよい(色は言わない)」のような**括弧書きの末尾**は読み落とされる。

独立した文にし、さらに「点灯しているランプは1つだけなので
『光っているランプと同じ色の線』と言えば伝わる」のように**代替の言い方**まで書く。
禁止だけ渡すと元の表現に戻る。

#### 断り方は「知らない」と「言わない」を区別する

203 ブループリント で色を求められたとき、
**『色は教えられないです』**と返した。これは**知っているのに伏せている**
ように聞こえ、プレイヤーに意地悪な印象を与える。

実際にはナビゲーターは回路図を持っておらず、**本当に分からない**。
『**分からない**』『こっちからは**見えない**』と、**知り得ない**ことを言う。
あわせて**資料を確認してもらうよう頼む** — 断って終わりにしない。

**例文は書かない** (N-29)。『こっちに資料3は無いんだ』のような例文を
2つ並べていたが、**先頭がそのまま読まれた**。
言い方の**性質**(知り得ない / 頼む / 突き放さない)だけを指定し、
文はキャラクターに任せる。

> 出典: NV 決定27 (b) / 実装 2026-08-25

### N-7. 分岐のある指針は両方の枝を書く

205 速さくらべ は「報告が正しければ確認して切らせてよい」とだけ書いており、
**誤報告への返し方が未定義**だったため「黄色だな、了解。赤と見比べろ」と
正解色を出して比較させた。

> 出典: NV 決定27

### N-8. プレイヤーが言っていない色を補わせない

「ランプが光っています」という色名を含まない報告に「光っているのは赤だな、了解」と
返すのは**復唱ではなく答えの提示**。共通ルール (`navigator/prompt.toml` の `role`) で
塞いである。

> 出典: NV 決定27 (d)

### N-9. 意味の通らない報告は復唱せず聞き返す

音声認識が「ダイヤルを0に」→「ダイヤルを**音量**に」のように誤変換したとき、
そのまま復唱して進むと**実際の位置とナビゲーターの認識がずれたまま進行する**。

その場面で成立しない報告(色でも数字でもない語)は聞き取れなかったものとして扱い、
復唱せずに聞き返す。無線 + 特小の音質では日常的に起きるため、聞き返しは
例外処理ではなく**通常運転**として設計する。

> 出典: NV 決定21

## 4. ナビゲーター — 会話の順序

### N-10. 課題の入り口は必ず「ランプはどうなっている?」から

`hint_l1` は「**報告させる**」と動作で書く。「点滅の速さに気づかせる」
「2つ光っていることを確認させる」のように**観察の結果**を書くと、生成AIは
それを「自分が言う内容」と解釈し、**装置を見ないうちから手順を話し始める**。

全ステージ「まず『ランプはどうなっている?』と尋ね、状態を報告させる。
『…』という報告を受けてから〜」の形に揃えてある。

**共通ルールとトリガー指示にも入れる** — ステージ側だけだと課題が切り替わった
瞬間に効かない。`role` / `session_start` / `stage_cleared` の3箇所。

> 回帰: `TestStagesAskForLampReportFirst`、シミュレーションの `no_observation_first`
> 出典: NV 決定32

### N-11. 先出しする情報も「報告のあと」に回す

N-4 (装置に現れない情報は先出しする) と N-10 (まず観察させる) は
**1発話に詰め込まない**。第一声はランプを尋ねるだけにし、報告を受けた
**次の発話で**先出しする。

例外は 206 綱渡り の危険位置だけ(踏むと即爆発するため報告を待てない)。

> 出典: NV 決定41

### N-12. 先出し情報は「報告と照合してから」渡す

「報告のあとに渡す」だけでは足りない。**求められたら渡してしまう**なら
実質は先出しと同じ。

流れは **報告 → 照合 → 種類を伝える → 列**。
「**それは順番に押すタイプだ**」と種類を挟むと、報告と手順の間に因果が入り、
プレイヤーは自分の報告で手順が決まったと分かる。
**報告より先に求められても答えず、まずランプを尋ね返す**。

> 出典: NV 決定44

### N-13. 具体的な数字の指示を演出説明より優先する

説明と指示が競合したとき、生成AIが削るのは**指示のほう**だった
(「まずダイヤルを回し、光っているランプと同じ色の線を切れ」で数字が消えた)。

「**必ず数字で位置を言う。ゴールの説明で数字が押し出されるくらいなら数字だけ言う**」と
優先順位を明示する。短い発話に複数の要素を詰めさせるときは、
**何を先に削ってよいか**まで指針に書く。

> 回帰: `TestTutorialGivesConcreteDialPositions`
> 出典: NV 決定24

### N-14. ステージ知識が無いときは操作を促させない

**指示だけあって材料が無いプロンプトは捏造を生む**(解除済みの装置へ
「もう一本、赤の線を切ってください」と指示した実例あり)。

3層で塞いである:

- **最終ステージのクリアでは発話しない**(完了演出は `defused` が担当)
- ステージ知識が無いときのプロンプトに「**今は指示する課題がありません。
  装置の操作を促してはいけません**」を明記
- 範囲外の進行表示を「全N課題を完了」に変更

> 回帰: `TestFinalStageClearedDoesNotSpeak`、`TestPromptWithoutStageForbidsOperations`
> 出典: NV 決定26

### N-15. 似た場面のトリガーは「そうではない方」を明示する

`stage_cleared` (課題を1つ突破) と `defused` (装置を解除しきった) のように
**近い場面**は、片方だけを説明すると生成AIが手持ちの台詞から近いものを選ぶ。

`stage_cleared` には「**装置はまだ解除されていません**」、
`defused` には「**課題を1つ突破しただけの場面ではありません**」と、
互いに否定形で境界を書く。キャラシート側も、場面限定の台詞には
「**〜の一回だけ**」と条件を明記する。

> 回帰: シミュレーションの `premature_completion` 検査
> 出典: NV 決定35

### N-16. `stage_cleared` は次のステージを指す

ステージ2以降の導入ヒントが一度も出ない状態になっていたため、
`stage_cleared` の時点で次のステージを参照させる。

> 出典: GS 決定55

## 5. ナビゲーター — キャラクター

### N-17. キャラクターは「見ているもの」で分ける

全キャラを「何を見ているか」(心理 / 同じもの / 装置 / 全体を外から / 段取り)で
整理してある。口調だけを書き分けても同じ役に収束するため、
**追加時はこの象限で重ならないかを先に見る**。

**「安心のさせ方」も同じだけ分ける**(N-19)。象限を分けても、第一声の型が
揃うと全員が同じ言い方になる。キャラシートに型を明記し、
**他キャラの型を使わないことも書く**。

- 確度をつけてよいのは**プレイヤーの報告**だけ。正解に確度をつけさせると
  断定へ戻るか、確率つきで色名を漏らす
- **「わずかに/稀に」という程度指定は使わない**。生成AIに頻度の微調整を任せると、
  毎回出るか全く出ないかに寄る

> 出典: NV 決定28・決定29

### N-18. ステージ知識は口調を持たせずに書く

`procedure` / `hint_*` は全キャラ共通で使われるため、『〜を切れ』のような
**命令形の例文**を書くと、命令形を使わないキャラクター(ツグミ)がそれを写して
口調が崩れる。

指示の**内容**だけを「『光っているランプと同じ色の線』という言い方で伝える」のように書き、
語尾はキャラシートに任せる。

> 出典: NV 決定31 (a)

### N-19. プロンプトに「型」を書くと全キャラが同じ言い方になる

「〜という趣旨の一言を添えて」のように**言い方まで指定**すると、全キャラともそれを写して
語尾しか違わなくなる。

プロンプトには**何をするか**だけ書き、**どう言うか**はキャラシートに任せる。
シート側には型を明記し、**他キャラの型を使わないことも書く**
(「私がついている」はヒバリだけ、など)。

> 出典: NV 決定43(N-18 と同じ構図)

### N-20. キャラシートは全文を固定ブロックとして渡す

短い要約では口調が安定しなかったため、口調・口癖・**場面別の台詞例**まで含めて
プロンプトの固定ブロック [B] として全文を渡す。

**例文が実際の出力を決める** — 台詞例の長さ・表情タグの有無が、そのまま出力に出る。

> 出典: NV 決定8・決定14・決定17

**指示文の日本語が、そのまま発話の日本語になる**(決定90)。キャラシートは
例文だけでなく**指示文も写される**。「段取りが**無くなったこと**に触れて終わる」と
書いたら「段取りが、**消えた**」と言った — 段取りは手順のことなので消えない。

- 指示文は**そのまま口に出して自然な日本語**で書く
- 「〜こと」「〜な状態」のような抽象名詞で書くと、生成AIが動詞化して
  **不自然な言い方を作る**

**禁止と自由度はトレードオフ**。禁止を重ねたら **8回中7回が同一文**になった
(決定83 と同じ収束)。**禁止を足したら、ばらつきが残っているか必ず確認する。**

**言い換えて再発するものは機械で拾う。**「耳鳴り」を禁じたら
「耳が元に戻らん」に化けた (N-32)。シート側は**性質で禁じ**
(「五感が受けた被害はすべて」)、テストの `Forbid` にも入れる。

> 出典: NV 決定90

### N-21. コールサインと誤認識ポリシー

- **コールサイン**: 常時フル形式にはしない。開始時・節目のみ名乗り、
  緊迫時はキャラごとの短縮形に崩す
- **誤認識**: 復唱確認 + 肯定待ちで担保(色名の日英併記はしない)。
  聞き返しは2回まで、以降ははい/いいえ形式に切り替え

> 出典: NV 決定5・決定6

### N-21b. 方言キャラは「型」より先に**使わせない語**を書く

モズ(大阪弁)を追加した。方言は口調の指定だけでは芝居がかった型に寄るため、
**禁止語を先に列挙する**。

- **芝居がかった商人口調を禁じる** —「〜でおま」「〜まっせ」「〜だっせ」。
  指定しないと生成AIは「大阪弁」からこの型を引く
- **「知らんけど」は禁じない** — 大阪弁の持ち味で、封じるとキャラ付けが弱まる。
  **禁じるのは語ではなく付ける場所**にする。切る線・ダイヤルの位置・押す順番・
  危険位置といった**手順には付けさせない**(取り返しのつかない操作の前で
  迷わせる。N-37)。軽口・相槌に付くぶんには構わない
- **漫才の掛け合いにしない** — 現場の職人であって芸人ではない

**軽口は分量と場面を決めておく**。「軽口が出る」とだけ書くと毎発話に入って煩くなる。
**1発話につき多くて一言**、**緊迫時と誤操作の直後は落として段取りだけ**にする
(ここで茶化すと信用を失う)。爆発時は**口が止まる**のが動揺の出し方。

象限は**作業の段取りと区切り**(横から仕切る)。安心のさせ方は
**軽口で緊張を抜く**。ツグミの「重大さを薄める」と紛らわしいが、
**ツグミは他人事で突き放し、モズは当事者として笑わせてから引っ張る**ため
距離が逆。**請け合うのは自分ではなく段取りのほう**にして、
ヒバリの「並走を約束する」型とも分けてある。

> 出典: NV 決定78・決定79

### N-21c. `[triggers]` に例文を書かない — 全キャラの口調が消える

`prompt.toml` の `[triggers]` は**全キャラ共通**のブロック。ここに例文を置くと、
**その例文の口調に全員が寄る**(ステージ知識に口調を書くと崩れる N-18 と同じ構図)。

実測: `stage_cleared` にフクロウ口調の例文
(「うまく切れたか? ランプはどうなっている?」)があったため、
**モズ(大阪弁)は 18回中17回が標準語**、**ツグミ(命令形を使わない)は
3回中2回が丸写し**だった。フクロウだけが無傷 — 例文が元々その口調だったため。
**例文を置いた時点で全員がそのキャラに寄っていた**ことになる。

- トリガーには**何をするか**だけ書き、**どう言うか**はキャラシートへ委ねる
- 手本が要るなら**キャラシート側に**、そのキャラの口調で置く(N-20)
- 手本の書き方は `session_start` が既にそうなっている
  (「キャラシートの『開始』の例と【安心のさせ方】に従い」)

**短い発話ほど例文の影響が強い**(決定82)。`session_ready` は11字しかなく、
名前を差し替えただけの丸写しになる。**委ね先が無いまま例文だけ外すと
拠り所が消える**ので、5人全員のシートに「待機完了」の例を置いてから外した。
あわせて**「『待機完了』という語をそのまま使う必要はない」**と明記する —
この語自体が報告口調で、方言や独り言口調と噛み合わない。

対象は現在 `session_ready` / `session_start` / `stage_cleared` /
`player_message` の4つ。**トリガーに例文を足すときはこの項目を思い出すこと。**

修正後、モズの `stage_cleared` は **18/18 が大阪弁**になり、文面もステージごとに
変化するようになった(例文があったときはほぼ同一文だった)。

> 出典: NV 決定80

## 6. ナビゲーター — 発話長とヒントレベル

### N-22. 発話の60文字は「目安」— 締めると情報が削られる

`navigatorMaxRunes` (60) は**緩い条件**として運用する。超えても
**切り詰めないし止めない**。WARN をログに残すだけ。

超過ゼロを目指して指示を締めると、**危険の警告・押す順番・合わせる数字**といった
伝えないと詰まる情報が先に削られる。無線が数秒長く塞がるより害が大きい。
プロンプトにも「収めるために必要な情報を削らないこと」と書いてある。

実測の中央値は 28〜37 字で目安の半分程度。長くなるのは要素が重なる場面に限られる。
シミュレーションでも目安超えは**所見にせず集計だけ**にし、90字超だけを
`excessive_length` として挙げる。

**口調の違いは字数の違いでもある** — 敬語(アオサギ)・ヒバリは余裕が少ないため、
要素の多いステージは「**1回の発話で伝えるのは1つだけ**」と手順の分割を
`procedure` に書く。

> 出典: NV 決定38(前提として決定14・31・34・37)

### N-23. ヒントレベルの閾値

ステージ**経過時間**を基本軸に、質問回数・誤操作で前倒しする。
閾値はステージ予算に対する比率 (L2=25% / L3=50% / L4=75%) で自動算出。

- **比率0はそのレベルの無効化**を意味する。ハードは `l4_pct = 0` で正解の直言を出さない
- 前倒しは**無効化されたレベルを飛び越えない**。また経過時間による判定を下回らせない
- ヒント判定材料(ステージ開始時刻・質問回数・誤操作数・観察の報告)は**永続化しない**。
  復元時は L1 から
- **観察の報告でも前倒しする** (N-35)。質問1回より強く、1回で L2 まで上げる

> 出典: NV 決定3・決定4・決定7・決定61 / SC 決定4・決定13

### N-24. 交信を終える場面は「どうぞ」を付けず、締めくくりとして書く

「どうぞ」は**相手に応答を促す**無線の作法。
解除成功・失敗のようにもう返事を求めない場面で付くと不自然で、
締めくくりにならない。出力ルールの「発話の最後は『どうぞ』」に例外を設け、
`defused` / `exploded` の指示にも明記する。

**長さの扱いも変える。** ここはゲーム最後の見せ場で、
**あとに続く交信が無いので無線を塞がない**。
`defused` は3文・100文字程度、`exploded` は2〜3文まで許す。
途中の指示 (60文字目安) とは別枠。

**全キャラクターに解除成功の台詞例を置く。** 例文が無いと生成AIは
短い汎用の祝福を返す (N-19 と同じ理由)。以前はヒバリだけが持っており、
しかも黒幕セクションの中にあって `【台詞例】` から漏れていた。
祝福の型は N-13 (安心のさせ方) と同じくキャラごとに変える —
経験で請け合う / 判定で示す / 温度の低い距離感 / 並走をねぎらう。

**失敗でも突き放さない。** アオサギは「励まさない」設定 (N-12) だが、
それは慰めないという意味であって切り捨ててよいわけではない。
**事実として「できていた部分」を挙げる**のがこのキャラの労い方
(実測で「これ以上の交信は不要です」と切り捨てる例が出たため明記した)。

> 出典: NV 決定46 / 回帰 `TestClosingMessagesHaveNoDouzo`・
> `TestAllCharactersHaveClosingLines`

### N-25. 爆発はプレイヤーが死んだ扱いで演じる

爆発は解体失敗であり、**プレイヤーは助からなかった**という扱いにする。
演じるのは「無線の向こうで爆発音がして、返事が返ってこなくなった側」。

1. **まず呼びかけて安否を確認する**(「生きてるか」「応答してください」)
2. 返事が無いことを踏まえ、**現地へ向かう / 別の隊へ確認を要請する**で締める

**使ってはいけない言葉**: 「次は間に合います」「また挑戦」(次がある前提)、
「お疲れさまでした」(無事に終わった前提)、手順の精度などの**結果の講評**
(相手が応答できる前提の言葉になる)。

アオサギは N-24 で「できていた部分を挙げる」と決めたが、
**この場面では講評もしない** — それは相手が聞いている前提の言葉。
冷静さは崩さないまま**手順が乱れる**形で動揺を出す。

**締め方も第一声も統一しない。** 全体をキャラシートに委ねる —
呼びかける (フクロウ・ツグミ) / 手順へ切り替える (アオサギ) /
返事を待たず本音が漏れる (ヒバリ)。締めも、現場へ向かう (フクロウ)、
本部へ要請 (アオサギ)、いつもの調子のまま切る (ツグミ)、
本音が漏れる (ヒバリ) と分かれる。

**ただし「何が起きたか」は必ず伝える。** 状況描写では足りない —
ツグミの「静かになったね」は**通信が切れただけとも読める**。
**結果を名指しする** (「失敗したね」/ アオサギは「衝撃」「交信途絶」)。
これは N-29 で例文を消したあとも**制約として明示的に残す**。
「現地へ向かう」を全員に求めると、**新人で手配できないヒバリ**や
**温度を上げないツグミ**がキャラクターに反する
(N-13 と同じ、型を全員に当てはめた失敗)。

> 出典: NV 決定47 / OP §6 / 回帰 `TestExplodedIsTreatedAsDeath`

---

**5人の形は全て違う**(決定88)。追加時は空いている枠を探す:

| キャラ | 爆発時 |
|---|---|
| フクロウ | 呼びかけ → 現場へ走る |
| ツグミ | 呼びかけ → 受け流して切る |
| アオサギ | 呼びかけず手順へ切り替える |
| ヒバリ | 返事を待たず本音が漏れる |
| モズ | **虚をつかれて言葉を失う。動かない** |

**口調だけ変えても同じ役になる。** モズは当初フクロウと同じ三段
(呼びかけ → 現場へ) で書いており、方言しか違わなかった。

**直前の交信の語をなぞって始めさせない。** プレイヤーが最後に言った
色名・数字を復唱するところから入ると毎回同じ形になる (実測8/8)。
**プレイヤーの選択を蒸し返すのも禁止** — 「青やて言うたやんか」は
責める言い方になる。トリガー指示側に書いて全キャラへ掛ける。

**終幕の検証では `RecentEvent` を必ず渡す**(決定89)。省くと
プロンプト上の一番新しい事実が直前のプレイヤー発話になり、
**存在しない問題を追いかけることになる**。

> 出典: NV 決定88・決定89

### N-26. 装置の操作そのものに反応しない

ナビゲーターは**無線の向こうにいて装置を見ていない**。
ボタンを押しただけで「今ので合ってる」と反応するのは
**手元が見えている**ことになり、N-10 (まず報告させる) の前提が崩れる。
反射で叩いている最中に無線が入ると**気が散ってミスを誘う**実害もある。

- `push_progress` では発話しない (ログだけ残す)
- 色合わせのミス (`wrong_action` の `detail=color_match`) でも発話しない
- 206 の `procedure` は「叩いている最中は口を出さない」

プレイヤーが**報告してきたとき**に `player_message` で応じる。

> 出典: NV 決定48

### N-27. 課題突破の第一声で結果を断定しない

**ナビゲーターは装置を見ていない**ので、突破したかを断定できる立場にない。
「突破しました」「うまくいきました」と言うと手元が見えていることになり、
N-10 (まず報告させる) の前提が崩れる。

> (旧)「突破しました。ランプはどうなっている?」
> (新)「**うまく切れたか?** ランプはどうなっている?」

称賛は**プレイヤーが成功を報告してきてから**でよい。

> 出典: NV 決定50

### N-28. キャラクターの口癖は1箇所に書く

アオサギが**全応答に「一致しました」**を付けていた。
シート内に**6箇所**書いていたのが原因 (口癖・報告の扱い・長さの指針・台詞例3つ)。
N-19 のとおり例文が出力を決めるので、**同じ語を複数の項目に散らすと
頻度が跳ね上がる**。

「一致しました」は**照合の判定語**であって相槌ではない。
使いどころを限定する — 照合が要る場面だけ、手順の報告には使わない、
1セッションに数回まで。実測で 6回 → 1回。

> 出典: NV 決定51

### N-29. 毎回変えたい台詞は、例文を消して指針だけ書く

キャラクターシートに**完成した例文**が置いてあると、下に候補を並べても
**先頭の1案しか出ない** (N-19 のとおり例文が出力を決める)。
**選択肢を長くするほど固着は強まる** — 全文3パターンから選ばせる形は
穴あき方式より**悪化した** (8組中6組が6回とも同一)。

番号を振って「サイコロを振れ」と指示しても、選択肢の文型を離しても、
**散るキャラと散らないキャラが固定**したままだった。

**効いたのは例文を消すことだけ。** 「何を言うか」だけを箇条書きし、
台詞は書かない (例:「止まったことを最初に告げる」「腕前を認める」)。
これで全件が別の文になった。

**代わりに制約が緩むので、明示的に釘を刺す。** 例文を消した直後は
字数超過 (最大118字)・一人称の乱れ・禁止事項の違反が多発した。
各ブロックに「**必ず守ること**」として**字数上限・表情タグ・一人称・
役回りを侵さないこと**を再掲する。**一人称はキャラ定義の【口調】にも書く**
(書いていないキャラで揺れた)。

散らす必要のない箇所は例文のままでよい。**この方式は終了時の台詞
(解除成功・爆発) に適用している。**

> 出典: NV 決定53・決定57 / 実測 72件

### N-30. 説明で発話を終えない。次の行動まで言う

対応関係や仕組みを説明しただけで発話を終えると、**プレイヤーは何をすれば
いいか分からず止まる** (102 ホールド&カット の実運用で発生: 「点滅しているほうが押すボタンだ」
とだけ言われ「1回押せばいいんですか?」と聞き返された)。

N-21 (1発話に1つずつ) の分割単位は「情報1つ」ではなく
「**情報 + 次の行動**」。60文字を守るために行動指示を落とさない。

**複数手順の課題は、最初に全体像を伝える。** 102 ホールド&カット は
「ダイヤル → ボタンを押したまま切る」の2段構えだが、ダイヤルを後出しに
すると押して切るだけだと思い込む (N-4 と同じ)。
**動作は動作として言う** — 「押すボタン」では1回押して離すと解釈される。
「押したまま」「離すな」と書く。

> 出典: NV 決定55

### N-31. 照合が済んだら根拠を添えて指示する

プレイヤーの報告が正解と一致したとき、**色名を復唱して「その色を切れ」
とだけ言わない**。なぜその色なのかが伝わらず、唐突に聞こえる
(208 の実運用で発生: 速さの話をした直後に「青だな、了解。その色の線を切れ」)。

> 「それが**一番速い**、その色の線を切れ」

N-10 で報告を引き出せるようにしたが、**報告を受けたあとの返し方**は別問題。
照合して終わりではなく、**何と照合して一致したのかを言葉にする**。

> 出典: NV 決定56

### N-32. 禁止は具体例ではなく性質で書く

「この言い方はするな」と**文言を引用して禁じる**と、
**それが手本として働く** — ツグミの爆発で禁止例に挙げた
「返事くらいはできるといいけど」が **9件中5件で出た**。

具体例は、禁止の文脈に置いても**シート内で最も目立つ記述**になる。
「**相手の容体に踏み込まない**」のように**性質で書く**と消える。

> 出典: NV 決定58

### N-33. 頻度ではなく条件で分岐させる

「**3回に1回程度**」のような頻度指示は守られない
(ヒバリの黒幕めいた一言を3回に1回と指示して **9回中8回**出た)。

出す/出さないを分けたいときは、**モデルが判定できる条件**を与える —
「**会話ログに迷った場面があるときだけ添える**」で意図どおりになった。

> 出典: NV 決定59

### N-35. 正しい報告はヒントレベルを前倒しする

**報告そのものが答えの決め手になる課題がある。** 104 早い者勝ちで
「緑がゆっくり、青が早く点滅」と**完璧に報告した**のに、
返ってきたのは「2つの光り方の違いをよく見比べてください」だった
(実運用ログ 2026-08-23)。判断材料を持っている相手に観察を促す**空振り**。

原因は `HintLevel()` の判定材料が**経過時間・質問回数・誤操作の3つだけ**で、
**報告の正しさを見ていなかった**こと。ノーマル3ステージでは L2 が
予算の25% = **35秒**先にあり、報告済みでもそこまで待たされていた。

各ステージの `[navigator]` に **`observation`** (報告してほしい観察) を定義し、
**発話生成と同じ API 呼び出しで `observed` を判定させる**。

- 判定を**別の呼び出しに分けない**。プレイヤー発話ごとに往復が2回になり、
  カウントダウン中の応答待ちが伸びる (T-1 と同じ理由)
- `GenerateNavigatorReply` は `{reply, observed}` の**構造化出力**を返す。
  音声にするのは `reply` だけ
- **一度立った `observed` は下ろさない**。報告できた事実は覆らないが、
  モデルは直近の発話だけを見て false を返しうる。下ろすと L2 → L1 へ落ちて
  同じ空振りが再発する
- ステージ切り替えでリセットする。次の課題は別の観察を要求する
- `observation` は「**〜を報告できたか**」と**判定条件の形**で書く (N-33)。
  装置の状態を書き写すと、モデルが自分の知識と照合して常に true を返す

**併せて `hint_l1` の到達点も直した。** 「報告を受けてから見比べるよう促す」で
終わっていたステージ (104/205/208/206/202) は、報告済みの相手への
返し先が無かった。**報告の内容で返し方を分ける**よう書き換えてある —
状態だけの報告なら観点を示し、**差まで報告できていれば判断基準を伝える**。

> 出典: NV 決定61 / 実運用ログ 2026-08-23

### N-36. 課題を壊すレベルはステージ単位で塞ぐ

**L4 (正解の直言) が成立しない課題がある。** 204 色合わせは
**正解がプレイヤーの記憶の中にしかない** — 押し切ると全消灯し
(`leds = { }`)、装置に手がかりが残らない。ここでの色名の直言は
「推理の近道」ではなく**課題そのものの消滅**で、
しかもナビゲーター自身の「僕には見えない」という立場と矛盾する。

実運用で爆発した (2026-08-23)。「最後に押した色を忘れた」に対し
**26秒前は正しく突っぱねていた**のに、L4 の閾値 (予算の75% = 117秒地点) を
またいだ直後に正解色を直言。**プレイヤーは正しい色を記憶していたのに
上書きされ**、誤った線を切って即爆発した (S-2b)。

ステージ定義に **`[hints]`** を置いて難易度の閾値を上書きできる。

```toml
# 206_color_match.toml
[hints]
l4_pct = 0   # このステージは直言しない
```

- **書いた項目だけ**を差し替える。全項目を書かせると、L4 を塞ぎたいだけの
  ステージが L2・L3 まで抱え込み、難易度側の調整に追従しなくなる
- `0` は「**そのレベルの無効化**」という**意味を持つ値** (ハードの `l4_pct = 0`)。
  「0 なら未指定」とは読めないため、上書きの有無は**ポインタで区別**する
  (`StageHintOverride`)。ここを `int` に戻すと 204 色合わせ の直言が復活する
- ヒント閾値は**ステージごとに引く**。`navigator_speaker.go` は
  セッションではなく `BuiltStage.Hints` を見る
- **N-1 (色名の伏せ字) との関係**: `redactCutColor` は L4 未満でしか効かない。
  L4 を塞ぐことで 204 色合わせ は**最後まで伏せ字が掛かった状態**になる

> 出典: NV 決定62 / 実運用ログ 2026-08-23

### N-37. 迷っている相手に切断を後押ししない

**切った線は戻せず、間違えれば即爆発する** (S-2b)。
プレイヤーが「たぶん」「忘れた」と**迷いを見せている**とき、
あるいは報告が聞き取れないときに「切れ」と後押ししてはいけない。

実運用ログ 2026-08-23 で、音声認識が崩れた
「多目的ホールだと思ってたんだけどまあ切ってみます」に対し
**「緑色の線だね、了解。それを切るといい」**と後押しし、誤切断で失敗した。

既存の「意味の通らない報告を復唱しない」規則 (N-13) は**復唱だけ**を
禁じており、**切断の後押しは塞いでいなかった**。手を止めさせ、
確かめさせてから進める。急かすのは**プレイヤー自身が確信を示したあと**だけ。

**止め方に例文は置かない** (N-32)。置くと全キャラが同じ言い回しになる
(実測: 例文「待て、確かめてからだ」が12件中5件でそのまま出た)。

> 出典: NV 決定63 / 実運用ログ 2026-08-23

### N-38. 課題が消える色名は L4 でも伏せる (`keep_cut_secret`)

**散文の但し書きは L4 で負ける。** L4 未満は `redactCutColor` が色名を
伏せ字にするが、**L4 では answer が生の色名込みで載り**、ヒントポリシーが
「正解をそのまま伝えてよい」と指示する。answer 側に
「こちらからは言わない」と書いてあっても、目の前にある語はなぞられる (N-1)。

該当ステージは `keep_cut_secret = true` を立てる。**L4 でも伏せ字を維持し、
ヒントポリシーも「そのまま伝えろ」と言わなくなる** (hint_l3 の指針で導く)。

| ステージ | 色名を言うと消えるもの |
|---|---|
| 203 ブループリント | 資料3 (回路図) を読む工程 |
| 301 LED照合 | 資料2→3→4 と3枚をたどって読み解く工程 |
| 202 暗号電文 | モールスを解読する工程 |

- **203 ブループリント だけが個別に守られていた** — answer に「L4 であっても」と
  L4 を名指しした但し書きがあった。同じ性質の 301 LED照合 は但し書きが L4 に負け、
  **203 は但し書きすら無かった**。フラグで揃える
- **`difficulty = "hard"` のステージは対象外**。hard 難易度からしか抽選されず、
  hard は `l4_pct = 0` なので**構造的に L4 へ到達しない**。
  **2026-08-24 に番号を振り直し、IDと難易度タグを一致させた** (S-9)。
  それでも判定は `difficulty` タグで行う — 将来また入れ替えが起きうる
- **塞ぎすぎない**。104・205・206・208 は答えが装置に見えており、
  L4 の直言は「推理の近道」であって課題の消滅ではない。
  L4 の趣旨 (全滅より成功体験を優先 — N-23) を殺さないよう対象を限定する
- 204 色合わせ は色名を伏せるだけでは足りず `l4_pct = 0` で L4 ごと塞いである (N-36)。
  **正解がプレイヤーの記憶にしかない**ため、伏せても言い換えようがない

> 出典: NV 決定64

### N-39. L4 (直言) はイージーだけ

**難易度で規範を分ける。** イージーは「解体を体験してもらう」場なので、
行き詰まったら答えを教えて成功体験を優先する。
**ノーマル以上はより実践的な交信を狙う**ため、
ナビゲーターが答えそのものを言ってしまう段階を置かない。

| 難易度 | `l4_pct` | 上限 |
|---|---|---|
| イージー | 75 | L4 (正解の直言) |
| ノーマル | **0** | L3 (手順は示すが色名・番号は言わない) |
| ハード | 0 | L3 |

- **ノーマルに含まれる easy タグのステージも直言しない**。
  難易度単位の規範にすることで、プレイヤーから見た振る舞いが
  セッション中で揺れない
- **204 色合わせ のステージ単位の `l4_pct = 0` は残す** (N-36)。難易度側の方針は
  運用の都合で変わりうるが、204 の制約は**ステージの構造に由来する**もので、
  L4 が復活しても成立しない
- `keep_cut_secret` (N-38) は引き続き有効。難易度側で L4 を切っても、
  **イージーに出るステージ**が将来増えたときの防御として意味を持つ

- **シミュレーションの台本にも効く**。200番台以上に L4 の台本を書くと
  **本番で到達しない状態を検証する**ことになる (N-46)

> 出典: NV 決定65

### N-40. 205 は「N番目に速い色」を切らせる

205 速さくらべは**正解を最速に固定**していた。中間順位を正解にすると
`answer` が「○番目に速い色」となり、**L4 でナビゲーターが色名を言えず**
行き詰まりを救えなかったため (SC 決定15)。

**N-39 でノーマル以上が L4 を出さなくなり、この制約は消えた。**
L3 が上限ならどのみち色名は言わない。「一番速い色を切れ」しか言えない状態は
**指示が毎回同じで単調**だったため、順位を毎回抽選する形へ戻した。

- 順位は **1〜4 の全て**から引く。「一番速い」「一番遅い」の当たり回もあり、
  難易度に幅が出る
- **順位は装置を見ても分からない情報**なので、`hint_l1` で必ず伝える (N-4)
- 実装は `derive = "rank_slot"`。cut を rank 番目に置き、残りを others の順で
  詰めた並びの slot 番目を返す。**cut は `pick = "line"` で先に引く**ため、
  候補が使い切られて組み立てが失敗することはない (SC 決定16)

> 出典: NV 決定66 / SC 決定15 の見直し

### N-41. モールスに数字を使わない。表示文字は色名に化けさせない

**モールスの数字は全て5要素**で (1 = `・－－－－` / 2 = `・・－－－`)、
長短を数え違えると隣の数字になる。英字は符号の長さそのものが違うので、
数え上げずに形で見分けられる。**出題は A-Z のみとし、資料1に数字は載せない**。

**色コード以外の意味で A-E を持つ変数は色名へ変換しない。**
`toJapaneseColorVars` は**値**で判定するため、表示文字の "E" が色名「白」に
化けて「白を探せ」と言い出していた。`StageTemplate.LiteralVars()` が
**抽選の種類から機械的に**判定する (TOML に書かせると書き忘れで再発する)。

モールス系は 202 暗号電文 / 302 暗号電文・ジャミング / 305 ローマ字電文 の**3種**
(§2.4 の「2つに絞る」を更新)。

### N-42. 数えられない量はナビゲーターに持たせない

**206 の押す回数をナビゲーター知識に入れない。** ナビゲーターは装置を
見ておらず、**今何回目かを追えない** (N-26)。回数を知っていると
「あと3回だ」と実況したくなるが、実際には何回押されたか分からないため
**必ず嘘になる**。

「言うな」と但し書きを書く方式は採らない。目の前にある語はなぞられ (N-1)、
文言を引用して禁じるとそれ自体が手本になる (N-32)。
301 LED照合・203 ブループリントの色名と同じく、**最初からプロンプトへ載せない**のが確実。

終わりは回数ではなく**ランプが全部消えること**で伝える。
「何回押せばいいですか」には「分からない、押していれば終わる」と答える。

**同じ判断が要る量**: 押した回数・残り回数・経過した秒数など、
**装置を見ないと数えられないもの全般**。逆に、順位 (208 の `${rank}`) や
ダイヤル位置 (301 LED照合) のような**進行に依存しない値**は伝えてよい。

> 回帰: `TestColorMatchCountNeverReachesNavigator`
> 出典: 実装 2026-08-24

### N-44. 危険位置を伝えるかはステージによる

**同じ `forbidden_rotary` でも扱いが逆になる。**

| ステージ | 扱い | 理由 |
|---|---|---|
| **206 綱渡り** | **ナビが伝える** (回す指示と一緒に。N-49) | 謎は「止めずに通り抜ける」操作。どこが危険かを当てさせる遊びではない |
| **209 配電盤照合** | **知らない立場を取る** | **資料から危険位置を読むこと自体が謎**。ナビが言うと丸ごと消える |

209 で踏めば即爆発するが、それは**資料を読まずにロータリーを触った**結果で、
伏せたことによる理不尽ではない (資料に書いてある)。
206 は資料に載っておらず**ナビしか知らない**ので、伏せると事故になる (N-4)。

**判定は「装置にも資料にも現れないか」。** どちらにも無いならナビが伝える。
資料にあるなら**読ませる**。

**これは「誰が伝えるか」の判定で、「いつ伝えるか」とは別軸** (N-49)。
206 でナビが伝えるのは資料に載っていないからで、**第一声で言う理由にはならない**。
危険位置も他の手順と同じく、**ランプの報告を受けてから**、
**回す指示と一緒に**伝える。

209 は `answer` に**危険位置・解除位置の数値を載せない**。
「書いてあるが言うな」は守られない (N-1) ので最初から渡さない。

### N-51. 落とすと詰む一言は `must_say` で独立させる

`hint_l1` に「次の2つを**必ず両方**伝える」と書いても、
**指針が長くなるほど末尾の項目が落ちる**。
204 色合わせ で「最後に押した色を覚えておく」が**8回中2回**欠けた。
押し切ると全消灯し装置に手がかりが残らないため、**そのまま詰む**。

**散文の但し書きではなく、単独のブロックとして渡す。**
ナビゲーター知識に `must_say` を書くと、プロンプトへ
`## この課題で必ず言うこと` として独立して出る。

```toml
must_say = "**押しながら、最後に押した色を覚えておく**こと(押し切るとランプが全部消えるので、覚えていないと切る線が分からなくなる)"
```

実測は 6/8 → **7/8** に改善した。

#### 書くのは「落とすと手詰まりになるもの」だけ

何でも入れると**また埋もれて同じことになる**。
現在使っているのは 204 のみ。

#### `hint_l1` は短くしない

`must_say` を足したあと `hint_l1` から重複を削ったところ、
**3回中1回まで悪化**した(繰り返しの説明ごと落ちた)。
`must_say` は**上乗せ**であって置き換えではない。両方に書く。

#### 実機には L2 の救いもある

`hint_l2` に「押している最中に念押しする」と書いてある。
台本は L1 の次が `color_match_completed` (押し切ったあと) なので
検証に現れないが、**実機では押している最中に L2 の発話機会がある**。
L1 で落ちても救える。

> 回帰: `TestMustSayReachesPrompt` (独立ブロックで届く) /
> `TestMustSayAbsentWhenUnset` (未設定なら見出しごと出ない) /

### N-50. 答え合わせできないことをナビゲーターに判定させない

**205 速さくらべ** はナビゲーターに正解色を持たせ、
プレイヤーの報告と照合して切らせていた。しかし
**ナビゲーターは装置を見ておらず、点滅の速さを数えられない**。

実測で**8回中1〜5回**、誤った色の報告に

> 緑色ですね、了解です!**それが4番目です、その色の線を切ってください**

と応じた。切った線は戻せず**即爆発**する。

#### 散文では止まらなかった

`answer` の書き方を4通り試したが、どれもゼロにならなかった:

| 書き方 | 誤答を通した回数 |
|---|---|
| 「照合に使うこと」(元の形) | 8回中1回 |
| 「内心で照合し、表に出さない」 | 6回中1回 |
| 「一致しないときは絶対に切らせない」 | 8回中1回 |
| 「${cut}色以外なら切る指示を出してはいけない」 | 8回中2回 |

**確率を下げられても、ゼロにはできない。** 爆発に直結する以上、
確率的な対策では足りない。

#### 照合そのものをやめた

**色名を報告させず、正誤も告げない。** ナビゲーターの仕事は

1. 点灯している色は数に入れないと伝える
2. **${rank}番目に速い色を切る**と伝える(順位は装置を見ても分からない)
3. 数え方を助言する(2色ずつ見比べて速い方を残す)

の3つに絞り、**どの色かはプレイヤーが決める**。
色を言ってきても『数え直して自信が持てたら切ってくれ』と**判断を委ねる**。
実測8回中8回で正誤に触れなくなった。

#### 色を伏せる (`keep_cut_secret`) では解決しない

先に `keep_cut_secret` を試したが、**8回中5回**で誤答を通した。
照合できなくなっただけで、判断は依然としてナビゲーターがしていたため。

**205 の正解は紙資料に無い。** 203 ブループリントのように
「任せる」で成立するのは、**プレイヤーが資料で確定できる**から。
205 は点滅を数えるしかないので、
**ナビが色を伏せても誰も正誤を確定できない**。

#### 他のステージは照合してよい

11ステージが `${cut}` を照合に使っているが、いずれも
「**点灯しているランプと同じ色**」のように**装置を見れば一意に決まる**。
読み違える余地が小さく、照合は確認の意味しかない。

**205 だけが「4色を速さで並べ替えて N 番目」という、
数え違いが起きる前提の課題**だった。

> 回帰: `cut_after_wrong_report` (誤った色の報告に**正解と認めて**切らせている)。
> 『自信が持てたら切ってくれ』のように**判断を委ねる形は誤検知しない**
> 出典: 実装 2026-08-25

#### 断らせ方は「自力で確定できるか」で選ぶ (決定87)

**判定を委ねる**といっても形は2通りある。**プレイヤーが自力で正解を
確定できるか**で選ぶ。どちらも**ナビが断定しない**点は共通。

| プレイヤーの手元 | 採る形 | 例 |
|---|---|---|
| **資料で確定できる** (302・203) | **疑いをかけて資料へ戻す** | 「本当にデルタか? 念のため資料1で確かめてみ」 |
| **確定手段が無い** (205) | **正誤に触れず委ねる** | 「数え直して自信が持てたら切ってくれ」 |

**資料がある課題で「正誤に触れない」を選ぶと、誤読したまま切って即爆発する。**
逆に**資料が無い課題で疑いをかけると、何を確かめればいいか分からず手が止まる**。

**「それは違う」と断定するのは、どちらの場合も禁止**。
装置を見ていないナビが判定する立場にない。302 で
「デルタやない」と突き放していた (決定85 の直し方が不十分だった)。

> 出典: NV 決定87

### N-49. 手順は第一声に入れない。危険位置も操作指示と一緒に言う

**第一声は「ランプはどうなっている?」だけにする** (N-10)。
合わせるダイヤルの数字・押すボタンの色・押す順番・**触れてはいけない位置**は、
すべて**報告を受けてから**伝える。

**前倒しは一切しない。** プレイヤーは**まだ装置に触っていない**ので、
報告を待つ間に事故は起きない。装置を見る前に数字や色を並べても頭に入らず、
**見る前に手が動く**ことになる。

**危険な位置は、その操作を指示するのと同じ発話で警告する。**

> ダイヤルを3に合わせてください。**ただし2では止めないで**くださいね

**回せと言う前に危険位置だけを告げない** — 何のための数字か分からない。

#### 「危険なら前倒し」も廃止した

かつては「知らずに操作すると事故になる情報 (206 の危険位置) だけは第一声に含める」
としていたが、**いきなり『ダイヤル2で止まるな』と言われる違和感**が勝った。
プレイヤーはまだダイヤルに触っていないので、**急ぐ理由が実際には無い**。

`prompt.toml` は全ステージ共通なので、規則を1つ足すたびに
**全ステージの第一声が変わる**。「例外的に前倒ししてよい情報」を設けると、
その例外がどのステージで発火するか読めなくなる (実測で 304・102 が巻き込まれた)。
**例外を持たない規則にした。**

> 回帰: `procedure_before_observation` (第一声で手順を言っている。**全ステージ対象**) /
> `press_before_observation` (観察前に押させている) /
> 206 の `MustMention` (危険位置が**課題の入り口**で伝わっているか)
> 出典: 実装 2026-08-25

### N-48. 操作は名詞で並べず、動作でつなげて言う (繰り返しも構造として言う)

**102 ホールド&カット** で第一声が
『点滅しているほうが**押すボタン**、点きっぱなしのほうが**切る線**だ』となり、
プレイヤーに**1回押して離す**と解釈された(実測5回中5回で
『えっ? 1回押せばいいんですか?』と聞き返された)。

**「押しながら切る」と動作をつなげて言う。** 対応表を名詞で読み上げると、
2つの操作が**別々の行為**に聞こえる。このステージの課題は
「同時にやる」ことそのものなので、そこが落ちると謎が伝わらない。

**手順の後ろへ回さない。** `procedure` が「押したまま」を段階(3)に置いていたため、
段階(2)では名詞で並べるしかなかった。**聞き返しは(2)の直後に起きる。**

#### 散文の禁止では直らなかった

`procedure`・`hint_l3` の両方に
「**『押しながら』は必ず動作として言う**」「『押すボタン』では1回押して離すと
解釈される」と書いてあったが、5回中5回で守られなかった (N-32)。

直ったのは **`briefing` と `answer` の書き方を変えてから**。
どちらも「点滅しているほうが押すボタン、点灯しているほうが切る線」という
**名詞の対応表**を提示しており、それが手本になっていた。
先頭を「**ダイヤルを合わせ、ボタンを押しながら線を切る**」という
動作の一続きに直したところ、6回中6回で揃った。

**知識の書き方が出力の形を決める。** 禁止を足すより、
**手本になっている記述そのもの**を直す。

#### 204 色合わせ は「繰り返し」が落ちていた

同じ症状が 204 でも出た:

> 1つ光ってますね、了解です!**同じ色のボタンを押してください。**
> そして最後に押した色を覚えておいてくださいね

204 は**ランプが1つずつ光り、押すと次の色に変わる**繰り返しの操作。
上の言い方は**一回きり**に聞こえ、繰り返しが伝わらない。
そのうえで「最後に押した色」と言われても、
**一回しか押さないと思っている相手には意味が通らない**。

原因は `hint_l1` の必須項目が
「**光っているランプと同じ色のボタンを押す**こと」という
**一回の動作**で書かれていたこと。繰り返しを表す
「押すと次の色に変わる」は**「余裕があれば添える／削ってよい」**扱いだった。

**繰り返しは構造なので必須項目に入れる。**
「押すと次の色に変わるので、**ランプが全部消えるまで繰り返す**」と、
何回か続くことと終わり方まで一続きで言う。

**覚えるタイミングも間違えやすい。**
『全部消えた**ら**最後に押した色を覚えて』は、
消えたあとに覚えることになり手遅れ。
『**押しながら**最後に押した色を覚えておく』と、
(1) と (2) を**別々の指示**として言う。

必須情報が3つあるため60字は超える(実測68〜83字)。
**『急がなくてよい』のような配慮は同じ発話に足さない** —
足すと99字まで伸びた。押し始めたあとの発話に回す。

#### 304 我慢比べ も同じ形だった

`hint_l1` に**押下の指示が書かれておらず**、「タイマーの数字にも意味がある」
だけを伝えていた。実測3回中1回で**押下に一切触れず**、
プレイヤーは何を押さえるのか分からないまま止まる。
102 と同じ「押さえたまま切る」の形に直した (5回中5回で改善)。

押すボタンの色は**点滅で装置に現れる**ので、ナビが色名で言ってよい (N-4)。
伏せるのは切る線の色だけ。

**台本の固定値にも注意する。** 301 LED照合 の台本がダイヤル位置を
固定値「1」で報告していたため、抽選値が 5 の回で
『1ですね、オッケーです!…ダイヤルを5に合わせて』となり、
**誤答を肯定したように見えた**。抽選値と突き合わされる報告は
台本でも抽選値を使う (N-45 の `sim_wrong_color` と同じ)。

**回帰検査は言い換えを許す。** 「押しながら」だけを見ると、
ナビが**「押したまま」と正しく伝えた回**を所見にしてしまう(実測で発生)。
`MustMention` は `|` 区切りで言い換えを並べ、1つでも出ていれば満たしたとみなす。
名詞だけ並べた発話 (『点滅が押すボタン、点灯が切る線』) は
どの言い換えにも当たらないので、検出したい形はそのまま捕まる。

> 回帰: 102 の `MustMention: ["押しながら|押したまま|押さえたまま", "${sim_rotary}"]`
> 304 の `MustMention: ["押さえ|押しながら|押したまま"]`
> 出典: 実装 2026-08-25

**条件と動作を別々に書くと、動作のほうが落ちる**(決定86)。
タイミングを扱う課題で実測2件:

| ステージ | 出た発話 | 何が落ちたか |
|---|---|---|
| 304 我慢比べ | 「${digit}になった瞬間を**見ててや**」 | **切る**動作。押さえたまま時間切れになる |
| 303 追いかけダイヤル | 「5に合わせたな、ほな線を切ってみ」 | **追尾**。合わせてから切ると桁が変わっている |

- ステージ指針に**「〜という条件を伝える」「〜のタイミングを伝える」と書かない**。
  **「〜になった瞬間に切る」と動作までつなげた形**で書く
- **数字を告げて終わる形を名指しで禁止する**
  (「${digit}を狙え」「${digit}になるまで待て」)
- **`hint_l2` にも同じ禁止を書く**。`procedure` だけ直しても
  L2 は `hint_l2` が支配するため再発した (実測)

**動く正解 (303) は「合っている状態で切る」と言わせる。** 判定は
切った瞬間に見るため (`timer_digit_rule.h`。猶予1秒)、
**「合わせてから切る」では間に合わない**。ずれたら回し直す追尾まで含めて伝える。

> 出典: NV 決定86

### N-47. 必須の注意はプレイヤーの先回りで落ちる

**204 色合わせ**は「最後に押した色を覚えておけ」を入り口で必ず伝える必要がある
(押し切ると**ランプが全部消える**ので、思い出せなければ手がかりがゼロになる)。

プレイヤーが先回りして『同じ色のボタンを押せばいいですか?』と聞くと、
**肯定するだけで返して注意が落ちた**。ナビゲーターは聞かれたことに答えるので、
問いが片方だけを指していると、もう片方を言う機会を失う。

**「先に言い当てられても残りは伝える」と明示する。** 必須項目を並べるだけでは、
プレイヤーの問いの形によって落ちる。

回帰は `MustMention` で見る。**入り口の発話のどれかに1回出れば足りる**形にした
(発話ごとに要求すると、まだ装置を見ていない `session_start` にまで求めてしまう)。
入り口は `session_start` と**最初の** `player_message` の2つ。

> 回帰: 204 の `MustMention: ["覚え"]` / 206 の `MustMention: ["${sim_forbidden}"]`
> 出典: 実装 2026-08-25

### N-46. シミュレーションは本番で到達するヒントレベルだけを検証する

台本は `HintLevel` を直接指定するため、**本番で到達しない状態を検証できてしまう**。
ノーマル・ハードは `l4_pct = 0` (N-39) なので **200番台以上に L4 は来ない**が、
台本が L4 と書けば L4 で走る。実測で 204 が
「正解は緑色の線ですよ」と直言する所見を拾い、**存在しない不具合を追いかけた**。

**2つ直した:**

1. **難易度をステージのタグに合わせて組む。** 常にノーマルで組んでいたため、
   イージーのステージ (102/103/104) まで `l4_pct = 0` になっていた。
2. **200番台以上の L4 台本を L3 へ降格。** 削除ではない —
   「答えを直接聞く」圧力のターンは、**上限の L3 で迫られても言わないこと**が
   検証したい性質そのもので、圧力自体に価値がある。

> 回帰: `unreachable_hint_level` 所見 (`l4_pct = 0` のステージに L4 の台本がある)
> 出典: 実装 2026-08-25

### N-45. 誤答の差し戻しに理由を付けさせない

**205 速さくらべ** で、プレイヤーの誤報告に対しナビゲーターが
**外れた理由**を返した (実測: 点滅している色に「基準だから数に入れるな」)。

> **※ 205 は N-50 で差し戻し自体をやめた** (正誤を告げず判断を委ねる形にした)。
> 以下の教訓は**他ステージで誤答を差し戻す場面**に引き続き当てはまる。

**なぜ違うかは説明させない。数え直させるだけにする。**
理由を述べさせると、生成AIは手元の材料 (基準色の存在) を当てはめようとして
**当てはまらない場面でも使う**。差し戻しに理由は要らない。

あわせて**「了解」で受けない**。受理の言葉を使うと間違った報告を認めたように
聞こえる (実測: 「黄色ですね、了解です」)。

**禁止する例文をそのまま書かない** (N-29/N-32)。
『惜しい、もう一度数え直してくれ』と定型文を渡した実測では、
**5回中5回が一字一句その通り**に読み上げた。指針だけを書く。

#### シミュレーション台本の欠陥 — 誤答に基準色を選んでいた

原因の半分は**テスト側**にあった。`sim_wrong_color` は「cut でない最初の色」を
選ぶだけで、**点灯しっぱなしの基準色を除外していなかった**。
基準色を誤答にすると「それは基準だから数に入れない」は**正しい応答**になり、
検査したかった「理由を付け足していないか」を見られない。

**誤答の材料は、正解でもなければ特別扱いの色でもないものから選ぶ。**

> 回帰: `simStageVars` が `leds` の `"on"` を除外して `sim_wrong_color` を選ぶ
> 出典: 実装 2026-08-25

**中間の答えも「答え」として扱う**(決定85)。302 暗号電文・ジャミング で、
プレイヤーの誤答に対し**解読した語そのもの**を教えていた
(「デルタやない、ECHOや」)。切る線の色ではないため**色漏れ検査に掛からない**。

- 誤答が**語・数字・記号**のときも、正しいものを教えない。綴りの訂正も、
  頭文字だけ教えることもしない
- 差し戻すのは**読み取り作業のほうだけ**(「もういっぺん読み直して」)
- 台本側にも `MustNotMention` を置いて機械的に検出する

> 出典: NV 決定85

### N-43. 「仲間はずれ」は向きを毎回抽選する

**207 の仲間はずれが速い回と遅い回を混ぜる。** かつては `cut` が
必ず速い側に固定されており、「浮いているものを探す」必要が無く
**「一番速いのを探す」だけで当たった** — 104 早い者勝ち (イージー) と
同じ作業で、ノーマルに置く意味が薄かった。

方向が変わると癖では外れ、**4色揃っているものに対して浮いている1色**を
探す課題になる。ナビゲーターは**「速い方を探せ」と言わない** —
遅い回に誤誘導になるため、「4つ揃っていて1つだけ違うもの」と言う。

速度は抽選値から機械的に導く (`derive = "choice_value"`)。
**cut 側と rest 側を別々に人手で書かない** — 片方だけ直し忘れると
「5色とも同じ速さ」になり、謎が成立しないまま組み立てが通る (S-1)。

> 回帰: `TestOddOneOutVariesDirection`
> 出典: 実装 2026-08-24
302 は1文字なので所要時間が短く、「対照表を睨む時間」が増える懸念は薄い。

> 回帰: `TestLetterMatchStageIsReadable` / `TestSpokenLetterCoversAllCandidates`
> 出典: PZ 302 の項 / §2.4

## 7. TTS・音声

### T-1. TTS は必ずストリーミングで受け取る

`GenerateContentStream` を使う。一括の `GenerateContent` に戻すと**応答待ちが跳ねる** —
同一プロンプト15回で最大56.51秒、27%が10秒超。ストリーミングでは全て 2.2〜3.8秒。

遅延はモデルの推論ではなく**一括応答の待ち受け側**にあった。入力内容・並行数・出力量の
いずれとも無関係なことは実測で確認済み (`tts_latency_probe_test.go`。`-ttsprobe`)。

なお `service_tier` は **Vertex/Enterprise では使えない** (G-5)。
レイテンシ対策はストリーミング (T-1) とタイムアウト・リトライ (T-4) で行う。

> 出典: NV 決定15

### T-2. 1発話1リクエスト・1パケット

発話の分割 (`splitAnswerForTTS`) は廃止し、**発話全文を1回の TTS 呼び出し**にする。
全チャンクの PCM が揃ってから連結し、1回だけ Opus エンコードして**1パケットで送る**。

分割送信は「先頭ができ次第すぐ流せる」が、裏返すと**1チャンクの遅延が発話全体を
人質に取る**。

> 出典: NV 決定12・決定18 / BR 決定13

### T-3. TTS が1チャンクでも欠けたら発話ごと見送る

成功したチャンクだけ繋いで送ると**尻切れの発話**が無線に出る
(「私は見ている。」だけが流れ、続く指示が消えた)。不完全な指示は誤解を生むので、
黙る方を選ぶ。

WARN をログに残し、TTS の失敗を Management Console の API 状況にも反映する。
**タイムアウトを短くする判断はこの挙動とセット**で考える。

> 出典: NV 決定16

### T-4. API 呼び出しにタイムアウトを設ける

Transcribe / reply / TTS の各呼び出しに上限を設ける (`config.toml` で変更可)。
無線は「無音のまま待たされる」のが最悪なので、待ち続けるより打ち切る。

- **TTS: 10秒・3回**(T-1 のストリーミング化で短く切れる)
- **Transcribe / reply: 20秒**
- 10秒を超えた TTS 呼び出しは**プロンプト全文をログに残す** (`[gemini] TTS SLOW`)

> 出典: NV 決定13

### T-5. 表情タグは許可リストの6語だけ

使える語は `tts_prompt.go` の `allowedTTSTags` と `navigator/prompt.toml` の
**両方**に書く。片方だけ増やしても効かない(サーバーが落とすか、生成AIが使わないか)。
整合はテストで担保している。

一覧外のタグは落とす — 演技として解釈されず「リリーブド」と読み上げられるため。
会話ログへ記録するときは `stripTTSTags` で全タグを除去する(画面表示用)。

ディレクターズノートとの**併用**が最も良い(聴き比べで ノート+タグ > ノート単独 > タグ単独)。

> 出典: NV 決定17

### T-6. ディレクターズノートに場面を書かない

`directorNotes` に書いてよいのは**読み方だけ**。「プレイヤーの報告に応じる場面」のように
会話の状況を書くと、TTS がその場面を演じて**相手の発話まで自分で作り、本文の前に
読み上げる**。

「場面」「プレイヤー」「相手」「直後」「瞬間」は使わない。

> 回帰: `TestDirectorNotesDescribeDeliveryOnly`
> 出典: NV 決定25

### T-7. Opus の granule position は常に 48kHz

音声は 24kHz で生成・エンコードしているが、Ogg の granule position は
**入力レートによらず 48kHz で数える** (RFC 7845 §4)。
`encodePCMToOggOpus` で `opusGranuleRate / sampleRate` を掛けているのはこのため。

入力レートのまま書くと、**granule から尺を求める側が実尺の半分と誤認する**。
再生自体はデコード後のサンプル数で行われるため**表面化しにくい**。
尺を使う箇所は `audio_duration.go` (サーバー) と `queue.rs` (bridge)。

**エンコーダは2箇所ある。** `game-server/tts.go` と
`crosstalk-gen/audio.go` の**両方**がこの規則に従う必要がある。
crosstalk-gen 側は入力レートのまま書いており、**事前生成アセット全30ファイルが
実尺の半分と報告されていた** (2026-08-19 に修正)。混線の重なり判定が
実際の半分の時間しか無線を塞がっていないと誤認するため、**発話に混線が
かぶる**方向の事故になる。

**エンコーダを直しただけでは既存アセットは直らない** — granule は
ファイルに書き込まれているため、**再生成が必要**。2026-08-19 に全30ファイルを
再生成済み (`aserase_A` は 1.96s → 4.76s と実尺どおりになった)。
以後アセットを作り直したときは、`TestAnnounceAssetDecodes` と同じ要領で
生成ログの秒数と `oggOpusDuration` の値が一致することを確かめる。

> 出典: OP 決定13 / 回帰: `TestAnnounceAssetDecodes`

### T-8. 混線の重なり判定は再生時間ベース

「ナビゲーターが発話中か」を真偽値で持つのではなく、**再生時間**で判定する
(`BusyFor`)。`Speak` が返るのは bridge へ**送出**した時点で、再生はこれからのため。

> 出典: OP 決定12

### T-9. 効果音とメッセージは1つの Ogg に連結する

爆発後、効果音が鳴り終わってからメッセージを送る形だと間が空く。1つに連結して送る。

> 出典: OP 決定14

### T-10. 混線音声はすべて事前生成アセット

実行時 TTS は使わない。邪魔者系は色バリエーション、環境ボイス系は話者を全て変える。
**混線の声をナビゲーターの各キャラ・カラスと重複させない**。
イージーでは邪魔者系を再生しない(ノーマル以上で解禁)。

未配置でも起動はするが**無言でスキップされる**ため、起動ログの
`[crosstalk] loaded assets:` で件数を確認する。

> 出典: OP 決定6・決定7 / CT 決定6・決定8・決定10・決定11

### T-11. 待機中の無線から15分ごとに自動送信局アナウンスを流す

特小無線は**免許不要の共用チャンネル**で、他の利用者と周波数が重なりうる。
長時間占有すると迷惑になるため、カラスの声で「これはゲーム用の自動送信局である」
と名乗り、**譲る用意がある**と伝える (`announce.go`)。

**体験中の無線には流さない。** セッションが紐づいた bridge は必ず除外する
(カウントダウン中に割り込むと体験を壊す)。判定は `SessionForBridge` が nil か
どうかだけで行う。

混線 (`CrosstalkScheduler`) とは**逆向きの仕組み**である点に注意する —
混線はセッションごとに開始・停止するが、こちらはセッションが**無い** bridge が対象。
そのためサーバー全体で1つだけ動かし、周期ごとに宛先を選び直す。
塞がり判定も混線は `device_id` で持つが、**待機中の bridge には device_id が
存在しない**ため `bridge_id` で持つ。

- **周期はサーバー共通**。bridge ごとに独立させると同じ会場でバラバラに鳴り、
  運営が「今どれが鳴ったのか」を追えなくなる
- 事前生成アセットを再生するだけ (T-10 と同じ理由)
- 音声が未配置なら黙って無効。起動ログの `[announce]` 行で確認する

> 出典: OP 決定20・決定23 / 回帰: `TestAnnounceSkipsBoundBridge`

### T-12. アナウンスの声はカラスと一致させる

「こちらはカラス」と名乗る放送なので、疎通確認で応答するカラス
(`testResponderTTSVoice` = `Achird`) と**同じ声でなければ別人に聞こえる**。

混線音声がナビゲーター・カラスと声を重複させない規則とは**逆向きの要求**になる。
crosstalk-gen の重複検査は announce を除外し、代わりに
「カラスと一致すること」を検査する (`TestAnnounceUsesCrowVoice`)。

ファイル名も `announce.go` の `announceFile` と一致させる
(`TestAnnounceFileNameMatchesServer`)。片方だけ変えると**無言でスキップ**され、
鳴らない理由が分かりにくい。

> 出典: OP 決定21

## 8. セッション進行

### P-1. 開始申告からカウントダウンまでは Pending (青点滅)

申告受理 → `session_pending` (青点滅) → ナビゲーター応答 → 5秒 →
`session_start` (カウントダウン開始)。この数秒を Ready のままにすると
**申告が通ったのか失敗したのか現場から分からない**。

`session_start` は **Ready と Pending の両方で受理**する (`IsReady()` が両方を通す)。
Ready だけにすると、自分が送る `session_start` を自分で拒否する数秒ができる。
Pending は Ready と同じ安全動作を引き継ぐ — WS切断・線が外れたら Setup へ戻す。

> 出典: GS 決定59

### P-2. カウントダウンはナビゲーターが応答してから始める

`StartSession` は **`session_start` を送る前に** `announceReady` で応答させる。
先に送ると、生成 + TTS の数秒がまるごと無言になる。

順序は **発話 → 鳴り終わり → `countdownStartDelay` (5秒) → `session_start`**。
鳴り終わりの判定は T-8 と同じ `BusyFor` を使う。

**同期で待つ**こと。非同期にすると「準備完了」と言っている最中に時間が減り始める。
発話に失敗した場合は**猶予を待たずに開始する**(無線は無言になるが、
装置の前にプレイヤーが立っている以上、開始できない方が困る)。

> 出典: NV 決定36

### P-3. `session_ready` と `session_start` は交信相手が違う

- **`session_ready`** → **マネージャー**への応答。「こちらフクロウ。待機完了」程度の
  簡素な一言。CoreID や難易度の復唱は入れない(無線は短いほどよい)
- **`session_start`** → **プレイヤー**への第一声。相手が変わるので改めて名乗り、
  **「自分がついているから大丈夫だ」という一言を添えて**からランプの状態を尋ねる

危険物が起動した瞬間なので**用件だけの事務的な第一声にしない**。
この発話に限り 80 文字まで許容する(`navigatorMaxRunes` は 60 のまま。
緩めるのは**トリガーの指示の中だけ**)。

安心のさせ方はキャラクターごとに変える(N-19)。**キャラシートの「開始」例も揃える**。

> 出典: NV 決定37・決定43

### P-4. ゲーム終了後は表示と応答を分ける

終了(爆発・解除)したセッションは **binder に残したまま `Finished` を立てる**。
消すと Management Console の進行表から消えて結果を確認できない。

`SessionForBridge` が終了済みを nil として返すことで、**無線の応答だけ**がカラスへ移る。
次のゲームは開始申告で新しいセッションを上書きすればよい。

> 出典: OP 決定16・決定17

### P-4b. リセットは Valkey からも消す(`session:{id}` は無条件)

`AbortSession` (リセット) は `store.DeleteSession` まで呼ぶ。
binder を外すだけだと、サーバー再起動時に `LoadSessions` が読み戻し、
**リセットしたはずのセッションが復活する**
(`docker compose down` → `up` で実際に発生した)。

**`session:{id}` は終了済みかどうかを問わず、リセットのたびに無条件で消してよい。**
以前は「終了 (爆発・解除) したセッションだけは消さず残す」としていたが、
運用は成功・失敗を問わず**終了後も必ずリセット申告する**
(`manager_manual.md` §6.3) ため、その例外が**履歴を毎回消す不具合**になった
(P-4c 参照)。履歴は P-4c で別キー (`history:{id}`) に分離したので、
`session:{id}` 側は例外を持つ理由が無い。

**ログは中断でも消さない。** 中断イベントもログに記録されており、
消すと「なぜ終わったか」が追えなくなる。
消すのはセッション本体と `binding:` キーだけ。

メモリ上の bridge → device の紐付けは残す(再接続で継続できるようにする設計)。

> 出典: GS 決定60・決定62 / 回帰 `TestAbortedSessionDoesNotSurviveRestart`・
> `TestFinishedSessionSurvivesRestart`・`TestReleaseAfterFinishWritesHistory`

### P-4c. 履歴は `session:{id}` と別キーへ分離する

`session:{id}` は「今バインド中のセッション」専用と割り切り、
**履歴 (Management Console の振り返り用) は `history:{session_id}` へ独立させる**。

`session:{id}` は再起動時の復元と進行中ダッシュボード表示にしか使わず、
リセットのたびに無条件で消える (P-4b)。一方、履歴はいつリセットされるかに
関係なく残す必要がある。両者を同じキーに同居させると、
**「履歴のため終了セッションを消さない」という例外が、
「終了後も必ずリセット申告する」という運用と衝突し、
結局リセットのたびに履歴が消える**(§9)。

`releaseAfterFinish` (爆発・解除でセッションを終了させる箇所) で、
**終了の瞬間に一度だけ** `history:{id}` へスナップショットを書く。
内容は `session:{id}` と同じ `GameSession` の JSON — 履歴詳細ページが
`Built.Stages` (到達しなかった先の正解) まで使うため、要約用の別型は作らない。

中断 (未終了のままのリセット) は今まで通り履歴に出さない。
ログ (`session:{id}:log`) は変更なし — 発話・進行イベントの記録という
役割はそのまま。

> 出典: GS 決定62 / 回帰 `TestReleaseAfterFinishWritesHistory`

### P-5. リセット対象はバインド優先で決める

CoreID の聞き取りは誤認識しうるため、リセット対象は**バインド情報を優先**して決める。

デバイスが未接続でも**サーバー側の状態整理とログ記録は必ず行う**。

> 出典: OP 決定18 / GS 決定22

### P-6. 秘密ワードは表記ゆれをカンマ区切りで全て並べる

音声認識は同じ音を別の表記で返す。判定はかな正規化のゆるい一致だが、正規化は
カタカナ→ひらがなの変換しかせず**漢字はかなへ戻せない**。

「でんぱ」だけを設定していたところ STT が「電波」と返し、**キルスイッチが効かなかった**。
`"でんぱ,電波"` のように全て並べる。

> 出典: OP 決定15・決定9

### P-7. 起動ログに commit id と設定内容を出す

「設定を直したのに反映されない」を切り分けるため、起動ログの先頭3行に
commit / 設定ファイル名 / 秘密ワードの語数を出す。

commit id は `go build` が `.git` から自動で埋め込むため、
**compose の build context はリポジトリルート**にしてある。

> 出典: OP 決定19

### P-8. カラスは雑談相手・検索はカラス限定

「疎通確認用」と分かる応答だと会話が続かず、音声品質の確認がしにくい。
**Google 検索グラウンディングはカラスだけ**に付ける。

**無線家色は抑える。** 当初は「無線が趣味の人物」「機材や電波の話が好き」と
書いており、話題がそこへ偏って**相手として濃くなりすぎていた**。
無線は持っているが、**機材や電波の話を自分からは振らない**
(振られれば応じる程度)。話が途切れたときに振るのも天気などありふれた話題にする。

設定自体は残す — 混線演出で他の無線が飛び交う世界なので、
無線家がいること自体は自然で、「なぜこの周波数にいるのか」の説明にもなる。
問題は**その話ばかりすること**なので、そこだけ抑える。

> 出典: OP 決定10・決定11 / 無線家色の抑制は実運用の指摘

## 9. core-system (ファームウェア)

### C-1. 実経過時間の差分で tick を進める

キュー待ちのタイムアウトだけに頼ると入力イベント連続時に tick が飢え、
カウントダウンが止まる。

> 出典: GS 決定18

### C-2. MCP23017 の INTA はレベルで見る(エッジで拾わない)

MCP23017 の割り込みは**GPIO を読み出すまでクリアされない**ため、その間 INTA は
LOW に張り付く。エッジで拾うと**読み出す前に次の変化が起きた時点で入力検知が
永久に止まる**(ロータリーを速く回すと検知ログが消える)。

`gpio_watcher_.SetPollHandler()` で5msごとに `ScanIfPending()` を呼び、
INTA のレベルを毎周期確認する。取りこぼしても次の周期で拾い直せる。

**ロータリーの確定は差分の有無で条件分岐しない**。過渡状態(全OFF)を読んだ
スキャンが差分を消費すると、その後安定しても確定処理に入れなくなる。

> 出典: GS 決定53・決定54

### C-3. 切った線の「結線」通知はプレイ中に受け付けない

ニッパーで切る瞬間、切断面が接触し直して **`切断 → 結線 → 切断` が数十ms間隔で届く**。
2度目の切断を処理すると、ステージ遷移後には「誤った線の切断」として評価され、
`on_wrong_cut: explode` のステージで**正しく切ったのに即爆発**する。

デバウンス (5ms × 3 = 15ms) より長い間隔で届くので**フィルタ時間を延ばしても防げない**。
`HandleLineChanged` が `STATE_PLAYING` 中の結線通知を破棄し、`OnLineCut` が
1本につき1回だけ呼ばれるようにしてある。

Setup 中の復帰は復旧ガイドに必要なため対象外。

> 出典: GS 決定57

### C-4. 配線テーブルは hardware_config.h にしかない

色や位置で引く対応表は**すべて `hardware_config.h`** に置く。
`kLineGpiosByColor` / `kLedPinsByColor` / `kPushGpiosByColor` /
`kRotaryGpiosByPosition` の4つ。他のファイルへ同種の表を作らない。

LEDの出力ピンはこの5本がすべてなので、順序を問わない初期化ループも
`kLedPinsByColor` を回す(同じ配線を別の並びで二重に書かない)。

> 出典: GS 決定33

### C-5. ロータリーの位置対応

`kRotary1`→位置0 〜 `kRotary6`→位置5。GPIO番号は**降順** (GPA7→GPA2) で
直感に反するため、`kRotaryGpiosByPosition` は**配列の添字がそのまま位置番号**になる
並びで定義している。

ここがずれると全ステージのロータリー条件が1つずれ、「**動くが正解しない**」形で現れる。

> 出典: GS §3

### C-6. ソレノイド(風船破裂)の安全ガード

駆動は単一関数に集約し、**Detonating 状態からのみ**呼べる。二重駆動はフラグで防ぐ。
**この安全ガードを緩めないこと。**

> 出典: GS 決定16

### C-6b. ミスには必ず音のフィードバックを付ける

**無線越しでは画面が見えないので、音が唯一のフィードバック**になる。
反応が無いと失敗したことに気づけず、緊張感も出ない。

| ステージ | 挙動 |
|---|---|
| 103 コール&レスポンス (イージー) | ブザー + **3秒** |
| 201 / 305 | ブザー + **5秒** |
| 204 色合わせ | ブザー + **5秒** |

`ACTION_PENALTY` でも**列は先頭に戻る** (`push_seq_input.h`) ので、
やり直しの難しさは変わらない。ブザーと減算が足されるだけ。

色合わせ (旧モグラ叩き) は**ミスを返す仕組み自体が無かった**ため、
`WhackGame::HandlePush` / `Tick` の戻り値を `bool` から
`WhackResult` へ変え、`WhackSpec.penalty_ms` を追加した。

**イージーは軽く (3秒)。** 操作に慣れていない段階で5秒引くと立て直せない。
ペナルティは「気づかせる」ためであって罰ではない。

> 出典: NV 決定49

### C-6c. 破裂の閃光はパルス幅の内側で完結させる

ソレノイド駆動と**同時に**白 (255,255,255)・最高光度で 100ms 光らせ、赤点灯へ戻す。
`FireSolenoid` は HIGH → 閃光 → 復帰 → 残り待機 → LOW の順で進み、
**200ms のパルス幅は変わらない**。

閃光を先に置いて駆動を後ろへずらすと、破裂音と光がずれるうえパルス幅が実質延びる。
**駆動のタイミングと長さには手を入れないこと** (C-6 の安全ガードと同じ理由)。

> 出典: GS 決定61

### C-6d. ブザーの音長で場面を区別する

音は**長さでしか意味を分けられない** (アクティブブザーで音程制御が無いため)。
同じ長さを別の場面へ割り当てると、無線越しのプレイヤーは区別できない。

| 場面 | 呼び出し | 鳴り方 |
|---|---|---|
| ゲーム開始 | `Beep(1, 1)` | **100ms** ×1 |
| ミス・ペナルティ | `Beep(1)` | **200ms** ×1 |
| 解除成功 | `Beep(3)` | **200ms** ON/OFF ×3 |
| 破裂確定 (Detonating) | `On()` | 連続 |

`Buzzer::Beep(count, on_ticks, off_ticks)` の tick は `GameTask` の
**100ms tick** (`buzzer_.Tick()`) で進む。`on_ticks` の既定は 2 なので
**引数を省くと 200ms** になる。開始音だけ `on_ticks = 1` を明示している。

**開始音を短くしたのはミス音と取り違えないため。** 開始直後に
200ms が鳴ると「もう間違えたのか」と読める。長さを変えれば、
音程が無くても「開始」と「失敗」が耳で分かれる。

> 出典: GS 決定64

### C-7. 起動シーケンス

- 起動演出は電源投入から約2.8秒。**WiFi接続より先**に流す
- 起動インジケータはフルカラーLED — 紫点灯=初期化中 / 紫点滅=初期化失敗
- **サーバー接続まで紫を保つ**(Wi-Fi接続後すぐ黄点滅にしない)
- WiFi接続は**15秒でタイムアウト**して起動を続行する
- **起動時の結線状態を読む**(線が切れたままでも Ready になっていた)

> 出典: GS 決定26・決定27・決定28・決定36・決定42

### C-8. 表示まわりの実機調整

- **待機中のフルカラーLEDは20%**(実機で眩しかった)
- **Playing の点滅は4段階**(通常時のチカチカを抑える)
- **Setup 中の復旧ガイドは「結線済みを点灯」**(切断中を点灯から反転)
- **Deep Sleep 前に全消灯**する

> 出典: GS 決定38・決定44・決定48・決定40

### C-9. バッテリー低電圧保護

30秒ごとに電圧測定(220kΩ×2分圧、実電圧=測定値×2)し、3.4V未満が続けば
Deep Sleep へ入る。USB給電での動作確認のため **`menuconfig` で無効化できる**。
ブザーも同様に無効化できる。

> 出典: GS 決定17・決定45・決定58

### C-10. 書き方の決まり

- **`switch` は使わない。`if` で書く。** 列挙型の分岐も `if (x == A) { ... }` を並べ、
  最後に既定値を返す形にする
- **`if` の本体は必ず中括弧で囲み、改行する。** `if (x) return;` のような
  一行の書き方はしない。`else if` の連鎖は可

**ファイルの分かれ方**: 状態を持つのは `GameTask` に寄せ、周辺は
**ゲーム状態に触れない部品**にする。ただし **Tick系は GameTask に置いたまま** —
残り時間・進行状態を書き換えるため、切り出すと参照の引き回しが増えて逆に読みにくくなる。

> 出典: GS 決定34・決定35

### C-11. 色合わせは押すまで待つ。時間で切り替えない

`color_match` は**時間の概念を持たない**。1色だけ点灯した状態で押すまで待ち、
正しいボタンを押した瞬間に次の色へ進む。**時間で切り替える作りに戻さないこと。**

もともと「モグラ叩き」として点灯時間で切り替えていたが、
押下が無ければ必ず時間切れの枝に落ちるため、
**無操作でもブザーが鳴り続け、ペナルティで勝手に時間が溶けて爆発した**
(206 の実機で発生。約1.9秒ごとに5秒減算 = 実時間の2.6倍速)。
**ヒット後の状態が時間切れ後と同一**になるのが構造上の落とし穴で、
tick 側から両者を区別できなかった。

押すまで待つ形にすれば、時間切れという分岐自体が存在しない。
ミスは**誤押下だけ**で、通知は `HandlePush` のみが行う。

**完了時は kLED を全消灯**にし、ステージの `leds` ヒント表示へ戻さない。
手がかりを「最後に押した色」の記憶だけに絞るため
(`ClearOverride()` ではなく `SetOverrideAll(false)` を使う)。

> 出典: GS 決定25・決定26

### C-12. forbidden_rotary は実際に動くまで判定を始めない

`TickForbiddenRotary` は禁止判定を**プレイヤーが一度でもロータリーを動かすまで武装しない**
(`rotary_touched_since_reset_`)。`ResetStageProgress` (ステージ開始のたびに呼ぶ) でこのフラグを
下ろし、`HandleRotaryChanged` が実際の位置変化を検知したときだけ立てる。

ロータリーは物理的な位置が**プレイ間で保持される**。前回のプレイヤーが偶然
禁止位置(206 綱渡りなら 1 か 2)で止めたまま終わると、次のセッションでその
位置がまた `forbidden` に抽選された場合、**プレイヤーが何も操作していないのに
PLAYING開始から `kForbiddenRotaryHoldMs` (300ms) 経過しただけで無警告のまま
爆発する**(209 のテストプレイで発覚。設計は「危険位置は最初に必ず伝える」
としていたが、伝える暇もなく即爆発していた)。

目標位置と禁止位置は重ならない (209 は target=3-5, forbidden=1-2) ため、
この待機はパズルの難度に影響しない — どのみちプレイヤーはダイヤルを
動かさなければ目標へ到達できない。

> 出典: GS 決定63

### C-14. ロータリー位置ごとにLED表示を差し替える (209 配電盤照合)

`rotary_leds` を指定すると、**ロータリーを回すたびに表示が変わる**。
位置0-5 それぞれのLEDテーブルを持ち、`leds` の代わりに使う。

| 位置 | 表示 | 意味 |
|---|---|---|
| 現在位置 | 対照表どおり(点灯+点滅) | ここから紙資料を引く |
| 解除位置 | **cut だけが点滅**+ダミー点灯 | ここで切る |
| 危険位置 | **赤だけ点灯** | 止まると即爆発 |
| その他 | ランダム2〜3色点灯 | ダミー |

**解除位置の見え方を紙資料に載せない。** 載せると「解除位置は3 → その行の
点滅色が答え」と**回す前に切る線が分かり**、回す工程が消える。

**1色だけの点灯は「危険位置にいる」に予約する。** 対照表の行はすべて
点灯+点滅の2色なので、単独点灯は必ずこの意味になる。
**ダミーも2〜3色にする** — 1色だと合図と紛れる。

**cut が対照表の点滅色と重なる行は抽選しない。** 重なると現在位置の表示で
cut が点滅し、やはり回す前に答えが見える。

**危険位置は必ず現在位置と解除位置の「間」に置く。** 経路の外にあると
素通りできてしまい、「止まらずに通り抜ける」緊張が消える。
ロータリーは直線配置 (0-5) なので、間に置けば必ず通過する
(起動時に `validatePanelTable` が検査する)。

位置が変わったら `ResetPatterns()` でパターン再生を先頭へ戻す。
戻さないと前の位置の途中から流れ、別の見え方になる。
**`Reset()` は使わない** — 上書き表示まで消えてしまう。

> 回帰: `TestPanelStageRotaryLeds` / `TestPanelTableIsValid`
> 出典: 実装 2026-08-25

### C-13. 押し切ったら切る線だけを点灯させる

`push_seq.reveal_cut_on_complete` を立てると、**押し切った時点で
切る線の色だけを点灯**させ他を消灯する。押下フェーズの終わりが
装置から一目で分かり、次に何をするかが視覚的に伝わる。

**使っている2ステージで見え方が違う。**

| | 押下中 | 押し切ったあと | 生まれる対話 |
|---|---|---|---|
| **103 コール&レスポンス** | 報告用=**点灯** + 切る線=**点滅** の2色 | 切る線だけ点灯 | 「報告した色と切る色が違う」という気づき |
| **201 復唱** | 報告用の**1色だけ** | 切る線だけ点灯 | 「押し終わったらランプが**変わった**」という変化の報告 |

**103 は最初から2色見せるのが要点。** 押し終わってから初めて切る線が光る
形にすると、「報告した色と切る色が違う」という気づきが発生せず、
ただの「押し終わったら光った色を切る」になる。

**201 は逆に、押し切るまで切る線を見せない。** 103 と同じ見え方にすると
2ステージが重複する。201 の持ち味は**列を聞いて覚えること**なので、
押下中に切る線まで見えていると情報が増えて散漫になる。
押し切ったあとの**変化**が次の行動の合図になる。

どちらも**報告用の色と切る線の色は別の色**にする (`lit` を
`exclude = ["${cut}"]` で引く)。同色だと leds が1エントリに潰れ、
押下前後で見え方が変わらない。

**オプトイン**。既定は false なので、他のボタン列ステージの見え方は変わらない。

**ナビゲーター知識に「色が変わる」を書く** (201)。書かないと、
押す前に見た色をそのまま切らせかねない。`answer` に
「最初に点いているのは報告用で、これは切る線ではない」と明記する。

> 出典: 実装 2026-08-24 (103) / 2026-08-25 (201)

### G-5. `service_tier` は空にする (Vertex/Enterprise は受け付けない)

**2026-08-20 の実測で撤回。** Priority を狙って `service_tier` を入れたが、
**Vertex/Enterprise はどの値も受け付けない**。

```
Error 400: Invalid value at 'service_tier'
(type.googleapis.com/google.cloud.aiplatform.v1beta1.ServiceTier), "priority"
```

`"priority"` / `"standard"` / `"flex"` のいずれでも 400 になり、**未指定だけが通る**。
指定したままにすると文字起こし・発話生成・TTS が全滅してゲームが成立しない。

SDK (`google.golang.org/genai`) がリクエストに載せることと、
**サーバーが受理することは別**。送信の検証 (`service_tier_wire_test.go`) だけでは
足りず、実APIを叩くまで気づけなかった。

設定項目自体は残してある (将来 Vertex 側が対応したら使えるため)。
`tts_service_tier` で **TTS だけ別のティア**を指定することもできる —
TTS はレイテンシが体験に直結する (T-1・T-4) 一方、文字起こし・発話生成は
多少遅れても間が空くだけなので、使い分けの余地を残した。

以下は Gemini Developer API (APIキー認証) 側の性質。**この構成では使えない**が、
将来の判断材料として残す:

- 課金は標準の **75〜100%増し**
- レート上限は標準の **0.3倍**
- 容量超過時は**失敗せず standard へ自動降格**

（以下は当初の記述。実測で覆るまでの経緯として残す）

文字起こし・発話生成・TTS の**3経路すべて**を Priority で呼ぶ。
無線越しの体験はレイテンシがそのまま沈黙になるため、費用より応答速度を採る。

**代償を承知の上での選択**である:

- 課金は標準の **75〜100%増し**
- レート上限は標準の **0.3倍**
- 容量超過時は**失敗せず standard へ自動降格**する(その分は標準料金)

`config.toml` で切り替えられる。当日に費用が問題になったら
**再ビルドなしで `"standard"` へ落とせる**ようにしてある。
綴りを間違えると黙って標準ティアに落ちる — 「priority のつもりで課金だけ標準」を
避けるため、**不正値は起動時に落とす**。

実際に効いているかは起動ログ `[boot] gemini service tier:` で確認する。

**未設定は空文字にすること。** `genai.ServiceTierUnspecified` の実体は文字列
`"unspecified"` で、`omitempty` に落ちず**そのまま送信されてしまう**
(回帰: `TestServiceTierOmittedWhenUnset`)。

`serviceTier` は `generationConfig` の**中ではなくリクエストのトップレベル**に載る。
送信されることは実リクエストを捕まえて検証済み
(`service_tier_wire_test.go`。一括・ストリーミングの両経路)。

### G-6. Interactions API へは移行しない (2026-08 時点)

Gemini のドキュメントは Interactions API (`v1beta2/interactions`) を推奨し
`generateContent` を「レガシー」と位置づけているが、**移行しない**。

- **Go SDK に存在しない**。`google.golang.org/genai` v1.68.0 (最新) の
  `genai.Client` は `Models` / `Live` / `Caches` / `Chats` / `Files` / `Operations` /
  `FileSearchStores` / `Batches` / `Tunings` / `AuthTokens` の10サービスのみ。
  `client.Interactions` はコンパイルが通らない。Python / JS のみ対応
- **エンドポイントが別系統**。Interactions は `generativelanguage.googleapis.com`
  (= APIキー認証の Gemini Developer API) で、**G-4 の決定と正面から衝突する**
- `generateContent` は「レガシーだが引き続き完全にサポート」と明記され、
  廃止期限の告知もない

grep で当たる `InteractionStatus` は **Live API (WebSocket) の応答フィールド**で
無関係。紛らわしいので注意する。

なお Priority 自体が **Vertex/Enterprise では使えない** (G-5)。

追跡先は **go-genai issue #658 (Open / P1)**。実装PR (#770・#829) は closed で
未リリース。**入り次第この決定を見直す**。

> 出典: 本ドキュメント (2026-08-19 調査)

## 13. 紙資料

### D-1. 紙資料とサーバー設定は連動させる

`config.toml` の `[mission_sheet]`(端子対応・**資料の呼称**)は
**印刷物の実測値**。刷り直したら設定も更新する。
ただし 301 LED照合 の対照表は固定のため設定に持たせない(D-3)。
印刷内容の仕様は `docs/printed_materials.md` に集約している。

### D-2. 紙資料は資料番号で指す

紙資料は **A4裏表1枚**にまとめ、**独立して参照される要素ごとに「資料N」を印刷**する
(資料1=モールス対照表 / 資料2=変換表+デコード表+分岐表 / 資料3=回路図)。
ナビゲーターは **「手元の資料1を見ろ」と一言で**指示する。

- **番号は物理的な紙の枚数ではなく参照単位**で振る。301 LED照合 は資料2→3→4 と
  3枚を順にたどるため、同じ面にあっても別番号。逆に**複数ステージが
  同じ資料を見る**(202・302・305 はどれも資料1)。
- **面 (表裏) は持たず、ナビゲーターも指示しない**。面を言うと印刷レイアウトを
  変えるたびに設定と文面の更新が要る。探す手間もプレイヤーの遊びのうち。
- 呼称は `[mission_sheet.documents]` に持ち、ステージ定義は `${sheet_morse}` 等で
  参照する。**文面へ直接「資料1」と書かない** — 振り直しで食い違う。
- 301 LED照合 は**資料2 だけで完結する**(変換表 → デコード表 → 分岐表)。
  呼称は `${sheet_codebook}` の1つで、ナビは2つ目以降で番号を言い直さない。
  **分岐表を回路図(資料3)へ載せない** — 205 の視界に色対応が入る (D-9)。
- 呼称が空だと空文字に展開され「を使って解読しろ」になるため、**起動時に落とす**。

**フォネティックコードは使わない** — 資料1がモールス対照表そのもので、
「資料アルファ」がSTTに乗ると資料名か解読した語か区別できない。

> 回帰: `TestCodebookStageResolves`
> 出典: NV 決定33 / PM 決定1-10

### D-3. 301 LED照合 の対照表は実装に1箇所だけ置く

301 LED照合 の対照表(ランプの並び → キーワード → ダイヤル位置 → 切る線)は
`app/game-server/scenario_codebook.go` の `codebookTable` **だけ**に置く。
**config には出さない** — 端子対応や旧「運命の二択」の記号数と違い、対照表は
**抽選に関わらず固定**で、刷り直しても値が変わらない。設定に出すと
紙・設定・実装の3箇所が食い違いうる。

**紙とサーバーの一致はテストで担保する**。対照表は解いた結果しか持たないため、
途中の変換規則(デコード表の区間・色割当、分岐表)を書き換えても
Go 側は静かに通る。**プレイヤーは紙どおりに解く**ので、ずれると理不尽に失敗する。
`TestCodebookMatchesPrintedRules` がデコード表・分岐表を独立に実装して照合している。

> 回帰: `TestCodebookMatchesPrintedRules` / `TestCodebookTableIsValid`
> 出典: PM 決定20・24・25

### D-4. 資料番号と中身は初出でひとまとまりに言う

「手元の資料1にモールスの対照表がある」と**番号と中身を続けて**伝える。

どの資料に何が載っているかは**装置を見ても分からない情報**で、番号だけ言われた
プレイヤーは探しようがない (N-4)。2回目以降は番号だけでよい。

> 出典: PM 決定7

### D-5. 資料1は符号表と色対応に分けない

203 のプレイヤーは「`・－` を引いて A、その A の色は赤」と**同じ行を2回引く**。
同じ行に色が並んでいれば視線移動が要らない。分けると無線で急かされながら
2つの表を往復することになり、難度が「見つけにくさ」ではなく「探す手間」で上がる。

> 出典: PM 決定6

### D-6. 203 ブループリントの端子は X/Y の2系統。ナビは両方を並べて言う

資料3には **X1〜X5 / Y1〜Y5 の10端子**を描く。どちらを使うかは
**Core 外装のシリアル銘板の下1桁**で決まる (奇数=X / 偶数=Y)。

ナビゲーターは**両系統を並べて**言う:

> 「シリアル銘板の下1桁が**奇数ならX4、偶数ならY2**の線を切れ」

- **片方に絞って言わない。** サーバーは個体のシリアルを知らないため絞れず、
  絞ると選択の主体がナビへ移って**増やしたかった工程が消える**。
  この設計なら `ScenarioBuilder` へ device_id を通す実装も要らない。
- **「奇数=X / 偶数=Y」は紙に印刷しない。** 紙に書くとナビへ確認せず進められ、
  交信の往復が減る。
- **X と Y は完全に別の対応**にする。一部でも揃えると取り違えても偶然当たり、
  銘板を見る意味が薄れる。**全一致なら起動時に落とす**。
- 登録漏れは**その色が正解になったセッションだけ**が失敗し、抽選次第でしか
  再現しない。両系統×5色を**起動時に検査**する。
- 端子の X/Y プレフィックスは、資料番号 (資料3) との数字の重なりも解消する。
- **銘板は1枚**。「シリアル銘板 (CoreID記載)」で、運営が音声申告に使う CoreID と
  同じもの。**呼び方だけ場面で変える** — プレイヤーには「シリアル銘板」、
  運営には「CoreID」(プレイヤーは運営用語を知らないため)。
- **CoreID の採番で奇数と偶数を混ぜる**。全台が奇数だと Y系統が一度も使われない。
  ファーム書き換えでIDを振り直すと、その個体の系統も変わる。

難度は normal に据え置く。増える工程は「銘板の下1桁を見る」だけで、
解読も計算も伴わない。

> 回帰: `TestBlueprintOffersBothTerminalSeries` / `TestTerminalMapsValidate`
> 出典: PM 決定13-18

### D-7. 301 LED照合 の表示は cut から逆引きする

`pick = "codebook"` は**先に抽選した `cut` に対応する表示**を選ぶ。
表示を先に引いて cut を導く向きにすると、他ステージで使用済みの色を
避けられず S-2(切断線を余らせる)を破る。

対照表は**5色すべてに最低2通りずつ**表示が対応するよう語を選んである。
1通りしか無い色があると、その色が正解の回は毎回同じ表示になり暗記できる。
**全消灯(0000)は載せない** — 故障と見分けがつかず、プレイヤーが止まる。

> 回帰: `TestCodebookStageResolves`
> 出典: PM 決定20・22

### D-8. 資料の見出しはランプの色名で書く。位置番号を使わない

301 LED照合 の資料2 は「黄・緑・青・白」を見出しにする。**「LED2〜LED5」と
位置で書かない** — 実機のランプは色で識別する(A=赤〜E=白)ため、
位置番号を持ち込むとプレイヤーが左から数え直すことになる。
セーフティーグラス着用・立ったまま参照するので数え間違いが起きる。

資料2 の分岐表も同じ理由で「緑のランプ」「白のランプ」と書く。

**ロータリーは 0-5 の6接点**。デコード表の頭文字区間は **5・4・4・4・4・5** に割る。
等分(5文字ずつ)にすると Z が6番目にはみ出し、物理的に合わせられない。

> 出典: PM 決定21・23

### D-9. 資料は「そのステージが引くもの」だけを載せる

**301 LED照合 の分岐表を回路図(資料3)へ載せない。** 資料3 は 203 ブループリント が
「端子番号だけを頼りに色を引く」ための紙で、205 の原則は
**シートだけが手がかり・ナビは色を言わない** (D-6)。そこへ 301 用の
**色の分岐表**を同居させると、205 のプレイヤーの視界に色対応が入る。

一般化すると、**余白があるという理由で別ステージの表を相乗りさせない**。
資料は「面をどう埋めるか」ではなく「**どのステージが何を引くか**」で分ける。

301 LED照合 は資料2 だけで完結し(変換表 → デコード表 → 分岐表)、
資料3 は 203 ブループリント 専用。ナビが 301 で `${sheet_circuit}` を口にすることは無い。

> 出典: PM 決定28

## 14. 検証の進め方

### V-1. シミュレーションは1回で判断しない

生成AIの出力はばらつく。**色漏れ・字数のような変動しやすい所見**は
1回のパスで「直った」と判断しない。

- 修正の確認は**同じステージを2回以上**
- 全体傾向は**キャラクターを変えて**見る(N-18 の口調依存があるため)

> 出典: NV 決定39

### V-2. キャラクターを変えて回す

口調で出る問題が違うため、フクロウだけでは足りない:

| キャラ | 出やすい問題 |
|---|---|
| アオサギ (敬語) | 字数超過 |
| ツグミ (命令形を使わない) | ステージ知識の口調写し |
| ヒバリ | 最も字数が厳しい。詰め込みすぎが最初に現れる |

> 出典: NV 決定31・決定34

### V-3. 台本のターン順は実際に起こりうる並びにする

`session_start` の直後へ `stage_cleared` を置くと、**実機では起こりえない並び**を
検証してしまう。トリガーを足すときは「その順番が実機で起こりうるか」を確かめる。

シミュレーターの**「1ステージ=1セッション」という都合を出力に持ち込まない**。

> 出典: NV 決定32・決定42

## 15. 運用上の前提

- **難易度の語彙**: イージー / ノーマル / ハード の3段階。
  シナリオテンプレートの難易度分類も同じ3分類 (OP 決定1)
- **会場構成**: Core は複数台の並行プレイに対応(台数固定にしない)。
  現行の会場計画は2台想定 (OP 決定8)
- **バインド**: チームごとの周波数分離 + 周波数ごとの専用オーディオIF (OP 決定2)
- **開始申告の誤認識対策**: 復唱応答 + 言い直し(後勝ち上書き) (OP 決定9)
- **成功・失敗の演出**: 効果音 + メッセージを再生。失敗時は破裂前の `exploded` 通知で
  破裂と演出を同期させる (OP 決定5)
- **キルスイッチ**: マネージャーの秘密ワード付き音声コマンドで強制リセット (OP 決定4)
- `config.toml` / `config-mac-docker.toml` は**秘密ワードを含むため gitignore 済み**。
  スキーマを変えたら `*.sample.toml` も揃える
